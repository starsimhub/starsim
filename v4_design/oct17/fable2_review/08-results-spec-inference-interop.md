# Results, model spec, inference, and interop: review

I read `design/09-results.md`, `13-inference.md`, `14-model-spec.md`, `16-interop.md`, the two best-practices files, the 09/13/14–16 sections and departures/known issues of `admin/implementation.md`, and the code in `starsim/results.py`, `spec.py`, `calibration.py`, `run.py`, `samples.py`, `interop/`, plus the result-creating parts of `solvers.py`, `transitions.py`, and `sim.py`; I ran small sims with the v4 python to check the timing convention, data alignment, the spec round trip, `to_code`, and many-run results. Verdict: the v4 pieces that are new are good and mostly match the spec (the time-point convention is right and tested, `data` by name works, `calibrate()` really is one call, the importers share one honest core), but each area is two systems side by side: v3 `Result`/`Results`/`reduce()` next to v4 strata and `MultiResult`; v3 `Calibration`+`CalibComponent` (1,150 lines) next to v4 `fit()`; six ways to run many sims; three names for the model file. The biggest user-facing costs are a flow/stock flag that only some results carry (so a `new_infections` data column is aligned wrongly), a many-run plot that draws one line, and a model spec whose rate strings and likelihoods do not round-trip in cases the design uses as its examples.

## Top findings

1. **Every result needs a flow/stock kind; today only transition flows and outcomes carry one, and the data alignment reads only that flag.** `solvers.py:1218` and `:1325` set `summarize_by='sum'` on transition flows and outcomes, but `n_<state>` (`:1215`), `new_infections`/`cum_infections`/`prevalence` (`:1224`), declared expressions (`:1226`), and `cum_<transition>` (`:1219`) get `None`. `calibration.compare()` decides flow-or-stock with `res.summarize_by == 'sum'` (`calibration.py:1330`, also `lineup()` `:1359`), while `sim.check_dt()` uses `res.summarize_by or res.summary_method()` (`sim.py:476`) and `resample()` uses the name heuristic (`results.py:303–322`). Verified: a data column named `new_infections` (the name the design keeps "so data files written for Starsim carry over", 09 §Automatic results) is interpolated as a stock, so weekly data of 24.1 and 30.9 is compared with 3.9 and 4.8; a column named `infection` is summed correctly. Proposal: give `ss.Result` one field, `kind` in `{'flow', 'stock', 'ratio'}` (or just always set `summarize_by`), set it for every auto-generated result in `init_results()`, and make `compare()`, `check_dt()`, `resample()`, and `annualize()` read only that. `summary_method()`'s name-sniffing (`new_` → sum, `_n_` → mean) can then go. Breaks nothing; v3 modules that declare results without a kind fall back to the heuristic once.

2. **`sim.run(n_runs=20).plot()` draws one run.** `restart_runs()` returns a `MultiSim` whose `sims` holds one sim per *input* sim (`run.py:1162`) with the runs only in `msim.results`, but `MultiSim.plot()` with `which is None` loops over `self.sims` and calls `sim.plot()` on each (`run.py:633–650`). Verified: 20 binomial runs, one line in every panel, no band. `msim.plot(lines=True)` (the design's spelling, 09 §One run, many runs) raises `KeyNotFoundError` from `plot_args`. The design's default (`msim.plot()` is median and interval) is only reachable through `MultiResult.plot()` on one result (`run.py:1042`). Proposal: `MultiSim.plot()` draws from `msim.results` when it is a `MultiResults` (median and 95% band per panel, `lines=True` for every run, data points from `base_sim.data`), and falls back to the per-sim loop only for v3 sims. This also makes `reduce()`/`mean()`/`median()` unnecessary for declared sims (see 3).

3. **One results model, not three.** Today: (a) `ss.Result` (`results.py:12`), an ndarray subclass with v3 `columns`/`low`/`high`, onto which v4 bolts `strata`, `denom`, `strats`, `dims` as undeclared attributes (`getattr(self, 'strata', None)` in nine places, `results.py:197–241`, `run.py:1086`); (b) `ss.MultiResult` (`run.py:931`), a plain object, not a `Result`, whose `quantiles()` and `select(run=3)` return bare ndarrays (`:956–990`), whose `by()` returns a dict while `Result.by()` returns a 2D `Result` (`run.py:996` vs `results.py:171`), and which has no `resample`, `to_df`, or `timevec` conversion; (c) `reduce()` writing medians into `low`/`high` of a copied v3 `Results` and merging flattened keys (`sir_n_s`) beside the nested `sir` (`run.py:346`, verified). The design says a MultiSim result "is the same result with a run dimension". Proposal: one `Result` whose values are an array with named axes `(run?, time, group?)` plus an optional `denom` of the same shape; `select()`, `by()`, `quantiles()`, `resample()` all return a `Result`; `MultiResult` goes. Known issue "arithmetic on stratified results keeps the values by group only for sums" follows from the bolt-on and would go with it. This is a structural change to `results.py`/`run.py` only; user code that treats a `Result` as an array keeps working for the no-run, no-group case.

4. **`resample()` is the v3 pandas path and disagrees with the time-point convention; `compare()` is right.** `Result.resample('week')` (`results.py:324–388`) converts the timevec to dates (failing with `TypeError` on a sim with `unit='day', stop=10`, verified), bins on pandas' Sunday-anchored weeks, and takes the *mean* of a stock (the design says the value at the end of the interval, 09 §`ss.Result`); verified: weekly `recovery` gives 13.5 for a first "week" whose daily sum over the sim's first seven steps is 29.8, and weekly `n_R` gives 6.3 where `n_R[7]` is 29.8. `compare()` (`calibration.py:1326–1337`) does it right: a flow is summed over `(t_prev, t]`, a stock is read at `t`. Proposal: one resampling function, used by `resample()`, `annualize()`, `compare()`, and `check_dt()`: bins anchored at the sim's start, flows summed over the step-ending-at convention, stocks read at the bin end, ratios recomputed from their parts. Two implementations of "coarser time step" is exactly the duplication the design's "one time vector, converted on request" was meant to avoid.

5. **The model spec is not yet "the model is data" for the design's own examples.** Rates are strings (`transitions.py:1795`, departure noted), which is fine as far as the `Parser` whitelist goes (`spec.py:62–102`, 40 lines, no code run). But anything outside the whitelist leaks out as Python repr: (a) a value by stratum in a rate is written `beta * by(age=[1.0, 0.5]) * I / (S + I + R).n`, which `from_spec()` refuses ("cannot read by(age=...)", verified) and `to_code()` emits bare `by(` (no `ss.`), so the generated file raises `NameError` (verified); (b) an outcome's likelihood is `str(dist)`: `'ss.nbinom(n=par(10, bounds=[1, 100]), p=0.5)'` (verified; `p=0.5` is nbinom's default leaking in), and a parameter's prior is `str(p.prior)` (`transitions.py:1776`), neither loadable (`spec.py:122, 164`); (c) `from_spec` cannot read networks (except named `ss.contacts`), modifiers, interventions, functions, or mobility (`spec.py:244–251, 193`), so `ss.load(sim.to_spec())` holds for a disease, not for "the whole sim: modules, networks, interventions, data, settings" (14 §What it is for). My opinion on strings vs. a JSON tree: keep strings (readable, one parser shared with interop's `Rates.parse`, `interop/core.py:161`), but close the leak by rule: any non-scalar factor in a rate (`ss.by`, `ss.timeseries`, `ss.seasonal`, a distribution) is hoisted into a named parameter whose `value` is the existing typed JSON (`quantity_json`, `transitions.py:1974`), so the rate string only ever contains names, numbers, operators, `.n`/`.frac`, the eight functions, and typed quantities; and likelihoods and priors go through `quantity_json` as `{"dist": ...}` dicts, which `quantity()` already reads (`spec.py:31–33`). Then `from_spec` and `to_code` share one grammar and the claim holds for every spec the library writes.

6. **Cut Starsim 3's `Calibration`/`CalibComponent`/five likelihood classes from v4; they are the "separate calibration vocabulary" the design rejects.** `calibration.py:26–1173` (1,148 of 2,587 lines) is v3's Optuna wrapper with `calib_pars`, `build_fn`, `extract_fn`, `conform=`, and `BetaBinomial`/`Binomial`/`DirichletMultinomial`/`GammaPoisson`/`Normal`, each with its own `plot_facet` and bootstrap. v4's `fit()` has its own likelihoods in `logpdf()` (`calibration.py:1418–1440`: `ss.poisson`, `ss.nbinom`, `ss.normal`, `ss.lognorm_ex`), so yes, these are two systems, and the two share nothing (not the data alignment, not the GOF, not the plots). Four of the five tests in `tests/test_calibration.py` are v3; two user-guide pages still teach it. What is lost by cutting: binomial-family data with a sample size (`x` of `n`, the prevalence-survey case), and Dirichlet-multinomial. Proposal: keep `ss.Calibration` in a `starsim.legacy` or drop it with a migration note, and add `ss.binomial(n=...)`/`ss.betabinom` to `logpdf()` so a data file with `prevalence` and `prevalence_n` columns works; that is ~30 lines against 1,148.

7. **`sim.calibrate()`'s five-way choice is the right default; the cost is in `fit()`'s shape, not its policy.** `default_method()` (`calibration.py:2072–2093`) is 20 lines and prints its reason (`:2198`): good. But `fit()` is a 305-line function (`:2095–2399`) with ten closures, three coordinate systems (`x`, `encode`/`decode` for log scale, `to_x`/`to_z` logit for samplers), method-specific kwargs that arrive through `**kwargs` and are popped in five places (`trials`, `draws`, `warmup`, `chains`, `particles`, `scan`, `stepsize`, `parallel`, `maxiter`), and the Optuna, SciPy, ASD, NUTS-in-JAX, NUTS-with-callback, and pMCMC branches inline. Map of the file: v3 `Calibration` 26–465; v3 alignment helpers 467–527; v3 components 529–1173; v4 `data` 1174–1290; alignment and GOF 1291–1400; likelihoods and priors 1402–1476; `ParticleFilter` 1478–1630; `pmmh` 1632–1707; `nuts`/`nuts_jax` 1709–1852; diagnostics 1853–1922; `Fit` 1923–2000; identifiability 2001–2070; `default_method`/`fit` 2072–2399; `compare_models` 2401–2587. What could be a library: R-hat/ESS (`:1853–1922`, ArviZ); the adaptive random-walk Metropolis in `pmmh()` (`:1632–1707`, BlackJAX has `rmh`/SMC, and `particles` has PMMH); ABC-SMC, which the design wants for stochastic sims without a likelihood and which pyABC provides. What should stay: the bootstrap `ParticleFilter` (it steps the kernels, `:1559–1630`), `compare()`/`lineup()`, `Density`. Proposal: split `fit()` into an objective-builder (parameters, bounds, scales, data, measure) and one function per method family (`optimize`, `sample_nuts`, `sample_pmcmc`) that take an explicit options dataclass instead of `**kwargs`; the user surface stays `calibrate(method=, **kwargs)`.

8. **Six ways to run many sims; make it two.** `ss.MultiSim(sim, n_runs=4).run()` (default `n_runs=4`, `run.py:46`), `ss.parallel(sim, n_runs=)`, `sim.run(n_runs=)` (`sim.py:1815`), `ss.multi_run(sim, n_runs=)`, `ss.parallel(sim, pars=dict(beta=[...]))`, and `multi_run(iterpars=)` (`run.py:845, 890`). Results come back two ways: `MultiResults` only when a sim is declared (`run.py:1226`), otherwise `None` until `reduce()`. A `pars=` sweep labels every run `''` and is navigable only through `msim.run_pars` (verified; `select(scenario=)` has nothing to select, and there is no `select(beta=0.3)`). Proposal: `ss.parallel(*sims, n_runs=, pars=)` and `sim.run(n_runs=)` are the two spellings; `MultiSim` stays as the container but is not constructed by users; `iterpars` is subsumed by `pars`; every MultiSim builds `MultiResults` (`from_sims()` already works on any sim with 1D results); a `pars=` sweep gives each run a `pars` coordinate so `msim.results.sir.n_I.select(beta=0.3)` works like `select(scenario=)`. `reduce()`, `mean()`, `median()`, `combine()`, `merge()`, `split()`, `compare()`, `plot_compare()`, `summarize()` (`run.py:261–520, 703–777`, about 500 lines) are then v3 compatibility; keep what the v3 tests need, behind the new results.

9. **Interop: keep the core and the standard format in `starsim/`; ship the framework importers as `starsim_interop`.** The package is 5,700 lines (with `dump_epimodel.R` and four dump scripts) and ten test files, of which seven skip unless `/home/cliffk/idm/lingua_franca_design` and its `_envs/` exist (`tests/test_interop_memilio.py:12–13`, `test_interop_camdl.py:15–16`, `test_interop_flepimop.py:16`, `test_interop_epydemix.py:12`, `test_interop_odin_sbml.py:12`, `test_interop_siminf.py:12`): the held-out validation runs on one machine. Rot risk, highest first: `memilio.py` copies the C++ equations of four models by hand (`:5–12`; `osecirvvs` and five others are refused, `:51–55`) and reads a JSON written by a script that monkeypatches MEmilio's `simulate()`; `epimodel.py` runs R with EpiModel's `netest`/`netsim`/`dcm`/`icm` replaced (`:4–9, 37–48`); `summer2`, `epydemix`, and `camdl` are sniffed by private attribute names of live objects (`interop/__init__.py:39–44`); `odin.py` and `siminf.py` parse R source with regexes. Lowest: `sbml.py` (a standard), `emulsion.py`, `flepimop.py`, `atomica.py` (declarative files). `Source` + `build()` (`core.py`, 464 lines) is a good shared core and not thin: `Rates.classify()` (`:258–307`) is exactly rules 1–5 of 16 §Classifying rates, every importer uses it (12–33 `Source` calls each), it prints how each rate was read and marks guesses, and it reuses the spec `Parser`, so interop and the model spec share one expression grammar. Proposal for `starsim/`: `Source`, `build`, `sniff`, `ss.load`/`ss.save` dispatch through an entry point, SBML in and out, Mermaid out. Everything framework-specific (ten importers, dump scripts, odin export, the import skills) moves to `starsim_interop`, versioned against those frameworks and tested where their environments are. What is lost: `ss.load('model.yaml', format='emulsion')` needs one more `pip install`.

10. **Three names for the model file, and `hash()` initializes the sim.** `sim.to_spec()` (`sim.py:1290`) writes the spec; `disease.to_json()` (`diseases.py:240`) also writes the spec; `sim.to_json()` (`sim.py:2275`) writes v3's pars+summary+results dump; `ss.load('x.json')` reads a spec (`utils.py:678–681`). The design uses `to_json()` for the spec (14 §What it is for). Pick one: either `to_spec()` on both sim and disease with `sim.to_json()` renamed to what it is (`to_results_json()` or just `to_df().to_json()`), or `to_json()` everywhere. Separately, `sim.hash()` and `sim.to_spec()` call `self.init()` (`sim.py:1281–1283, 1298`), so asking for a hash changes the sim (verified: `initialized` False → True), and `hash()` on an already-run sim hashes post-run state. Hashing should be on the inputs.

## Other findings

- **The design's own likelihood snippet errors.** `ss.outcome(..., likelihood=ss.nbinom(n=ss.par(10, bounds=[0.1, 100])))` (09, 13, and calibration.md all show it) raises `Could not find a name for the parameter 10 used in "cases"; give it one with ss.par(..., name=...)` (`transitions.py:1443`, verified). Parameters elsewhere are "named from their slots"; the slot here is `n`, so name it `cases_n` (or `n`) as `fit()` already does for externals (`calibration.py:2161`).
- **Data points are plotted against the per-step flow.** `sim.plot()` scatters the data at its own times over the result's per-step line (`sim.py:2424–2440`); `fit.plot()` does the same (`calibration.py:1983–1999`). For weekly data on a daily flow (not an `every=` outcome) the points sit seven times above the line, although `compare()` sums correctly. Either draw the model as `compare()` sees it when the data's spacing exceeds `dt`, or draw the data as a per-step rate.
- **`ss.Sim(results=[...])` (09 §Requesting fewer results) is not implemented and not in the departures list.** It raises `KeyNotFoundError: Key(s) ['results'] not found` from `SimPars` (verified). Either implement pruning or list it as deferred. Likewise `sim.sensitivity()` (13 §Sensitivity): no definition anywhere in `starsim/`, not in departures. And `fit.sim` / `fit.pars` exist but `method=[...]` staged fitting and `pars=[beta * contacts]` are only noted as not yet.
- **`new_infections` is an alias series with its own storage.** For a one-transmission SIR, `res.infection` and `res.new_infections` are the same numbers (`solvers.py:1434`) under two names, with different `scale` and no `summarize_by`; `cum_infection` and `cum_infections` likewise. If the naming question (09 §open) resolves to keeping both, make one a view of the other with the same flags.
- **`ss.diff` is good but only for the parts `to_spec` carries as data.** Networks, modifiers, and `stratify` are compared as whole-dict equality with a count (`spec.py:771–773`), so "networks changed" is as far as it goes; fix 5 first and this gets its detail for free.
- **`to_code()` and `from_spec()` are two serializers of the same table.** `quantity()` (`spec.py:20–54`) and `code_value()` (`:279–316`) are the same dispatch twice, as are `strat_kwargs()`/`movable()` and `disease()`/`disease_code()`. Is `to_code` worth maintaining? Yes, while `from_spec` cannot read networks/modifiers/interventions: it is the artifact a user edits after an import (`sim.to_code()` carries the import's choices and the untranslated list as comments, `sim.py:1332–1350`), and the import skills hand over to it. But generate both from one table of `(json shape → object, json shape → code)` to halve the surface, and make `to_code` output importable (finding 5a).
- **The `MultiSim` from `restart_runs()` lies about its size.** `len(msim)` is 1 after `sim.run(n_runs=20)` (verified), `msim.sims[0]` is the last run, and `msim.summarize()` summarizes that one sim. If `MultiResults` becomes the only results path (finding 3), `MultiSim.__len__` and `summarize()` should read the run count from it, and `extinction()` should be part of `summarize()` as the design says (implementation.md notes this).
- **E206's message names the same module twice.** Reusing `S, I, R` from `ss.states()` in a second `ss.Disease` gives `state "S" is used by transitions in two modules, "sir" and "sir"` (`transitions.py:1275`, verified). The real cause is "a state object belongs to one disease; call `ss.states()` again"; say that.
- **`Samples`/`Dataset` (`samples.py`, 432 lines) is untouched v3 code with no v4 caller.** It stores per-seed outputs as a zip of pickles and a summary frame. A `MultiResults` with a run axis plus `to_df()` covers the summary use; the "load one seed's full outputs" use is real for large sweeps but is `sc.save` per run plus a frame. Candidate to drop or move to the library.
- **`likelihood=` is accepted in two places with two key spaces.** On the outcome, and at `calibrate(likelihood=dict(...))` keyed by column, by result name, or by `res.name` (`calibration.py:1409`). That is per the design (the open question of where a ratio's likelihood goes); one key space (result name, with `name[dim=level]` for strata) would do.
- **Departure I would revisit: "no ABC-SMC, Optuna instead" with `n_runs` defaulting to 1** (`calibration.py:2178`). A stochastic compartmental model without a likelihood now gets a TPE search on an objective evaluated from one run per trial, and the design's promised interval is gone. If pyABC is not wanted, at least default `n_runs` to something like 4 under CRN for `solver != 'ode'` and say so in the printout, as 13's printout example does ("4 runs each").
- **`import starsim` exports `Calibration, CalibComponent` and the five v3 likelihoods at top level** (`__init__.py:168`), beside `ss.fit`, `ss.Fit`, `ss.data`. If 6 is accepted this goes; if not, they should be the ones that move under a namespace, since the v4 names are the short ones a new user reaches for.

## Things that are good

- The time-point convention is implemented once, is consistent between `n_<state>`, flows, `cum_`, and `compare()`, and is tested (`tests/test_results.py:167–187`); `n_R[ti] - n_R[ti-1] == recovery[ti]` verified exactly on an ODE run.
- `ss.data` by name: `E705` with the closest names, `aliases`, `ignore_extra`, long-form strata as `cases[age=0-14]` (`calibration.py:1174–1289`) is the simplest data interface in the review's corpus and should not be touched except to fix finding 1.
- `compare()`/`lineup()`: the flow-summed-over-interval, stock-read-at-time rule in 25 lines, and `lineup()` as a matrix so the same rule runs inside JAX. Keep.
- `calibrate()` printing the method and the reason, `W1301 AtBound`, `W1302` identifiability from the model and from the posterior, `W1304 NotConverged` with R-hat and ESS: this is the "checked claim" the best practices ask for.
- NUTS through BlackJAX with the log-density as one JAX function (`nuts_jax`) and a callback fallback (`nuts`): wraps, does not own, as the design says; the three-draw check that the JAX density equals the sim's (`calibration.py:2335–2341`) is a cheap and good guard.
- `interop/core.py`: `Source`, `Rates.classify`, the printed "how each rate was read", guesses marked in `describe()`, `W1601` with the untranslated list kept on `sim.imported`. This is the part of interop with lasting value whatever happens to the importers.
- `ss.diff` reporting in model terms with transitions matched by endpoints and parameters written in as values (`spec.py:728–753`), so an import and its hand translation compare as the same.
- `restart_runs()`: `sim.run(n_runs=)` as one kernel call is the reason many-run workflows are fast; keep it and build the results fix (2, 3) on top of it.
- `msim.extinction()` and `ss.compare_models` with `holdout`/`folds` are small (40 and 190 lines) and do what the spec says.

## Questions for Cliff

- Interop: separate package `starsim_interop` (my recommendation), or keep in `starsim/` but mark the importers as "validated against framework version X" and accept that their tests run only where `lingua_franca_design/_envs` exists?
- Starsim 3 `Calibration`/`CalibComponent`: drop in v4 with a migration note, or keep under `starsim.legacy`? Who still uses `BetaBinomial`/`DirichletMultinomial` (stisim, hpvsim) and would a `ss.binomial` likelihood in `logpdf()` cover them?
- The flow-naming open question (09): data files from Starsim 3 say `new_infections`; v4 says `infection`. If both stay, is `new_<transition>` to be generated for every transition, or only `new_infections` for transmission? Finding 1 needs an answer either way.
- Is `to_code()` the primary artifact of an import (then make its output importable and keep `from_spec` for hashing and tests), or is `from_spec()` meant to become complete (then `to_code` can be generated from the same table and demoted)?
- Rate strings: are you willing to adopt the hoisting rule (every non-scalar factor in a rate becomes a named parameter) so the string grammar is closed, or do you prefer the JSON tree you noted you dislike?
- `Samples`: keep, move to the library, or drop?
