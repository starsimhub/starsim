# Design specification: review

I read all twenty files in `v4_design/design/` (5,457 lines), `best-practices/principles.md`, `admin/implementation.md`, and `admin/deferred.md`, and spot-checked about forty spec statements against `starsim/` with the v4 Python (constructor signatures, error codes, `describe()`, the results convention, the model spec, the public namespace). Verdict: the spec is unusually honest and most of it is real; the core (one `ss.Transition`, the bare-state rule, `describe()` with `[guessed]`, `.select()`/`.by()`, data by column name, `calibrate()` from bounds) is right and should not be touched. The costs are elsewhere: the document is about twice as long as its reader needs because the same rules are restated in up to eight files; the vocabulary count in 17 measures the language rather than what `ss.` actually shows a user (94 counted, 253 visible); several "two ways to say one thing" survived the trim; and roughly a dozen spec statements are not true of the code and are not in the departures list, including the spec's own headline error example (`E102`).

## Top findings

1. **Every flow result exists under two names.** `09 §Automatic results` keeps both the transition's name (`sim.results.sir.infection`, `cum_infection`) and Starsim's (`new_infections`, `cum_infections`) "until the vignettes have been written both ways" (19 B1). Verified: a two-transition SIR exposes 11 result keys, 4 of them duplicates. The vignettes have now been written (implementation.md, 25 of them), so this is settled by evidence and should close. The transition's name is the one that matches the model text, `ss.modify` targets, `ss.outcome('infection')`, and data columns; keep it and drop `new_<x>`/`cum_<x>s` for declared diseases (library classes such as `ss.SIR` keep theirs, as 09 already says). Before: `res.infection`, `res.new_infections`, `res.cum_infection`, `res.cum_infections`. After: `res.infection`, `res.cum_infection`. Breaks: Starsim 3 scripts reading `new_infections` from a declared disease; one alias line in the migration guide covers it.

2. **The vocabulary count does not count what the user sees.** 17 counts 94 `ss.` names and calls the language "small and counted" (README claim 5). `dir(ss)` has 253 public non-module names. The extra 160 are mostly Starsim 3 surface that v4 replaces: `RoutineDelivery`, `CampaignDelivery`, `BaseTest`, `BaseScreening`, `routine_screening`, `campaign_screening`, `BaseTriage`, `routine_triage`, `campaign_triage`, `BaseTreatment`, `treat_num`, `BaseVaccination`, `routine_vx`, `campaign_vx`, `simple_vx`, `Vx`/`Dx`/`Tx`, `seasonality` (next to `ss.seasonal`), `rate`/`time_prob`/`rate_prob`, `Route`, `Person`, `Engine`/`Compartmental`/`Agents`/`Mixing`/`Crossing`/`CountState`, and the calibration internals (`CalibComponent`, `BetaBinomial`, `GammaPoisson`, `linear_accum`, `step_containing`). Principle 9 says the reader's vocabulary is the constraint; the reader autocompletes `ss.` and gets all 253. Propose: (a) 17 counts the namespace, not the language; (b) the Starsim 3 delivery classes move to `ss.library` or a `ss.legacy` namespace (their replacements, `ss.vaccinate`/`ss.screen`/`ss.treat`, are listed as done); (c) solver internals go under `ss.solvers`. Breaks: Starsim 3 scripts using `ss.routine_vx` etc.; this is exactly the Starsim 3 compatibility v4 can drop.

3. **`E102 WrongDimension` is never raised.** It is the worked example of the message shape (15 §Message shape), the example in 02 §Arithmetic, and the one dimensional check principles.md lists under "stop, because a guess would be wrong quietly". Verified: `ss.progression('I -> R', rate=ss.peryear(0.1)*ss.days(3))` builds and runs with the product silently read as a per-day rate of 0.00082. The code lists `E102` in the catalog dict (`starsim/transitions.py:32`) and nowhere else. Either implement it (the typed product is a plain number landing in a `rate=` slot, which is exactly the check 02 describes) or take it out of 02 and 15. Same status, same fix: `E604 UnvaluedParameter` (`ss.par()` with no value and no bounds builds silently; verified), `W1002`, `W1303`, `E1401` (catalogued, no code), and `E505 UnknownEffect`/`E506 UnknownDisease` (in the code, not in the catalog, although 15 says every cited code is listed and every listed code has a test).

4. **Three-valued `approx=` reads backwards.** 01 §solver: `approx=None` approximates and prints a note, `approx=True` approximates and hides the note, `approx=False` errors. A user reading `approx=True` will think it enables approximation, which the default already does; the only thing it does is silence one line, which `verbose=0` also does. Propose a two-valued keyword with one meaning: `approx=True` (default, approximate and say so) and `approx=False` (error). Drop the silencing value; `verbose=0` hides notes. Before: `ss.Sim(hiv, solver='ode', approx=True)` "I know, don't tell me". After: `ss.Sim(hiv, solver='ode', verbose=0)`. Removes a row from the table in 12, two bullets in 18 §4, and one branch in `sim.init()`.

5. **"When" is spelled seven ways across four objects.** `ss.change(at=)`, deliveries `years=`/`dates=`/`interval=`/`start=`/`stop=`/`when=`/`on=`, `ss.modify(start=, stop=, when=)`. Two of these pairs are one concept each: `years=` and `dates=` differ only in the type of the value, which the library already reads from the value everywhere else (02 §Time in a sim: "a string is a calendar date; a bare number is a year"), and `when=` is `where=` returning one boolean for everyone (07 defines `where=` as a condition evaluated against the sim, and a function of the sim returning a scalar already fits). Propose: deliveries take `at=` (as `ss.change` does) in place of `years=`/`dates=`; `when=` is dropped from `ss.modify` and deliveries, and a `where=` that returns a scalar applies to everyone. Before: `ss.vaccinate(bcg, coverage=0.7, years=[2021, 2025])` and `ss.modify(school.pars.n_contacts, multiply=0.2, when=many_cases)`. After: `ss.vaccinate(bcg, coverage=0.7, at=[2021, 2025])` and `ss.modify(school.pars.n_contacts, multiply=0.2, where=many_cases)`. Cuts three keywords from the delivery table in 17 and one from `ss.modify`, and closes 19 B7's "should `when=` exist".

6. **Two vocabularies for "only these people" on transitions.** `ss.transfer(..., states=['on_treatment'])` (03, 05) and `where=` on a progression (03 §I.n) say the same thing, and `where=` is the general one (`states=[X]` is `where=X`). The implementation rejects `where=` and `p=` on `ss.transfer` (verified: `ValueError: ss.transfer() takes one dimension ... not ['risk', 'p']`), although 03 and 05 both say transfers take `p=`. Propose: `ss.transfer` takes `where=` like every other transition and `states=` goes; the TB example becomes `ss.transfer(resistance='DS -> MDR', rate=ss.peryear(0.02), where=on_treatment)`. Also, 17's keyword table for `ss.Transition` lists `rate dur p stages name label` while the implementation (and 01's equivalence rule) has `beta source where move` too; `beta=`/`source=` on the explicit form are a second way to write `rate=beta * I` and should stay on `ss.transmission` only.

7. **`stratify()` should be idempotent, not an error, on a repeated call.** 05 §stratify: in place by default, and `E305` on stratifying by a dimension the model already has, which "is what a notebook cell that is run twice will hit, and the message says so". 05 §Stratifying the sim or the disease already carves out the exception "same dimension, same levels: adds the adjustments and does not split again". Extend that rule to the model itself: a call that repeats an existing dimension with the same levels is a no-op (or adds `adjust=`), and `E305` is reserved for different levels. Notebook re-runs then just work; nothing else changes; risk 11 in 19 D goes away. One rule instead of a rule plus an exception plus an error with an apology in it.

8. **The `init` rule has a trap in it.** 03 §Initial conditions: "A Python `int` of exactly 1 is one individual and a `float` of exactly 1.0 is everyone." Verified: `init=dict(I=1)` gives `n_I[0] = 1`, `init=dict(I=1.0)` gives `n_I[0] = 10000`. Nobody writes `I=1.0` meaning "everyone in I"; everyone-in-one-state is already what the remainder rule gives for the first state. Propose: below 1 a fraction, 1 and above a count, no type distinction. Drops a sentence from 03, a row from 19 B1, and a silent 10,000-fold difference between `1` and `1.0`.

9. **Rule 4 of the unit ladder guesses what a bare number meant, and the guess is wrong often enough to be an error.** 02 §The sim's unit: with no `unit=`, no typed `dt`, no dates, the unit of every bare number is taken from the typed values, "the smallest, with a note" when they disagree. 19 B1 already says an error may be better; implementation.md's known issues show it biting ("with `stop=ss.weeks(12)` and no `unit=`, the sim runs in weeks even if every rate is per day"). Propose: rule 4 applies only when the typed values agree; disagreement with bare numbers present raises an error asking for `unit=` (reuse `W103`'s text as `E103`). Rules 1 to 3 and the timestep rule stay as they are; they are right.

10. **The spec restates its three biggest rules in up to eight places each.** The approximation policy is in 00 (twice), 01 §solver, 03 §Dwell time, 04 §A distribution as a value, 06 §Routes, 12 (three sections), 15, 18 §4, and 19 A. "States that are not people" is in 03, 05, 06, 10, 12, 14, 16, and 19 B2. "A bare state means exposure" is in 00, 03 (twice), 06, 14, and 19. Each restatement is slightly different (03 says `I.frac`, 06/14/17 say `I.prev`; the code has only `frac`), and the reading list for writing a model (00 §Reading order) is 1,828 lines. Propose one owner per rule and links elsewhere: 12 owns approximation, 03 owns states and the bare-state rule, 05 owns stratification of counts. That alone removes about 600 lines.

## Other findings

### Vocabulary: cut, merge, or infer

- **`ss.func`** (17, 03 §Custom per-step behavior) does not exist in the code (verified) and the plain function works without it. Remove from 17.
- **`ss.change` is `ss.modify(target, multiply=ss.timeseries({...}, mode='constant'))`**, as 08 §ss.change itself says. It is one of 8 names in the "interactions" group and adds `at`/`by`/`to`, where `to=` is `set=`. Keep it only if the vignettes use it more than `ss.modify` with a time series; otherwise cut it and show the time-series spelling in 08.
- **`ss.erlang(k=, mean=)` and `stages=k`** say the same thing (03 §Dwell time, 04). The spec calls `ss.erlang` "the one addition" to the distributions and then adds a keyword that duplicates it. Keep `stages=` (it also applies to a non-Erlang distribution and to agents) and drop `ss.erlang`; `ss.gamma(a=3, scale=...)` remains for people who want the distribution object.
- **Three ways to add births**: `ss.birth('-> S', rate=)` on the disease, `ss.Births()` in `demographics=`, and `birth_rate=` on `ss.Sim` (still a `SimPars` key; verified). Same for deaths. The spec documents the first two; 17 does not list `birth_rate`/`death_rate`. Drop the sim keywords.
- **`ss.Sim` carries 33 keywords, the spec lists 25.** The extra are Starsim 3's: `dur` (duplicates `stop`), `pop_scale`, `rescale`, `rescale_threshold`, `rescale_factor`, `people_results`, `birth_rate`, `death_rate`, `use_aging`, `substeps`, `custom`, `modules`. Of the spec's 25, the ones that earn their place are the model, `networks`, `people`, `stratify`, `total_pop`, `n_agents`, `start`, `stop`, `dt`, `unit`, `solver`, `approx`, `rand_seed`, `verbose`, `interventions`, `connectors`, `analyzers`, `data`, `pars`, `label`. `results=` (restrict which results are kept) is specified in 09 and not implemented (verified: `KeyNotFoundError`); `integrator=` is specified as `'scipy'`/`'jax'` and the code wants a SciPy method name (`integrator='scipy'` raises; verified). `track_writes=` is on one keyword and one method for a diagnostic nobody has asked for (19 B1 says drop `what_modifies` if the vignettes never use it; implementation.md's 25 vignettes do not mention it).
- **`ss.Requires`** exists for a feature that is deferred (the data-entry form) and no library module uses it (verified by grep). For declared models the `requires()` table is generated from the parameters without it. Cut the class; keep `sim.requires()`.
- **`ss.freq` and its four constructors** exist so that `per + freq` is an error and `freq × dur` is a count. That is 5 of the 22 time names for one slot (`acts=`, `n_contacts=`). Since every slot types a bare number anyway, `acts=2` with the unit from the sim does the same job. Worth asking whether the type earns its five names.
- **`dependence='density'` and `n_ref`** (06 §Frequency and density dependence; 16 import rule 3) are not implemented (`self.dependence = 'frequency'` is a fixed attribute; verified) and implementation.md's departure says "there is no density-dependent mixing". Remove the section and `n_ref` from 17.
- **`ss.Mobility(kind='force')`** (06) exists for LASER's convention and the spec says it is "less mechanistic". Principle 9 case; keep only because the LASER vignette needed it to agree, and say so in 06.
- **The strain-kind name list** (`strain`, `variant`, `genotype`, `serotype`, `resistance` make a dimension strain-like; 05 §Kinds; code `transitions.py:2430`). A TB model with a plain `resistance` dimension silently gets a per-strain force of infection. 19 B6 asks whether a name list is right. It is not: `kind='strain'` is one keyword, and a guess that changes the model's structure from a variable name is the kind the spec elsewhere refuses to make ("the unit is never guessed from the size of the numbers"). Keep `age` and the geo-valued space inference; drop the strain names.

### Coherence

- **07 vs the code on reading a modified array.** 07 §Base and effective values: reading gives the effective value, `.base` reads the base. Code and departures: reading gives the base, `.effective` gives the modified value, no `.base`. 07 (120 lines including the worked example and the cache rules) is now wrong and should be rewritten to the departure; 19 B1's row on this closes.
- **07 vs 10 on where a modifier's condition is evaluated** (19 B1 flags it). The departure settles it ("a modifier acts where the engine uses the quantity"). Close the question and delete 10 §Where ss.modify is evaluated's four-step cache protocol, which is implementation and was departed from.
- **03 `ss.Transition` signature vs 01's equivalence rule** (see finding 6).
- **13 §Choosing the method vs the departure**: the table promises ABC-SMC for stochastic and cheap agent-based sims; there is none, Optuna is used, and particle MCMC for stochastic compartmental with likelihoods. Rewrite the table. The `[CK: ...]` note on Optuna intervals and the `[CK: don't particularly like this]` on nested-list rate expressions (14 §Rate expressions) are both resolved by departures (rates are strings now) and should be folded in.
- **14 says every field is present in every document**; the real spec has no `data` or `fit` keys (verified). 14 and 09 say `sir.to_json()` is the model spec of one disease; only `sim.to_spec()` exists and `to_json` is Starsim 3's (departure listed for the name, not for the loss of the per-disease form).
- **04 says inline values are addressable through their transition** (`sir.infection.beta`) for `ss.modify`. Verified: `sir.infection.beta` is `None`, and `ss.modify(sir.infection.beta, ...)` raises `E504`; `sir.recovery.dur` works. Either implement or say `sir.pars.beta` (which is what the user gets anyway, since inline values are collected into `pars`).
- **02 says a model with nothing typed has no calendar**; `ss.Sim(sir)` with no `stop` gets Starsim 3's `days(0)` to `days(50)` while `describe()` prints "unit none: time is in timesteps" and "steps 0 to 50.0" (verified). The departure "sims with no declared states keep Starsim 3's time defaults" does not cover this (the states are declared). Either `stop` is required for a declared model or the default is 50 steps, said so.
- **12 §Stochastic compartmental specifics** says thinning MUST be used and freezing is "not acceptable without a note"; the departure holds values for a quarter-step with a note. Rewrite the MUST.
- **01 §Not included: "positional values after an arrow are not accepted"** and 15 lists it as a `TypeError`. Verified: `ss.transmission('S -> I', 0.05)` is accepted. Harmless; drop the sentence rather than add the check. Same for "`None` is not accepted as a source" (03): `ss.Transition(None, 'S', ...)` works.
- **`sir.solvers()` and `sim.sensitivity()`** (01, 03, 12, 13, 17) do not exist (only `sim.solvers()`; verified). `crn_report` (MAY) likewise. Remove or mark not yet.
- **The north-star claim on run time is not met and the table that would say so does not exist.** README claim 6 and 18 §13: "no more run time than the original", with a published table. implementation.md reports LASER at 131 s against 3.0 s and SimInf at 3 s against 0.08 s in prose. 18 says such rows are "listed as such, with the reason"; there is no list. Either publish the table (it is a day's work from implementation.md) or restate the claim as lines only, with time reported.

### Over-specification

Everywhere the spec says how the library computes rather than what the user observes, the implementation has already departed: the modifier cache protocol (07 §Implementation, 10), the SciPy/JAX line (12 §How a model is built), nested-list rate expressions (14), thinning (12), `stream(dist) = PRNG(seed = H(...))` (11 §Streams), "the groups are still a grid" (05). These paragraphs constrain nothing the user can see and cost a reader. Cut them; what remains in each case is a one-line observable (the base is never overwritten; the same seed gives the same draws in any order; the hash is from the normalized spec).

### Open questions (19)

Settled by the implementation and should close: flow result names (finding 1); modifier read/write and `.effective` (departure); where a modifier's condition is evaluated (departure); counts in an agent-based run advanced deterministically (done, RK4, with a known issue noting the limit); `sim.people.age` as the bin midpoint (done, with a known issue); the Erlang stage formula; `what_modifies()` kept; what `calibrate()` returns (`ss.Fit`); the default goodness of fit and log-scale search; B2 entirely (tbsim resistance, malaria with species, SISe3 reservoir per herd all built; only vector interventions untried); B3's SciPy/JAX line (departure); B6's `ss.transfer` with delivery keywords (done); B7's lazy-condition extent and `where=` on transitions (done); B8 "is `ss.outcome` needed" (yes: the flepiMoP, camdl, and MEmilio vignettes chain them); B11's `ss.prob` and nested lists (strings; departure). That is 18 of about 45 rows.

Decided, in my view, wrongly: `approx=True` as silence (finding 4); `E305` on a repeated `stratify` (finding 7); `int` 1 versus `float` 1.0 (finding 8); unit from disagreeing typed values (finding 9); the strain name list (above). B12's `I.contact` spelling: close as no; `S >> I @ beta * I` reading like the equation is the point. B8 "bounds and prior as one argument": keep separate; they answer different questions and the implementation already fits both.

Still open and worth a decision rather than a row: where cross-module results live (B8); `ss.null`'s name (B12; `ss.outside` reads correctly in both positions and is no longer); whether `ss.change` stays (above).

### Structure of the spec

Twenty files is the wrong shape for its reader. A person writing a model needs 00, 03, 04, 06, 08, 09 (1,828 lines); with the duplicates removed and the "Rejected" sections moved out, the same content is about 700. A shape that fits: (1) *The model*: 00 + 01 + 03 + 04, one file, 600 lines; (2) *Structure*: 05 + 06; (3) *Interventions and results*: 07 + 08 + 09; (4) *Running*: 10 + 11 + 12; (5) *Fitting*: 13; (6) *Files and other frameworks*: 14 + 16; (7) *Discipline*: 17 + 15 + 19, with 18 as `tests/README.md`. Eleven files have a "Rejected" section (about 150 lines in all, 40 bullets); a writer of models never needs them, and they belong in 19 as one table. 02 is the one short file that is exactly right and should stay separate.

### The conventions, and whether they pull their weight

- **Timing/results convention (09 §Automatic results)**: yes, and it is implemented and verified (`n_R[1] - n_R[0] == recovery[1]`; a sim with `stop=30` has 31 points). It is one 200-word paragraph; a three-row table (stock at `ti`, flow during the step ending at `ti`, `stop=T` ends at `T`) says it in a tenth of the space.
- **Units rules (02)**: rules 1 to 3 and timesteps, yes; rule 4 is the one guess that should be an error (finding 9). The four types earn their place except, possibly, `ss.freq` (above). The arithmetic table and the conversion table are good and should stay; 02 is the best-proportioned file in the folder.
- **Error-code scheme (15)**: partly. Codes are greppable and the implementation really uses them (`ss.error('E505', ...)`), which is more than most frameworks manage. What does not pay: notes carrying `W` codes (15 admits the muddle: "Note (`W`, marked 'note' below)"), the sparse numbering with gaps from the 75-to-54 trim (`E202`, `E203`, `E207`, `E303`, `E304`, `E401`, `E501` to `E503`, `E601`, `E701`, `E801` to `E803`, `E1001`, `E1002`, `E1101` all absent), and the 1xx-to-16xx grouping by file number, which means a code renumbers if the files are merged. Propose: errors keep codes and names (users search them); notes keep names only; renumber densely before 1.0, or drop numbers and keep `ss.UnknownParameter`-style names, which are what people remember. The catalog's own rule, "a code with no test is removed", would remove five codes today (finding 3).
- **Conformance suite (18)**: suites 1 (form equivalence), 3 (solver agreement with stated tolerances), 9 (published `describe()` per corpus model), 13 (the north-star table), and the corpus table earn their place and are the spec's teeth. Suites 4, 6, 7, and 8 re-list behaviors already stated in 12, 10, 07, and 05 as bullet lists; they are the same text twice. Replace them with one sentence ("every MUST and every coded error in the spec has a test that triggers exactly it") and keep the four suites that say something the spec does not.

## Things that are good

- The bare-state rule (`S >> I @ beta * I` is exposure through whatever routes the sim has; `I.n` is a count) and the one transition class whose kind is derived. This is the design; everything else can be cut around it.
- `describe()` with `[guessed]` and the rule that produced each guess. Verified real, and it is what makes guessing safe.
- The results convention and `.select()`/`.by()` with one result per quantity; data attached by column name; `calibrate()` with nothing but `bounds=` and `data=`. The 30-lines-to-3 comparison in 13 is honest and accurate.
- `ss.null`, states that are not people inferred from connectivity, and `init` only where nonzero. Three small rules that remove whole classes from other frameworks.
- `solver='auto'` that never approximates mixing and prints its reason; `stratify` returning the model so it can go straight into `ss.Sim`.
- The ordered loop kept, with the schedule view in `describe()`.
- The "Removed since the first draft" tables in 15 and 17, and the departures list in implementation.md. The discipline of listing what went is the reason this review could be concrete.
