# Tests, documentation, and errors: review

I read the seven v4 test files (`tests/test_transitions.py`, `test_dimensions.py`, `test_deliveries.py`, `test_kernels.py`, `test_gradients.py`, `test_named.py`, `test_interop*.py`), the conformance and error chapters of the spec (`v4_design/design/18-conformance.md`, `15-errors.md`), the build-set README, `v4_design/admin/implementation.md`, the error and note machinery in `starsim/transitions.py:30-73` and its call sites, and the Quarto docs tree; I ran the v4 tests and a sample of v3 ones, and triggered a dozen errors by hand. The verdict: everything runs and the tests pass (67 v4 tests in about 95 s; v3 `test_sim`/`test_diseases`/`test_interventions` still pass), but the three things this area is supposed to deliver are each a fraction of what the spec promises. The conformance suite of 18-conformance is not implemented as a suite; its claims are scattered through 45 long feature tests with loose tolerances and no golden outputs. The user docs contain zero v4 content. And the coded-message system has drifted into three unconnected mechanisms, one of which (notes) silently discards the code it was given.

## Top findings

1. **Note codes are accepted and thrown away; the W catalogue is ceremony with no output.** `ss.note(msg, code=None, sim=None, verbose=None)` at `starsim/transitions.py:58-71` never reads `code`: it prints `  note: {msg}` and appends the bare string to `sim.notes`. Ten call sites pass `code='W101'`, `'W212'`, `'W404'`, `'W502'`, `'W503'`, `'W1205'`, `'W1302'` (e.g. `sim.py:391`, `solvers.py:1117`, `connectors.py:170`) and the user never sees a code; the other 13 `note()` calls pass none. Real output: `  note: the modifiers a, b both set the same quantity at the same time; the last one wins` (spec: `W502 OverlappingSet`, a *warning* through `ss.warn`). The tests consequently match substrings (`any('Erlang' in note for note in sim.notes)` at `test_transitions.py:277`, `'both set'` at `test_deliveries.py:104`, `'made it negative'` at `:819`), which is exactly the brittleness codes exist to prevent. Meanwhile the six genuine warnings hand-paste the code into the string (`ss.warn(f'W1601 ImportIncomplete: ...')` at `interop/core.py:463`, `calibration.py:1971,1976`, `networks.py:987`, `export.py:405`), bypassing the `codes` dict, and 15-errors.md says notes "use Python's `warnings` machinery ... so they can be filtered" when they use `print()`. Proposal: one function, one registry. Either `sim.notes` becomes a list of `(code, msg)` and the printed line is `W1205 StagesUnderAuto: ...`, with tests matching the code, or (my preference, see finding 7) drop the W numbers from the spec and keep names only. What breaks: nothing user-facing, since nobody can be depending on codes that are never shown.

2. **With `verbose=0` or `approx=True`, notes are lost from `sim.notes` and so from `describe()`, against the spec in three places.** `sim.py:388` wraps the unit, units-disagree, and state-not-people notes in `if pars.verbose:`, so with `verbose=0` they are never stored. Verified:

    ```text
    === verbose=0 run
    notes kept: []
    === describe() of the verbose=1 sim
    note         unit='week' (from dt)
    ```

    And `approx=True` drops the approximation note entirely (`approx=True notes: []`, while `verbose=0 notes: ['RandomNet approximated by homogeneous mixing with 10 contacts per step']`). The spec says the opposite: 12-backends.md:134-135 "Whatever is printed, the notes are stored with the results ... and remain available from `sim.describe()` and `sim.solvers()`", 12-backends.md:309 "`approx=True` or `verbose=0` hides it, and it is still stored", and conformance suite 4 "with `verbose=0` nothing is printed, and the note is still in `sim.describe()`". The `note()` docstring itself promises storage regardless of verbosity. Since every test file sets `kw = dict(verbose=0)`, the test suite runs in exactly the mode where these notes vanish, which is why it has not noticed. Fix: move the `if pars.verbose` inside `note()` (it already handles printing) and store unconditionally; make `approx=True` affect only printing. Also: `describe(verbose=True)` is specified at 01-objects.md:336, 02-types.md:39, and 10-execution.md:128, and `describe(self, output=False)` at `sim.py:1076` has no such argument.

3. **The conformance suite is not implemented as a suite; what exists is 45 feature tests with hand-chosen tolerances, no golden outputs, and no corpus.** 18-conformance.md promises 14 suites over 18 named corpus models, "a published expected `describe()` output" per model (suite 9), recorded difference tables for approximated models (suite 3), tolerances "stated per test with the reasoning", and a north-star table (suite 13). What is in `tests/`: `test_solvers()` at `test_transitions.py:198-252` loops four ad hoc models over five solvers and asserts the peak within `rtol=0.07` of the ODE (the spec asks for the mean of 1,000 runs within 2 Monte Carlo standard errors, per time point); `test_describe()` at `:425-436` checks eight substrings; no recorded table exists anywhere; the corpus is implicit (the SIR is defined six times: `test_transitions.py:15`, `test_deliveries.py:16`, `test_kernels.py:14`, `test_named.py:13`, `test_gradients.py:19`, `test_interop_export.py:18`), and the solver loop is hand-rolled three ways (`solvers = [...]` plus `run()` at `test_dimensions.py:13,26`, `run_each()`/`check_close()` at `test_deliveries.py:37,42`, inline `for solver in [...]` at `test_transitions.py:211`). The held-out set (the real validation per `examples/README.md`) lives in another repository and the interop tests skip without it (`test_interop_flepimop.py:17`). None of this is wrong, but the spec says "a claim with no test should be treated as a hope", and by its own rule most of 18-conformance is currently a hope. The right shape, using what is already in the repo: (a) `tests/corpus.py` with the 18 models as named constructors, imported by every v4 test; (b) `@pytest.mark.parametrize('solver', ...)` over the corpus instead of per-file loops; (c) golden `describe()` text per corpus model under `tests/test_data/describe/`, diffed, updated by the existing `update_baseline.py` pattern; (d) recorded tables in the existing `baseline.yaml`/`test_baselines.py` machinery, which already does exactly "a change in the table is reviewed like any other change"; (e) one parametrized error test over the code table (finding 5). What it would cost: a day of moving code; what it would break: nothing.

4. **The user docs have no v4 in them at all, and the v3 pages teach as the primary path what v4 makes the escape hatch.** `grep -rlE "ss\.transmission|ss\.progression|ss\.states\(|ss\.Disease\(|\.stratify\(|ss\.modify\(|ss\.vaccinate\(|solver=|ss\.outcome|ss\.par\("` over `docs/**/*.qmd,*.md` returns nothing. The only v4 prose a user can find is `CHANGELOG.md` (the 4.0.0 entry, one paragraph per feature) and the spec itself. The tutorials (`docs/tutorials/t4_diseases.qmd:126-139`) and user guide (`docs/user_guide/modules_diseases.qmd:46`) present subclassing `ss.Infection` and overriding `step_state()` as the way to write a disease; `t6_interventions.qmd` and `modules_products.qmd` teach `ss.Vx(df=...)`/`ss.Dx`, which `implementation.md` keeps as aliases of `ss.Vaccine`/`ss.Test`. These pages are not wrong for v4 (the v3 path still runs, and the v3 tests pass), but a new user who follows them will write forty lines of `step_state()` for what is now two lines, will never meet `solver=`, `stratify`, `describe()`, or `calibrate()` on a declared model, and will not learn that bare numbers in a declared model take the sim's unit while in a coded module they keep the default's (a known issue at `implementation.md:295`). Pages whose content is actually contradicted by v4 and would need rewriting rather than demoting: `advanced_time.qmd` (time in timesteps when nothing has a unit; the unit note), `basics_results.qmd` if it describes result timing (I did not find an explicit statement of the v3 convention to contradict, so unverified), and `workflows_calibration.qmd` (`calib_pars`/`CalibComponent` versus `ss.par(bounds=)` + `ss.data`). Proposal below in finding 6.

5. **Error messages are mostly good, but the spec's four-part message shape is not delivered anywhere, and the registry has already drifted.** Real output from twelve triggers:

    ```text
    E204 UnknownState: no state named "J" was declared in "sir". Declared states are S, I, R; did you mean S, I, R?
    E205 BadBranchSplit: the branch probabilities out of state "I" sum to 1.2, not 1 (severe: p=par(0.3), mild: p=par(0.9)).
    E504 UnmodifiableTarget: the target of the modifier "m", sir.pars.betta, was not found. Quantities that can be modified: sir.pars.beta, sir.pars.dur, sir.infection, sir.recovery, sir.rel_sus, sir.rel_trans; did you mean sir.pars.beta, sir.pars.dur, sir.recovery?
    E602 UnknownParameter: pars= has a value for "betta", which matches no parameter. Parameters are sir.beta, sir.dur; did you mean sir.beta, sir.dur?
    E605 : the place "Narnia" was not found in starsim_data: location 'Narnia' not found (did you mean: Gambia, Latvia, Namibia?).
    E209 UndrivenTransition: the transition "recovery" (I -> R) has no rate, no duration, and no p=. Give it one, e.g. I >> R @ 0.1
    E305 DuplicateStructuralDimension: "sir" is already stratified by "age". stratify() works in place, so this is what running the same line (or notebook cell) twice gives.
    E302 BadSplit: split= has 2 entries, but "age" has 3 levels (0-14, 15-64, 65+).
    ValueError: A transition takes rate= or dur=, not both
    TypeError: Cannot use the expression "I" where Python needs a single True or False; it has no value until the model runs
    AlreadyRunError: Simulation is already complete
    ```

    Against "every error names the rule, shows the offending expression, and states the fix": they name the thing and usually the alternatives (good; E209 and E305 are model answers), but none quotes the declaration with a caret (15-errors.md message shape item 3), and several have small defects that a parametrized test would catch: E204 and E602 list the options twice because `closest()` at `transitions.py:66` falls back to `list(options)` when `sc.suggest` finds nothing, giving "Declared states are S, I, R; did you mean S, I, R?"; E205 leaks the repr `p=par(0.3)`; E605 has no name because the `codes` dict at `transitions.py:30-41` lacks it; `E1003 RunAfterFinish` is in the dict but the code raises v3's `AlreadyRunError(RuntimeError)` at `sim.py:1379,1766,1833` so the code is dead; `E505 UnknownEffect` and `E506 UnknownDisease` (`products.py:381,466,471`, `interventions.py:727,730,1120`) are implemented and absent from the spec; `E1401 SchemaTooNew`, `W1002 CoarseFlow`, `W1303 StageStopped` are in the spec and absent from the code (W1203/W1204 are documented as dropped, fine). The tests check `pytest.raises(ss.CodedError, match='E204')` and nothing else about the message, for 28 of the 50 codes in the dict; 15-errors.md:386 says "a code with no test is removed from this list", which would remove 22. Proposal: trim the spec's message shape to what is delivered (one line naming the thing, the alternatives, the fix) and drop the caret clause; fix `closest()` to return nothing when nothing is close; one parametrized test that triggers every code and asserts code, name, and that the message contains the user's name for the thing.

6. **The spec's chapters 00 to 09 could be the user guide with light editing; chapters 10 to 19 should not be.** The spec's reading order (`design/README.md`: "Start here" 00; "The language" 01-09; "Running and fitting" 10-13; "Machinery" 14-16; "Discipline" 17-19) is already a documentation structure, and 00-overview ("the whole language in one example") is a tutorial opening. The chapters are written in the user's terms, with before/after snippets, and `describe()` output pasted from the real thing (01-objects.md:325-331 matches what the code prints today). What would have to go for them to be user docs: the MUST/SHOULD register, the "Rejected" and "Removed since the first draft" sections (e.g. 12-backends.md:300-312, 15-errors.md:378-382), the pointers to `best-practices`, and the departures now listed only in `implementation.md:258-286` (e.g. `has_<product>`, `.effective` instead of `.base`, no named geographies, the results timing convention), which should be folded into the chapters they amend so that the spec says what the code does. Proposed structure for `docs/`: tutorials = the nine build steps of `examples/README.md` (SIR in all spellings; SEIR with Erlang; branching; cholera; age with a contact matrix; vaccination; outcomes, data, and fitting; custom code; a network model), each one `.qmd` and each already written as a test; user guide = spec 00-09 and 12-13 edited as above; reference = 15 (generated from the code's registry, finding 7), 17 (vocabulary), 14 (model spec); examples = the vignettes; migration = a `v3_v4` page listing what the v3 pages teach that is now the long way. The v3 tutorials move to "writing a module in code", after the declared form. 18-conformance and 19-open-questions stay in `v4_design/`, since they are for the maintainer.

7. **The numbering-by-section scheme costs more than it returns; names are the useful part.** The number tells the user which spec chapter to open, which the docs will not be organized by (finding 6), and it is the thing that has drifted: three registries (the spec table, the `codes` dict, the hand-pasted warning strings) that disagree today. What users and tests actually need is a stable, searchable name (`UnknownState`, `CapabilityError`) and, for catching, a class: `except ss.CapabilityError` reads better than `except ss.CodedError as e: if e.code == 'E804'`, and `pytest.raises(ss.UnknownState)` better than `match='E204'`. Proposal: `class UnknownState(ss.ModelError)` etc., one class per current E code (34 classes, each three lines), with the catalogue page generated from the classes' docstrings; keep the number as an optional class attribute if Cliff wants greppable codes in the docs, but never print "E605 :". For notes, drop codes entirely and keep the one-line text, stored unconditionally (finding 2). What breaks: `ss.CodedError` and `match='E...'` in 28 test lines, a mechanical change.

8. **There is no single verbosity control, and v3's `verbose` semantics leak into v4.** Controls today: `ss.options.verbose` (default 0.1, documented at `settings.py:89` as "an update every 10 simulated timesteps"), `sim.pars.verbose` (`parameters.py:303`, accepts `'brief'` meaning -1), `verbose=` on `run()`, `approx=True` (which also silences, finding 2), `output=True` on `describe()`/`solvers()`/`equations()`, and the specified but missing `describe(verbose=True)`. Setting `ss.options(verbose=1)` on a declared model prints a cyan banner per step (`Running days(2) ( 2/6) (0.03 s)`) for a run that takes 30 ms, with the W502 note buried between banners. Proposal: `verbose` is an integer level, 0 = nothing, 1 (default) = the solver line and the notes, 2 = the step log; `approx=` decides only note-versus-error; `output=` stays as is. The fraction-of-steps meaning can live on at level 2 if anyone uses it.

9. **`implementation.md` is five documents in one file, and four of them have a better home that already exists.** It is 316 lines and 23 commits of (a) a checklist, (b) a performance log ("a Gillespie SIR in 100,000 people takes 0.16 s, from 4.2"), (c) departures from the spec, (d) known issues, (e) validation results against other frameworks ("agrees within 1.5 people of 10,000"). Its first line is already stale: it names three test files when there are seven. Proposal: (c) goes into the spec chapters (finding 6), so that the spec is true; (d) becomes GitHub issues or a "Limitations" doc page, since users hit them (`implementation.md:293-316` is a list of things a user will trip over, e.g. a typed quantity changed in place is not seen); (b) goes into `tests/benchmark*.yaml`, which already exists for v3 and is the only place a regression would be noticed; (e) is the north-star table of suite 13, one generated row per vignette, which is the headline result of the whole project and currently exists only as prose in a checklist; (a) is the CHANGELOG, which already carries it. What stays is a short status page.

10. **A misspelled destination state is created silently when states are inferred.** `ss.progression('R -> J', dur=10)` in a model with inferred states builds a four-state model and prints nothing at default verbosity (`describe()` shows `states S, I, R, J [inferred from the arrows]`, but only if you ask). The spec exempts this from `E204` by design, and `W207 UnreachableState` does not fire because `J` has an inflow. The cheapest guard is to print the inferred state list once at build time, as the unit line is: `note: states S, I, R, J inferred from the arrows`. One line, no new code, and it catches the typo the day it is made rather than when the results look odd.

## Other findings

- **Tolerances are ad hoc and sometimes loose enough to pass a wrong solver.** `rtol=0.07` on the peak in `test_transitions.py:226`, `rtol=0.2` at `test_dimensions.py:124`, `rtol=0.15` at `:140`, `check_close(..., rtol=0.1)` as the default in `test_deliveries.py:42`. The spec asks that tolerances be stated with reasoning; here they are the number that passed. The 20% ones would not have caught the "biased by 5% and a step early" bug recorded at `implementation.md:80`.
- **Tests are one giant function per feature, so a failure hides what follows.** `test_states()` at `test_dimensions.py:105-182` asserts about ten independent behaviors (species as counts, a stage dimension, a clinical split by age, an init by level, two `E306` cases, infectiousness by level); a failure at the second stops the other eight. Combined with `@sc.timer()` and `return sims` (the `PytestReturnNotNoneWarning` is suppressed in `pytest.ini`), the files are scripts with assertions rather than a suite. Parametrizing over the corpus and solvers fixes this and finding 3 together.
- **Errors raised as plain exceptions outnumber coded ones in the core module.** `transitions.py` has 30 `ss.error(` calls and 46 plain `raise ValueError/TypeError/...`; `interventions.py` 5 against 14. 15-errors.md:368-376 allows plain exceptions for "ordinary Python usage errors", but several of the 46 are model errors. Whatever the registry becomes (finding 7), the rule for which errors get a name should be "a user can make this mistake in a model", not "it was in the first draft's table".
- **The `codes` dict is missing names the code uses.** `E605` (produces "E605 :"), and all of `W1301`, `W1302`, `W1401`, `W1601` (harmless only because those paths bypass the dict). A one-line test `assert set(codes) == set(codes_used_in_source)` would hold the two together.
- **Interop tests depend on files outside the repository**, with `skipif` guards (`test_interop_flepimop.py:17`, `test_interop_camdl.py:114,130`), so a fresh clone runs a different suite from Cliff's machine. The held-out set is the validation the design rests on; at least the small originals (the JSON dumps) could be committed under `tests/test_data/`.
- **Suite 10 (reproducibility and the hash) is almost untested.** Only `hash().model`/`.pars` (`test_transitions.py:89-90`) and one `.scenario` inequality (`:806`) are asserted; `config` and `seed` never are, nor "changes in exactly the part that was changed".
- **Spec 15 contradicts itself on mechanism.** "Warnings and notes use Python's `warnings` machinery" (15-errors.md:243) versus the levels table where a note is "one printed line". Pick one; the code picked `print`.
- **The vocabulary is not cross-checked against the tests or the namespace.** Of the ~140 backticked `ss.*` names in 17-vocabulary.md, 37 appear in no test file; some are in the "removed" tables (so my count overstates), but `ss.stratify` (17-vocabulary.md:52, suite 8) exists and is untested anywhere. A test that walks the vocabulary table is cheap and keeps 17 honest.
- **`docs/_quarto.yml` points at `docs/api/index.qmd`, which does not exist in the tree** (generated by `make_api.py`); the `llms.txt` route is the only place a v4 user could get signatures today, and only after building.

## Things that are good

- The error messages that exist are written for a person: E209, E305, E302, and E504 say what, list what is allowed, and say the fix, in one line. Keep that register whatever happens to the numbering.
- `describe()` is the best piece of user-facing documentation in the project and it is generated, so it cannot go stale; the `[guessed: ...]` annotations are exactly what the spec promised. It should be the spine of the golden tests.
- The tests, for all their shape, do exercise real behavior with real numbers (final size against the analytic SIR at `test_transitions.py:245`; conservation of people; `coverage=0.6` delivering 60%), not just "it ran". Keep every assertion when restructuring.
- The build set in `examples/README.md` is a ready-made tutorial sequence and is already encoded in `test_transitions.py`; the docs can be lifted from it.
- `tests/baseline.yaml` and `test_baselines.py` already implement "recorded, reviewed tables"; the v4 suite should reuse them rather than invent a mechanism.
- CHANGELOG's 4.0.0 entry is a good one-paragraph-per-feature summary; it is the right level for the checklist part of `implementation.md`.
