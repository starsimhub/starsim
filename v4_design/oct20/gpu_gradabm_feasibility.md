# Feasibility: Starsim agent models on GPUs, and differentiable ABMs

2026-10-20. Answers two items in `v4_design/admin/todo.md` ("Consider GPU support", "Consider differentiable ABM"). Prototype scripts are in `v4_design/oct20/gpu_gradabm/`.

## Summary

- **GPUs: feasible for a subset of declared models, if the whole run is one JAX function.** A per-step GPU backend under today's Python-orchestrated agent engine is still a dead end (as found in July: CuPy is NVIDIA-only, torch means a rewrite, and per-step work loses on a GPU below about 1M agents). What changes the picture is the path v4 already uses for ODEs: build one pure function for the whole run from the declared graph, and `jax.jit` it with `lax.scan` over steps. That removes the per-step Python overhead, runs on CPU or GPU unchanged, and gives batching over seeds and parameter sets (`vmap`) for free. The cost is a new, restricted agent engine (fixed array sizes, declared modules only), not a port of `ss.solvers.Agents`.
- **Measured on CPU (no GPU available yet; see below):** a bare SIR on a daily-regenerated random network (10 contacts) ran in JAX about 3–4× faster than v4's `abm` solver at the same size (0.37 s vs 1.48 s at 100k agents, 5.2 s vs 15.2 s at 1M, 100 steps, 8 cores). On a GPU, the literature suggests another 10× or more at ≥1M agents (GradABM: 800k agents, 133 steps, 4 s on GPU vs 60 s on CPU).
- **Differentiable ABMs: technically easy once the JAX engine exists, but the gradients are biased in exactly the regimes that matter.** Swapping each Bernoulli draw for a straight-through or Gumbel-softmax version is a few lines. But in my prototype, near the epidemic threshold, straight-through gradients were 5× too small. On a sparse static network every estimator was off by 3–5×. This matches what Quera-Bofarull et al. (2025) report: biased estimators do poorly on sparse networks, and only unbiased stochastic derivatives (StochasticAD.jl, Julia, costly) were robust.
- **Recommendation:** (1) build a JAX agent engine for the declared subset, valued first for speed and for batched ensembles (calibration, uncertainty), on CPU and GPU. (2) Offer ABM gradients from it as an opt-in, labelled as biased. (3) Keep exact ODE gradients of the same declared model (which v4 already has) as the main gradient route. Unbiased ABM gradients in JAX would be a research project; defer it.

## What v4 already has that helps

- **A declared model graph.** States, transitions, rates as expressions, and parameters are data (`ss.transitions.Graph`), not code. So a second engine can be built from the same graph, as `ss.solvers.Compartmental` and the JAX ODE run (`ss.gradients.Run`) already are. "One declared model, any solver" is the main thing that makes this feasible.
- **Expressions that evaluate against any array namespace.** `ss.transitions.Expr` evaluation takes `ctx.xp` (`expressions.py`), which is already `jax.numpy` for the log-density. Rates written by modelers would carry over without a new expression compiler.
- **Counter-based common random numbers.** v4's CRN uniforms are a splitmix64 hash of (seed, call index, agent slot) (`ss.kernels.crn_key()` / `crn_uniform()`). That is the same idea as JAX's threefry and CUDA's Philox: stateless, parallel, and identical on any device. Ported to JAX (uint64, so `jax_enable_x64`, or a uint32 variant for float32 uniforms), a JAX engine could reproduce v4's draws for the agents and calls it shares. That would allow exact parity tests against `abm` for simple models, not just distributional ones.
- **A JAX path, and the habits around it.** `ss.gradients.reason(sim)` says in a few words why a sim cannot run in JAX. JAX is imported lazily and is an optional extra (`starsim[jax]`). The compile cache (`ss.options.jax_cache`) and `ss.parallel()` already switch to JAX for many runs (`ss.run.jax_runs`). An agent engine would follow the same pattern: a `reason()` that lists what is unsupported, and an automatic choice in `ss.solvers.choose_solver()` or `ss.parallel()`.

## What stands in the way on the agent side

The current agent engine (`starsim/solvers/agents.py`, about 2,900 lines) is Python orchestrating NumPy and Numba passes over variable-length UID arrays. Almost every feature assumes dynamic shapes or Python control flow:

| Feature | Why it resists JAX | Workaround in a JAX engine |
|---|---|---|
| UID lists of changing length (`members()`, `infect()` returning UIDs) | `jit` needs static shapes | Boolean masks over all agents; `jnp.where` instead of indexing; counts by `sum`. Costs passes over all agents, but on a GPU that is cheap |
| Scheduled exits (dwell times sampled on entry, exits due at `ti`) | Fine as arrays | An exit-time array per timed state; compare it with `t` each step. Differentiating through dwell times needs smoothing (see below) |
| Births and population growth (`People` arrays resize) | Shapes change | Preallocate capacity with an `alive` mask, and fill free slots. Bounded growth only |
| Dynamic networks with durations, `PartnerNet` / `MFNet` degree targeting | Sequential matching, variable edge counts | Fixed-capacity edge arrays with an active mask. Random regeneration and static networks are easy; preference-based pairing is hard (sort-based matching is possible but slow to write) |
| Mixing pools, contact matrices, homogeneous mixing | None: these are group sums | `segment_sum` by group: easy and fast |
| Interventions, triggers (`ss.on()`), analyzers, and coded modules with their own `step()` | Arbitrary Python | Out of scope, except declared modifiers that are tabulated in time (as the kernels already require: `sim.kernel_reason()`) |
| Strains, immunity combined by a function | As for the ODE JAX run | Same limits as `ss.gradients.reason()` |
| Exact v3-style RNG per distribution | Distributions are Python objects | Port only the hash used by the declared engine |

In practice the supported subset is the same as for the whole-run kernels and the JAX ODE run: declared diseases, demographics as rates, modifiers, mixing pools, and simple networks. That is a large share of models but excludes HIV-style partnership models, which are the ones that most need agents. Covering `PartnerNet` would be the largest single item.

## GPU specifics

- **Launch overhead and the 1M-agent threshold.** The July finding (a per-step workload loses on a GPU below about 1M agents) was about a backend driven from Python each step: around 15 passes, each a kernel launch plus synchronization. Under `lax.scan`, XLA fuses most elementwise passes, and the loop runs on the device with no host round trips. So the break-even should drop by an order of magnitude. That is to be measured, not assumed.
- **Batching is the bigger win.** Calibration, uncertainty, and scenario sweeps are many runs of a modest population. `vmap` over seeds and parameters fills a GPU even at 10k–100k agents (for example, 100 runs × 100k agents = 10M agent-steps per step). `ss.parallel()` already does this for ODEs above 300 runs; the agent engine would do the same.
- **Memory.** Per agent: a state code (int8), one or two exit times (float32), susceptibility and transmissibility (float32), and group: about 20 bytes. A random network with 5 edges per agent adds 40 bytes. So 10M agents need about 0.6 GB, which fits a consumer GPU. Reverse-mode gradients store every step (see below) and do not fit at that scale without checkpointing.
- **Precision and reproducibility.** Consumer GPUs are slow at float64, so the engine should be float32 throughout. v4's `ss.dtypes.float` and the float32 CRN branch (`crn_bits()`) already allow this. Scatter-adds (`segment_sum`) of floats use atomics on GPU, so summation order and therefore the last bits vary between runs. Integer counts (the number of infectious contacts) are exact, so the infection draws themselves stay reproducible if hazards are computed from counts.
- **Portability.** JAX runs on NVIDIA (CUDA), on AMD (ROCm, less mature), on Apple (Metal plugin, experimental), and on TPU. That is wider than CuPy or Numba-CUDA, and the same code runs on CPU, so a GPU is never required.
- **Not yet measured here.** The machine's RTX 3050 Mobile (4 GB) was not usable: the userspace driver (595.99) was updated on 2026-10-14 but the loaded kernel module is still 595.91. After a reboot (or a reload of the module), and with `jax[cuda12]` in a separate env, run `python v4_design/oct20/gpu_gradabm/proto_speed.py 1000000`. That card is a lower bound on what a workstation or cloud GPU would give.

## Differentiable ABMs: the literature

- **Chopra et al. 2023, "Differentiable agent-based epidemiology" (GradABM; AAMAS 2023, [arXiv:2207.09714](https://arxiv.org/abs/2207.09714)).** A tensorized SEIRM in PyTorch: agent states as vectors, the contact network as a sparse adjacency matrix, and transmission as a message-passing sum (order-invariant, as Starsim's is). Infection draws use Gumbel-softmax. Progression is deterministic (fixed stage durations), which avoids the hardest part. Parameters, including a time-varying R_t, come from a neural network (CalibNN, a GRU over auxiliary data series) trained end to end on deaths. Scale: 800k agents and 5M interactions over 133 steps in 4 s on a V100 (60 s on CPU), about 300× faster than Mesa. The gradients are not checked against finite differences.
- **Quera-Bofarull et al. 2025, "Automatic differentiation of agent-based models" ([arXiv:2509.03303](https://arxiv.org/html/2509.03303v1)).** The most careful treatment, and the one most relevant to Starsim. It gives a recipe: control flow becomes masked sums with sigmoid or softmax surrogates, and discrete draws use straight-through, Gumbel-softmax, or stochastic derivatives (smoothed perturbation analysis via StochasticAD.jl). It checks gradients against finite differences on Axtell's firms model, Sugarscape, and a network SIR with 2,000 agents. It uses gradients for variational calibration, and says forward mode suits ABMs because memory is constant in the number of steps. Findings: pathwise gradients match or beat score-function (VarGrad) estimators, especially as the number of parameters grows. Straight-through works near mean field (complete graph), but on sparse networks the biased estimators performed poorly. Unbiased StochasticAD was the most robust but costly. Parameters of discrete structure (network topology) stay out of reach.
- **Chopra, Quera-Bofarull, and Zhang, "Differentiable agent-based modeling: systems, methods and applications" (AAMAS 2024 tutorial, [MIT Media Lab](https://www.media.mit.edu/publications/tutorial-diffabm/)).** The page is only an abstract. It covers AD, differentiable ABMs with millions of agents, and a country-scale surveillance deployment in New Zealand, using AgentTorch.
- **AgentTorch and "large population models"** ([AgentTorch, NeurIPS 2023 workshop](https://neurips.cc/virtual/2023/79209); [Chopra et al., "On the limits of agency in agent-based models", AAMAS 2025, arXiv:2409.10568](https://arxiv.org/abs/2409.10568v2)). A PyTorch, GPU-first framework that grew out of GradABM, DeepABM ([arXiv:2110.04421](https://arxiv.org/pdf/2110.04421)), and flame. It scales to 8.4M agents (New York City) and adds LLM-driven agent behavior in archetypes.
- **Quera-Bofarull et al. 2023:** "Bayesian calibration of differentiable agent-based models" ([arXiv:2305.15340](https://arxiv.org/pdf/2305.15340)); "Some challenges of calibrating differentiable agent-based models" ([arXiv:2307.01085](https://arxiv.org/abs/2307.01085)); and BlackBIRDS, a calibration package for differentiable simulators ([JOSS 2023](https://joss.theoj.org/papers/10.21105/joss.05776.pdf)). These cover generalized variational inference, and combining reverse mode (for the flow) with forward mode (for the simulator).
- **Arya et al. 2022, "Automatic differentiation of programs with discrete randomness" ([NeurIPS 2022](https://arxiv.org/pdf/2210.08572)).** StochasticAD.jl: unbiased, automatic derivatives of programs with discrete random draws, including ABMs (Game of Life) and particle filters. Julia only; there is no JAX equivalent.
- **Andelfinger 2021, "Differentiable agent-based simulation for gradient-guided simulation-based optimization" ([arXiv:2103.12476](https://arxiv.org/pdf/2103.12476)).** The first smooth-surrogate approach, for traffic and epidemics.
- **Rijal and Mehta 2024/2025, "A differentiable Gillespie algorithm" ([arXiv:2407.04865](https://arxiv.org/abs/2407.04865v2); eLife 2025).** A smoothed SSA. It is relevant to v4's stochastic compartmental solvers rather than to agents.
- **GPU ABMs without differentiation:** FLAME GPU 2 ([Richmond et al. 2023, Software: Practice and Experience](https://eprints.whiterose.ac.uk/199416/)); PanSim (50M agents on one 16 GB GPU); EpiFast (distributed CPU). gemlib ([arXiv:2511.08124](https://arxiv.org/pdf/2511.08124)) is JAX/TensorFlow epidemic inference, but compartmental. I found no JAX-based, differentiable epidemic ABM library: the space is PyTorch (AgentTorch) and Julia (StochasticAD.jl).

## Prototype: gradient estimators through a stochastic SIR ABM

`gpu_gradabm/proto_grad.py` and `proto_grad2.py` implement an SIR in JAX with 10k agents and 100 daily steps. Recovery is geometric with a mean of 10 days. The gradient is of the final attack rate with respect to beta, taken in forward mode (`jax.jvp`) and averaged over 400 seeds. The reference is a central finite difference of the mean over the same 400 seeds, with common random numbers. The estimators are:

- `st`: straight-through (the sample forward, the derivative of its mean backward)
- `stgs`: straight-through Gumbel-softmax, τ = 0.5 (hard forward, relaxed backward)
- `gs`: Gumbel-softmax with a soft forward pass, τ = 0.5 (fractional agents, as in GradABM)

| Network | beta | Attack rate | FD of mean | st | stgs | gs |
|---|---|---|---|---|---|---|
| Dense: 5 new random edges per agent per day (near mean field) | 0.03 | 0.95 | 6.09 ± 0.03 | 5.47 (−10%) | 6.42 (+5%) | 4.22 (−31%) |
| Dense, near threshold | 0.012 | 0.25 | 91.7 ± 0.5 | 19.6 (−79%) | 29.2 (−68%) | 96.2 (+5%) |
| Sparse static: 1 fixed edge per agent | 0.2 | 0.12 | 0.86 ± 0.02 | 0.16 (−81%) | 0.15 (−83%) | 3.05 ± 0.80 (+250%, one-run SD 16) |

Reading the table:

- **Far from threshold, near mean field, the cheap estimators are usable** (within 5–10% for `stgs` and `st`). This is the regime where an ODE describes the ABM well anyway, and v4 already has exact ODE gradients for it.
- **Near threshold, or on sparse networks, pathwise estimators miss most of the gradient.** The mean attack rate depends on beta mostly through the chance that chains of transmission take off or die out. That is a discrete jump in each run, which a pathwise derivative cannot see: it is the jump term that smoothed perturbation analysis adds. `gs` landing close to the reference in the near-threshold case looks fortuitous: it is 31% off in the easy case and 250% off on the sparse network. No single estimator is reliable across regimes, and the bias is not visible from a single run.
- **Cost is not the problem.** For one parameter, forward mode cost 1.18× a plain run, and reverse mode 1.46× (10k agents, 100 steps, CPU). Reverse mode stores every step, which is about 4 GB at 1M agents × 100 steps × ~10 float32 arrays. So at scale use forward mode (one pass per parameter) or `jax.checkpoint`, as Quera-Bofarull et al. recommend.
- **Dwell times are a separate problem.** v4 schedules exits from durations sampled on entry, and `t ≥ exit time` has zero derivative with respect to the duration. The prototype used geometric per-step recovery to sidestep this, and GradABM used fixed durations. A real engine would need a sigmoid surrogate on the comparison, or would treat exits as a hazard. Either one is another source of bias.

Caveat: this is one simple model, the obvious implementation of each estimator, and 400 seeds. The pattern matches the published findings, but the size of each bias is specific to this setup.

## What it would take

1. **A JAX agent engine for the declared subset (the main work).** A new engine beside `Compartmental` and `Agents`: it builds one step function from the graph, runs it under `lax.scan`, and `vmap`s it over seeds and parameter sets. It would include a `reason()` listing what it cannot run, CRN uniforms ported from `ss.kernels`, and results in the same `Results` objects. Start with homogeneous mixing, groups and mixing pools, static and random networks, timed and rate exits, and tabulated modifiers. Add births into preallocated capacity next, and `PartnerNet` last, if ever. Test it against `abm` in distribution, and exactly for simple models via the shared hashes. This is comparable in size to the JAX ODE run (`gradients.py`, about 1,200 lines) plus a large share of the semantics in `agents.py`. Keeping the two agent engines in agreement is the ongoing cost.
2. **Batched ensembles through `ss.parallel()` and calibration.** Small once (1) exists, and the main payoff on both CPU and GPU.
3. **Opt-in ABM gradients.** Small once (1) exists: a switch on how each Bernoulli draw is made (`st` or `stgs`), forward mode by default, and a warning in the docs that they are biased away from mean field. Worth having for exploration, and for coupling to learned components as GradABM does. It should not be the default gradient for calibration: `sim.gradient()` on the ODE form of the same model is exact and far cheaper.
4. **Unbiased ABM gradients (research; defer).** Smoothed perturbation analysis in JAX: track alternative paths for flipped draws, with pruning and smoothing, following StochasticAD.jl. Nothing exists to build on in Python. A score-function (likelihood-ratio) estimator is the other unbiased route: it is easy in v4, because every draw's probability is known. Its variance is high, but batched GPU runs with control variates might make it workable for a few parameters. I did not test it.

## Open questions for Cliff

- Is a second agent engine (restricted, JAX) worth its maintenance cost, given that `abm` must stay for everything outside the subset? The alternative is to keep `abm` as is, and get the ensemble speed from more CPU processes.
- Which downstream models would use it? Most of the subset (no partnership networks, no coded interventions) is already well served by the ODE and stochastic compartmental solvers. The engine pays off where agent heterogeneity matters and the model is still declared, for example networks with individual susceptibility or households.
