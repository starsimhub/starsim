# Simplifying Starsim v4: a survey

Written 2026-10-20 on `v4-simplify` (`79592ae6`), in response to [simplify_prompt.md](simplify_prompt.md). Read-only: nothing in `starsim/` was changed. Eight surveys, one per group of modules, are in [simplify_claude/](simplify_claude/) (A to H, with usage counts, `file:line` locations and the test scripts). This page is the synthesis. Line counts are estimates from function sizes and greps unless marked as measured; where two surveys counted the same code, it is counted once here.

## In one page

- **Size.** The package is 66,705 lines: 46,139 code, 13,324 docstrings, 1,198 comments, 6,045 blank. v3 (`/home/cliffk/idm/starsim`, main) is 23,332 lines, of which 13,003 are code. So v4 has 3.5 times v3's code. Lines are also denser than v3's: `compartmental.py` averages 66 characters a line against v3's 42, and hundreds of lines run past 200 characters. The line count understates the code.
- **Main diagnosis.** Most of the growth does not come from any one feature. It comes from a multiplier. Each declarative feature is written four to six times: in the agent engine (`solvers/agents.py`), in the compartmental engine (`compartmental.py`), in the Numba kernels (often several copies; the rate interpreter has five), across diseases tracked jointly (`crossing.py`), in JAX (`gradients.py`), and in the spec, presentation and solver-choice tables (plus a refusal in `choose.py` and often a second one at engine build time). A feature that "works under every solver" costs four to six times what it costs in agents. The cheapest simplification is a rule about which features get the full treatment, and it is the one that most reduces the corner cases people trip over.
- **The rule proposed** (criterion 1, the backbone of this page): a small **core language** runs under every solver. Everything else is **agents only**: `auto` picks agents, and an explicit compartmental solver raises one `CapabilityError`. Anything a few lines of `step()` can do is better as a **coded module** than as declarative syntax. That is only possible because coded modules already drop in (see "Composability").
- **What can go.** About 14,000 lines on a conservative path and about 22,000 on the full path, after allowing for overlap. That takes the package to about **52k** or about **44k**. Getting to about 40k also takes trimming docstrings and messages (about 2–3k), or one of the radical options below. About 6–9k of the savings are *moves* out of the package (importers, JAX, the v3 calibration), not losses. Tests would shrink by about 5–8k lines as well (they are 23.8k now); that is not counted above.
- **Concepts.** The top level has 287 names that are not submodules (v3 had 212). About 113 is a reasonable target: 61 error classes, 14 calibration names, 14 time names and the v3 intervention classes move to the submodules they already live in. A generic `__getattr__` hint ("ss.X is now ss.errors.X") makes that move nearly free. [CK: no one is using this code yet, so we don't need to handle any deprecations.] Beyond names, the larger cost in concepts is the number of spellings: three ways to write a transition, about seven ways to write a branch, about six ways to say "time since", three multi-strain mechanisms, two calibration stacks, and two agent transmission paths.
- **Composability** mostly works: v3 code, a hand-written agent module, and a pure-NumPy ODE as an `ss.Module` all run. Three real gaps, all verified: `unit=` is silently ignored when no declared module is present; any coded module, even an analyzer that only reads `sir.I.n`, silently switches `auto` from ODE to agents; and `ss.Loop` cannot run without a full `Sim`. The first two are small fixes, and they matter more for the "swap pieces in one at a time" goal than any amount of trimming.

## The core language

These run under every solver, and are what tbsim v1.0.0 (the one real v4 port) uses. Keep each one implemented everywhere:

- States, `ss.Transition`, one shorthand for it (see below), `ss.par`, `ss.null`, branches given as a list of destinations with `p=`.
- Dwell times that are exponential, Erlang (`stages=`) or fixed (`ss.constant`, conveyors), and minimum stays only where they reduce to a fixed delay.
- Transmission by homogeneous mixing, contact matrices (`ss.contacts`), mixing pools by place, `ss.geo`/`ss.gravity` commuting and migration.
- `stratify`, `ss.transfer` (aging, counters, Erlang stages), `ss.by`, `ss.timeseries`, `ss.seasonal`, life tables.
- Births and deaths of the population, `ss.outcome`, `ss.modify`/`ss.change`, and triggers within one module (`ss.on`).
- Deliveries of a product to people chosen by state and group on a schedule, with coverage and a capacity cap, tests with immediate results, one-disease cures, exponential waning, `.ever` memory, and the whole-run kernel path for them.

**Agents only** (refused under compartments, with `auto` choosing agents): anything that couples two declared diseases (crossing) [CK: this seems a little extreme, if these are just extra states], pregnancy and fetal levels, lactation, `ss.birth(per=)`, rates that read time in state or `.progress`, clocks as strata, `ss.attr` levels, `ss.spread`, `ss.update`, lasting partnerships, `queue=`, delayed results, `.since`/`.count` memory, waning given as a function, deliveries to several diseases, and the event algebra (`a | b` of events as shares [CK: hm, events as shares seems potentially useful, but i could be convinced]). Each of these is a real modeling need, and each still works as agents. What they lose is an ODE form that no downstream package uses today and that, in most cases, was added in the last week.

**Coded modules rather than syntax**: hooks (`ss.func`), derived and recorded attributes, `ss.update`, back-dated seeding, movement registers, agent weights, budget optimization. Each is a few lines of `step()` in a connector or analyzer, and the framework already supports that well.

## Composability

Scripts testing each case are in `simplify_claude/scripts/` (`E_*.py` and `numpy_ode.py`, `coupled.py`, `asdisease.py`).

What works: v3's `ss.SIR` source verbatim as an `ss.Infection`; a plain `ss.Module` with a `FloatArr`; a disease written from scratch on `ss.Module`; a pure-NumPy ODE as an `ss.Module` with its own `step()` and `ss.Result`; that ODE beside a declared `ss.SIR` under agents, and under the ODE if it sets `compartmental = True`, where it can read `sim.diseases.sir.I.n`; `ss.Timeline` on its own. `modules.py`, `loop.py` and `people.py` kept v3's contract, and that is v4's composability success.

What breaks, in order of how much it matters (the first two verified again for this page):

1. **A coded module changes the solver of unrelated declared diseases.** `ss.Sim(diseases=ss.SIR())` runs as `ode`; adding an analyzer whose `step()` only reads `sir.I.n` makes it run as `abm`, and the results change from deterministic to stochastic, with no warning beyond a line in `describe()`. The way out, `compartmental = True` on the class, is documented only in the design docs. Fix: `auto` is decided by the declared modules only; a coded module that touches per-agent data in a compartmental run gets the clear `CapabilityError` that already exists (`sir.S.uids was asked for, but a compartmental run has the number in each state`). That deletes the `compartmental` flag from the user's view and the probing of user code in `choose.py`.
2. **`unit=` is silently ignored without a declared module.** `ss.Sim(connectors=P(), dt=1, unit='day')` gives `dt = 1 year`, because the unit is set inside `choose_solver()`, which returns early for sims with nothing declared. A user moving step by step (loop, then time, then disease) hits this at the second step; one survey's NumPy ODE blew up to NaN because of it. About 5 lines: set up time in `Sim.init()` for every sim.
3. **`ss.Loop` needs a full `Sim`.** `collect_funcs()` hard-codes the module categories, `sim.people` and `sim.pars.rescale`. Make the loop take an ordered list of `(label, func)` and have the Sim build it; rescaling becomes a module. About the same size, but the loop becomes usable on its own.
4. **A coded module can never share a compartmental whole run.** With one present, every declared disease steps in Python (correct, but whether a run is fast depends on about 20 conditions in `kernel_reason()` that users cannot predict). Make the engine accept an opaque module stepped between kernel steps, and say once that it costs speed.
5. **Lower layers know about higher ones.** Time types build model expressions when multiplied by a function (`TimePar._defer_ops`); distribution discovery skips solver internals by attribute name; `SimPars` assembles modules; `conditions.py` imports interventions and products; `People` knows about `ss.Pregnancy`; arrays notify engines; `RandomNet` reads the compartmental `sim.mixing`; `Delivery` keeps caches on `sim.__dict__` and discovers what to remember by walking `vars()` of every module. Each dependency should point one way (lower layers return `NotImplemented` and let the higher layer handle it). None of these is large, but together they are why a NumPy user cannot ignore the declarative machinery. [CK: ok]
6. **The model spec forces every feature into the declarative mold.** Every feature adds a hash-stable `to_json` branch "only when set, so that other specs are unchanged". If the spec moves with interop (item 1; [C2]), `sim.hash()` can be a plain hash of parameters and structure.
