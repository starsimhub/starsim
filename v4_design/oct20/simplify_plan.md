## In one page

- **The direction** [Cx Recommendation, §6]: ordinary Python components are the foundation, and the declarative language is an optional way of building them. A modeler should be able to say "I can use this loop with my arrays, then add only the services I need", and an engineer should be able to write an ordinary component without touching solver choice, graph expansion, JAX, source generation and the namespace together.
- **The compartmental boundary gets firmer** [Cx §2, Cl "The core language"]: a small declared subset has explicitly supported compartmental forms; this is not a promise that every combination works under every backend or compiles as a whole run. Individual histories, parent–child links, queues and remembered selection run as agents (`auto` picks agents; an explicit compartmental solver raises one clear `CapabilityError`). User-owned NumPy components retain their own algorithms. Crossing stays, simplified and bounded; pregnancy should have a small, explicitly described ODE approximation, without general relationship conversion.
- **No compatibility layers.** v4 is unreleased: no deprecation shims, no moved-name hints, no `_removed` tables, no migration examples. Old names are removed, and migration is by AI-assisted scripts and the migration skill. What v3 users relied on must still be possible with the new classes, though not every bell and whistle.
- **What stays in the package but leaves the root**: `ss.interop` and `ss.library` stay (and the library should grow), but are not imported by `import starsim`; inference stays (it is a major part of the value) but moves to a submodule; errors, debugging and spatial tools get submodules. Plotting stays first-class and at the top level.
- **JAX and BlackJAX become dependencies**, as Cliff allowed, but a single JAX implementation for declared ODE execution is an experiment, not a prerequisite for composition or a requirement on NumPy components (S1.6). Making a dependency mandatory does not by itself remove duplicated implementations or make posterior inference the right default.
- **Expected size**: prioritize fewer supported combinations and fewer dependencies between subsystems. The earlier 8–15k deletion estimate is a hypothesis, not a delivery target; its upper end includes unproven backend savings and documentation cuts. Keep separate counts for the full package, package excluding interop (Cliff's preferred convention), and execution/modeling services. Keeping inference and domain services makes the Codex survey's 43k illustrative package non-comparable without adjustments; see the ledger at the end.
- **Order**: scope and baselines first (S0), then the small composability slice (S1.1–S1.5), clear removals (S2), and the reduced compartmental boundary (S3/S4). Consolidation and namespace work follow on the smaller implementation. S7.1/S7.2's approved feature removals precede the Delivery split; the JAX spike and optimization pruning follow the boundary decision. Run focused checks per change, the full test suite (`cd tests && ./run_tests`) at coherent stage boundaries, and the perf guard for execution changes. Reuse the recorded baseline rather than rerunning all checks before every edit.

## Rules for implementing this plan

The Codex architecture is the governing direction; the Claude inventory supplies concrete cuts, not a requirement to complete every refactor. Cliff's explicit decisions above and below take precedence over either survey. Keeping interop, the library, inference, pregnancy, strains, plotting and the existing import style is compatible with modularity: what matters is that the scheduler and numerical components do not depend on their internals.

- **Do not replace deleted features with a new framework.** No universal capability lattice, generated multi-backend compiler, generalized hybrid population engine, or mandatory policy-builder vocabulary. If a cut needs a large replacement, stop and reassess that item rather than force it through for a line target.
- **Separate the kinds of support.** A component can run in the Python schedule without population data, graph lowering, whole-run compilation, gradients, serialization, or snapshots. Those are separate optional capabilities; absence of one must not block an ordinary run. The global declared solver governs declared population models, not the internal algorithm of an opaque NumPy component.
- **Preserve scientific meaning.** Conservation, competing risks, event timing, shared-person correlations, CRN and observation alignment remain requirements. A fallback/refusal must occur before unsupported declarations start running. Do not retry a partially executed arbitrary callback under another solver.
- **Use concrete replacements, not test counts, to justify cuts.** One test is not evidence of low usage; zero downstream callers is a search result, not a permanent fact. For each removed convenience, demonstrate its supported replacement or record that the capability is deliberately being dropped. Keep small helpers when replacing them introduces more rules.
- **One ownership contract and one schedule.** Ordinary arrays/callbacks must remain usable outside Starsim. Category keywords and the agent phase preset stay; neither should impose people or disease initialization on independent components. A schedule must say when a callback observes state and when mutations become visible.
- **Distinguish moves from deletions.** Namespace changes and moves into the in-package library save no package lines. Benchmark-dependent savings and new adapter code must be counted separately. Useful documentation and scientific validation are not a line budget.

These rules are acceptance criteria for the stages, not extra infrastructure to implement.
