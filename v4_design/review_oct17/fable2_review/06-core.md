# Core (Starsim 3 base that v4 sits on): review

I read `v4_design/design/01-objects.md`, `02-types.md`, `10-execution.md`, `11-random.md`, the departures and known issues in `admin/implementation.md`, and then `starsim/sim.py`, `modules.py`, `loop.py`, `people.py`, `arrays.py`, `parameters.py`, `time.py`, `timeline.py`, `distributions.py`, `diseases.py`, `utils.py`, and `settings.py`, diffed against the v3 tree at `/home/cliffk/idm/starsim/starsim/` (the diff is 1,324 lines in `sim.py`, 288 in `diseases.py`, 215 in `distributions.py`, and under 100 in each of the rest; `modules.py` changed by 17 lines). I ran about twenty small probes with the v4 Python to check claims. Verdict: the v3 machinery that v4 reuses (the module lifecycle, the loop as data, arrays, CRN) is in good shape and was changed very little, which is the right call; the cost has landed almost entirely on `Sim`, which went from 21 to 59 instance attributes and now carries ~1,300 lines of v4 bookkeeping that has no owner object. The second theme is that "two systems" is real and visible to the user in three places: time defaults, what the library `ss.SIR` is, and how a bare number is read. Each has a concrete fix below.

## Top findings

1. **`Sim` is carrying ~400 lines of group/stratum state and ~250 lines of solver/unit choice that belong on two small objects.** `sim.py:547-936` (`init_strats`, `init_ragged`, `fold`, `fold_matrix`, `group_vals`, `grid_index`, `init_crossings`, `groups_changed`, `group_raw`, `folded`, `level_raw`, `init_strat_vals`) and the attributes they set (`strats`, `sim_strats`, `cross_strats`, `group_shape`, `group_mults`, `group_coords`, `group_split`, `birth_split`, `group_fold`, `group_inside`, `group_levels`, `joint`, `dim_moves`, `_group_cache`, `_group_dirty`, `_level_cache`, `rng_strat_*`) are one concept: the grid of groups. `init_solver` (292-400) plus `init_unit` (1026-1074), `agent_reasons`, `try_functions`, and `init_named_people` are another: resolving the run. The symptom that the group state has no owner is that `init_strats()` runs up to three times per build (327, 378, 787) and `ss.solvers.Mixing(self)` is constructed up to three times (328, 379, 788) because later steps discover dimensions and have to redo it. For the user nothing changes if these become `sim.groups` (a `Groups`/`Strata` object in `transitions.py` next to `Strat`, which `solvers.Mixing` already is the model for) and `sim.t.unit`/`sim.t.unit_source` (the unit rules on `Timeline`, which already owns `start`, `stop`, `dt`); `sim.describe()`, `solvers()`, `hash()`, `to_spec()`, `to_code()`, `R0()`, `check_dt()`, `gradient()`, `restart()`, `what_modifies()` are a fine user surface and should stay as methods, but each should be a two-line forwarder to `spec.py`/`solvers.py`/`calibration.py` (most already are; `check_dt` at 445-491 and `what_modifies` at 493-533 are the ones with logic inline). The win is for the maintainer only, which is still worth it at 2,700 lines: `sim.py` is no longer holdable in one head, and the `Sim.init()` order (233-290) interleaves v3 steps and v4 steps that depend on each other in ways the comments do not say (e.g. `init_solver` must run before `init_time` because `init_unit` rewrites `pars.dt/start/stop`, 1066-1073).

2. **The library models are still the second system: `ss.SIR(beta=0.1)` is not "an ordinary module" as 01-objects §Library models promises.** Spec 01:150 says a library model "is an ordinary module: `describe()` prints it in full and `equations()` works on it". In the code `ss.SIR`, `ss.SEIR`, `ss.SIS`, `ss.NCD` (`diseases.py:979-1353`) are the v3 imperative classes with `define_pars`/`define_states`/`set_prognoses`; `ss.SIR().equations()` raises "has no declared transitions", `describe()` prints `written as code`, `solvers()` says `no (works on agents)` under ODE, and `sim.new()`, `check_dt()`, `R0()`, `what_modifies()` all refuse the sim (verified). This is not in the departures list. Rewriting the three in the class form is the one step that makes the class form "the long form of the same vocabulary rather than a second system", and it is small:
   ```python
   # Before (diseases.py:1065-1175, ~110 lines of methods)
   class SIR(Infection):
       def __init__(self, pars=None, beta=_, init_prev=_, dur_inf=_, p_death=_, **kwargs): ...
       def step_state(self): ...
       def set_prognoses(self, uids, sources=None): ...
   # After (the same keywords, every solver, describe/equations/R0 work)
   class SIR(ss.Disease):
       beta     = ss.par(ss.peryear(0.1))
       dur_inf  = ss.par(ss.lognorm_ex(mean=ss.years(6)))
       p_death  = ss.par(0.01)
       S, I, R, D = ss.states(4)
       infection = ss.transmission(S, I, beta=beta)
       recovery  = ss.progression(I, R, dur=dur_inf, p=1 - p_death)
       death     = ss.death(I, dur=dur_inf, p=p_death)
   ```
   What breaks: v3 code that reads `sir.infected`, `sir.susceptible`, `sir.ti_infected`, `rel_sus` as `FloatArr`, overrides `set_prognoses`, or uses `infection_log`. The Agents engine already makes `sir.I`, `sir.ti_I`, `rel_sus`/`rel_trans` arrays (`solvers.py:3163-3172`), so `infected`/`susceptible` could be aliases of `I`/`S` for one release. `ss.Infection` (the v3 network-transmission base, `diseases.py:390-820`) stays for subclassers; it is the library instances, not the base class, that should move.

3. **Time defaults differ between the two forms, and the "timesteps" sim is secretly a days sim.** `ss.Sim(ss.SIR(), stop=10)` is 10 years at `dt=years(1)`; `ss.Sim(ss.Disease(...), stop=10)` is 10 steps (verified). The departure is listed ("Sims with no declared states keep Starsim 3's time defaults"), but two costs are not. First, the unitless sim is implemented as days: `sim.py:1063` sets `unit_base = unit or 'day'`, so `t.tvec` is `days(0), days(1), ...`, `t.yearvec` is `0.0, 0.00274, ...`, and `t.datevec` is `datedur(, +23:59:60)` (verified; garbage), and a v3 `ss.Births(birth_rate=20)` in the same sim is still in years. Second, ~50 lines exist only to warn about the collision: `parameters.py:38-60` (`note_bare`, `forget_bare`, `bare_units`), `modules.py:715-725` (`check_bare_units`), and the known issue "a bare number given for a parameter of a module written as code keeps the unit of its default". Two rules for one thing ("what unit is a bare number in") is the kind of finding the brief asks for. Proposal: one rule, the spec's (02:82 "the slot gives the dimension and the sim gives the unit"), applied to user-supplied bare numbers in v3 modules too, with the typed defaults (`beta=ss.peryear(0.1)`) untouched; and a real step unit (`ss.steps`, a `dur` with no calendar) for the unitless case so `yearvec`/`datevec` do not exist rather than being wrong. What breaks: `ss.SIS(dur_inf=10)` in a sim in days would mean 10 days, not 10 years; that is the only form that changes meaning, and it is exactly the case the warning fires on today, so the warning becomes the migration note.

4. **The loop has two notions of `ti` and a magic-name filter, both to give declared models the "results at time point ti" convention.** `loop.py:383-396` (`_before_first_step`) drops the step entries at `ti=0` for every sim by matching function names (`start_step`, `update_results`, `sim.finish_step`, analyzers, module `finish_step` but not people/sim), and `loop.py:360-381` (`_at_start_funcs`) rewraps declared diseases' `step_state`/`step` and deliveries' `step` in `ss.solvers.interval()` (`solvers.py:537-553`), which decrements `sim.t.ti` and `mod.t.ti` for the duration of the call. So inside a declared disease's step (including a user function passed as a keyword, which `Disease.step` calls inside the wrapper, `diseases.py:347-351`) `sim.ti` is the start of the step, while in a connector, an inserted function, or an analyzer in the same step it is the end. That is a per-row difference a user writing custom code will hit and cannot see from `sim.loop.to_df()`. Proposal: make the convention structural rather than patched: `init_results()` records the start at index 0, the plan runs steps `1..T` with one `ti` meaning "the step being taken" for everyone, and `interval()`, `_before_first_step()`, and the `_at_start_funcs` rewrap go away. What breaks: v3 modules that index results by `self.ti` get the same arrays they get now (the filter already changed their convention); the only code to touch is `Module.finish_step`/`finalize` (`modules.py:872-899`) which increments and then decrements `ti`.

5. **Spec and code disagree on the type arithmetic, and the dimension check the spec promises is not there.** (a) 02:62 says `per × dur` is "the expected count over the period, not a probability"; the code (`time.py:2203-2204`, `per.__mul__ = to_prob`) gives `1 − exp(−r·t)`: `ss.perday(0.05) * ss.years(1)` is `0.99999`, not `18.25` (verified), and `freq × dur` is the count. One of the two is wrong, and since the section opens with "Starsim's rules, summarized", it is the spec. (b) `E102 WrongDimension` (02:69-78) is in the code table (`transitions.py:32`) but is never raised anywhere; `ss.progression('I -> R', dur=ss.probperday(0.1))` is accepted and `describe()` prints `dwell ~ exponential(mean = 0.1 probability per day)` (verified). The type system is strict where it is cheap (`1 - ss.peryear(0.008)` raises, `ss.peryear(0.1) > 0.05` raises, `np.exp(-rate)` asserts) and lax where it matters (a rate in a duration slot). (c) `ss.Sim(..., results=[...])` (01:191) is not implemented: `KeyNotFoundError: results`. (d) 01:121 says a module is named from "the variable it is bound to where it is passed to `ss.Sim`"; `sim.py:113` applies that only when `type(mod) is ss.Disease`, so `my_model = SEIR(); ss.Sim(my_model)` is named `seir` (verified). (e) 01:13 says `ss.Module` "owns states, transitions, parameters, results"; only `ss.Disease` has a `graph` (`diseases.py:63`), and `sim.py` tests for it by `getattr(mod, 'graph', None)` in 8 places. None of (a)-(e) is in the departures list; (a), (b), and (c) should be fixed or de-specified, (d) is a two-line fix (`isinstance` and a frame lookup for any module), (e) needs a sentence in the spec.

6. **The time vocabulary a v4 user needs is `dur`, `per`, and `prob`; `freq` and the deprecated aliases should leave the public set.** Counting uses outside `time.py`: `freq*` appears 7 times in `starsim/`, all in v3-style modules (`MFNet.acts`, `Pregnancy.fertility_rate`, `Births`, cholera's `shedding_rate`, `DiskNet.v`); `prob*` 6 times (demographics' internal conversions and two placeholders); `ss.rate`, `ss.time_prob`, `ss.rate_prob` (`time.py:2401-2411`) only in the v2→v3 migration docs. In a declared model every rate slot accepts all three and converts to a hazard (`solvers.py:32-34`; a `freqperday(0.3)` and a `perday(0.3)` transmission give identical ODE peaks, verified), so for v4 users `freq` and `per` are the same thing with two names and a 4×4 grid of 16 constructors to learn. The one real distinction `freq` carries is linear scaling for a Poisson `lam` (`scale_types`, `distributions.py:268`), which is a property of the distribution's parameter, not a time type the user should pick. Proposal: the spec's "four types" (02:9-16, 01:25) become three in the user-facing docs and `__init__` exports (`dur`, `per`, `prob`, with `freq` kept as an internal alias of `per` with count scaling for `Dist` parameters, or dropped once `acts=` is a `per`); delete `rate`, `time_prob`, `rate_prob`. On the known issue "a typed rate cannot be used as a plain number": the `__rsub__` error (`time.py:1803-1807`) is the right design (`1 − r` is dimensionally meaningless), and the message already names the fix; the real issue is the one in finding 5(b).

7. **`sim.people` is reused as the group table in a compartmental run, and it leaks.** `sim.py:385` sets `pars.n_agents = n_groups`, `1532` builds `People(n_agents=n_groups)`, `277-282` deletes `people.age`/`female` when they are not dimensions, `people.py:109-116` adds a `__getattr__` to explain the deletion, and `sim.py:161` means `repr(sim)` prints `Sim(n=1; 0—10; diseases=sir)` for an unstratified ODE sim (verified; `len(sim.people) == 1`, `sim.pars.n_agents == 1`). The known issue "a condition on a property of people needs a `ppl` object (`ss.People(1)`) even in a compartmental model" comes from the same choice. Proposal: in a compartmental run `sim.people` is `None` and `sim.groups` (finding 1) carries the per-group properties (age midpoints, sex) that conditions and `adjust` read; and lazy conditions get a module-level spelling that needs no `People`, in the style of `ss.null`:
   ```python
   # Before
   ppl = ss.People(1)
   ss.progression('S -> R', rate=ss.perday(0.05), where=ppl.age >= 50)
   # After
   ss.progression('S -> R', rate=ss.perday(0.05), where=ss.age >= 50)
   ```
   (`ss.people` is now the named-population loader, `people.py:725`, so the attribute would be `ss.age`, `ss.female`, or `ss.attr('age')`; `arrays.py:453-454` already returns an `ss.Cond` from a comparison on an uninitialized array, so the plumbing exists.)

8. **`pars=` on `ss.Sim` means two things, decided by a heuristic.** `sim.py:77-78`: a `pars` dict is model-parameter values unless any key is a sim parameter, so `ss.Sim(sir, pars=dict(beta=0.1, rand_seed=2))` raises `KeyNotFoundError: beta` (verified) and `pars=dict(beta=0.1)` silently becomes sim pars if a model ever names a parameter `dt`, `label`, `unit`, or `verbose`. The spec (01:190) gives `pars=` one meaning. Proposal: `pars=` is model values only; v3's sim-parameter dict is the first positional argument, which `sim.py:71-72` already reads. What breaks: v3 scripts that write `ss.Sim(pars=dict(n_agents=...))`, a mechanical one-line migration.

9. **Four ways to set a parameter on a declared disease, one of which prints a spurious warning.** `sir.pars.beta = 0.6` works but prints `No known mechanism for handling <class 'starsim.transitions.par'> → <class 'float'>; using default` (`parameters.py:132`, because `Pars.update` does not know `ss.par`), and replaces the `ss.par` with a float, so `sir.graph.pars['beta']` and `sir.pars.beta` are no longer the same object (verified; the engine still reads the right value, but a later `ss.modify(sir.pars.beta, ...)` now raises `E504 UnmodifiableTarget` because the target is a plain float, while the string form `ss.modify('sir.pars.beta', ...)` still works). `sir.update_pars(beta=0.6)` does the same; `sir.set_pars(beta=0.6)` (`diseases.py:105-115`) is the third method, added for `ss.par`; `ss.Sim(pars=dict(beta=0.6))` is the fourth. Proposal: teach `Pars` one rule, "if the old value is an `ss.par` and the new one is not, set `.value` in place", and delete `set_pars`.

10. **A transmission model with nobody infected runs to zero in silence.** With no `init_prev`/`init`, `describe()` prints `init: S = 1.0 [guessed: nothing given]` (which 01:327 shows as the intended output), the run produces a flat zero, and neither `W1201 SmallCounts` nor any other note fires (verified; `sim.notes == []`). For a model with a `transmission`, a guess of zero infected is wrong every time. Either `init_prev` defaults to a small seed when the model has a transmission and nothing is given (and `describe()` marks it `[guessed]`), or the build prints one line: `note: nothing starts infected, so 'infection' can never happen; give init_prev= or init=`.

## Other findings

- **`I >> R @ 10` is a rate of 10 per step and nothing says so.** The spec (02:91) chose "a bare number after `@` is always a rate" knowing `@ 0.1` and `@ 10` cannot be told apart; under the ODE no `W102 LargeStep` fires (right per 02:49) so the model silently recovers everyone in a tenth of a step (verified: `dwell ~ exponential(rate = 10 per step)`, no note). A one-line note when a bare rate after `@` is ≥ 1 per step ("did you mean `dur=`?") costs nothing and catches the case the spec itself flags; it also caught me while writing the probes.
- **`requires` has two meanings.** `modules.py:270` makes it metadata (a list of `ss.Requires`, "never enforced"); v3's `self.requires = ss.HIV` is a dependency checked by `ss.check_requires` (`debugtools.py:358`), and `sim.requires()` (`sim.py:1237-1246`) handles both in one loop. One word, one enforced and one not. Keep the metadata meaning and spell the dependency as `ss.Requires('hiv', module=True)` or leave v3's under a different name.
- **The sim keeps four records of what it was given.** `pars` (the merged values), `given` (which keys, `sim.py:87`), `inputs` (a second deep copy of every module, `85-86`, made only when a module has a graph), and `par_values` (`75`). `sim.new()`, and through it `R0()`, `check_dt()`, `gradient()`, `try_functions()`, work only when `inputs` exists, which is why they refuse v3 sims (`428-430`). `copy_inputs=True` already copies the modules once (`83`); keeping that copy as `inputs` for every sim would make `new()`/`check_dt()` work for v3 models at no extra cost.
- **A typed `start`/`stop` duration is a unit source the spec does not list.** `sim.py:1050-1051` takes `stop=ss.weeks(12)` as the sim's unit before the typed values in the model, which is the known issue "the sim runs in weeks even if every rate is per day"; 02:99-108 has no such row. Either add the row (it is a reasonable rule) or drop the branch and let rule 4 decide.
- **`describe()` prints nothing about common random numbers.** 11:47-55 specifies a CRN section listing paired and unpaired draws; the output has no such lines (verified on an agent-based declared sim). Not in the departures. Either implement (the Agents engine names every stream, `solvers.py:3193-3218`, so the list is available) or de-specify.
- **Four spellings of a gamma dwell time.** `ss.gamma(a=, scale=)`, `ss.gamma(mean=, std=)` (`distributions.py:1803-1812`, new), `ss.erlang(k=, mean=)` (`1821-1842`, new), and `stages=` on the transition. The spec (02:170) added `erlang` and in the same sentence says `stages=` "says the same thing". Cut `ss.erlang`: `dur=10, stages=3` is shorter and is already the spec's word; `gamma(mean=, std=)` is worth keeping because it is how people know their data.
- **`Dist.__init__` has 13 keyword arguments** (`dist, distname, name, unit, round, seed, offset, strict, auto, sim, module, mock, debug`; `distributions.py:397`); a v4 user needs `unit` and, rarely, `name`. The rest is CRN/debug plumbing that the Agents engine already hides (it creates ~15 named `ss.random()` streams per disease and draws per UID at `3611`, so a v4 user never calls `rvs`). Nothing to cut in the engine, but the signature the docs show could be `ss.Dist(dist=None, name=None, unit=None, **pars)` with the rest keyword-only on an `options`-style object. The lazy `rng` sync (`540-570`) and the static-parameter cache (`837-868`) are good additions and should stay.
- **`Timeline` has six vectors (`tvec`, `yearvec`, `timevec`, `relvec`, `datevec`, `tivec`; `timeline.py:86-166, 501-533`) and in a unitless sim three of them are meaningless** (finding 3). This answers the spec's open question (02:200): the irreducible three are `tivec` (step), `timevec` (the sim's own unit), and `datevec` (calendar, only when there is one); `yearvec` and `relvec` are conversions. `time.py` itself is 2,612 lines of which `date` (436), `DateArray` (201), `datedur` (323), and the Matplotlib converters (`2418-2612`, ~200) are calendar code that could live in a `dates.py`, leaving the four types in ~1,000 lines.
- **`time.py:804-821` (`_defer_ops`) monkeypatches every `TimePar` operator at class-definition time to yield to model expressions** (`_is_expr`). It works, but it is a hidden dependency of `time.py` on `transitions.py`; the standard way is for `Expr` to define the reflected operators and set `__array_priority__`/return `NotImplemented` itself, which keeps `time.py` ignorant of the model layer.
- **`ModifiableArr.record()` walks Python frames on every write** (`arrays.py:946-957`) to name the writer. Fine while `track_writes` is off by default, but the docstring in 10:66 should say it is also slow when on, not only "not free".
- **Naming collision question (asked in the brief): there is none.** v3 renamed its boolean array to `ss.BoolState` (`arrays.py:1088`) and `ss.State` is only `transitions.State` (`transitions.py:428`), so the name is not overloaded. But the two concepts do meet in the Agents engine, which makes a `BoolState` per declared `State` plus `ti_<name>`, `ti_exit_<name>`, `exit_<name>`, `mult_<name>` arrays (`solvers.py:3167-3172`): five arrays per state, and a user who writes a per-agent function sees these names with no documentation. The UID/`auids`/`raw` distinction is something a v4 user meets only in such functions ("the function takes uids", `sim.py:987`), which is the right place for it to stay.
- **`kernel_reason()` returns `'unknown'` when the kernels do run** (`sim.py:1884`); harmless, but it reads as a bug in `restart()`'s error path.

## Things that are good

- `modules.py` changed by 17 lines and `loop.py` by 93. The lifecycle (`init_pre`, `init_post`, `start_step`, `step_state`, `step`, `step_die`, `update_results`, `finish_step`, `finalize`) was reused, not forked; a declared `ss.Disease` forwards eight of the hooks to its engine (`diseases.py:256-365`) and defines no new ones. Do not add a parallel lifecycle for declared models; the one asymmetry (finding 4) is fixable inside the existing one.
- The loop as a data object, `Loop.plan` made lazily (`loop.py:90-99`, so a kernel-only run never builds it), and `insert()` accepting a module (`495-517`).
- `describe()` (`sim.py:1076-1163`) is the best thing in the file: every guess marked, the schedule grouped by timestep, the unit source shown. Keep it exactly as specified; finding 10 is about what it should additionally say.
- `init_unit()` (`1026-1074`) is a readable implementation of the spec's five rules; the problem is only where it lives and the extra row.
- CRN is already hidden from v4 users (one `ss.random()` per decision per disease, drawn by UID), and the `Dist` optimisations (lazy `rng` jump, static parameter cache, direct `ppf` for normal/lognormal) are real wins that cost nothing in API.
- `gamma(mean=, std=)`, `truncnorm`, `People(p_female=)`, `ss.people('Kenya')`, `nb_true_raw`/`nb_count`, `count_gone`: small, correct, cheap.
- `sim.hash()` built on `split_numbers()` (`utils.py:246-273`) so the model hash ignores values and the pars hash ignores structure; `to_spec()` as plain JSON with rates as strings.
- `Requires` as metadata that is never enforced (`parameters.py:633-661`).

## Questions for Cliff

- Finding 3: are you willing to break `ss.SIS(dur_inf=10)` (today 10 years in any sim) so that a bare number means the same thing in both systems, with the current warning as the migration note? If not, the warning stays and the two rules should be written side by side in 02-types.
- Finding 2: rewrite `ss.SIR`/`ss.SEIR`/`ss.SIS` in the class form (keeping the keyword names, aliasing `infected`→`I` for a release), or keep them imperative and change 01:150 to say library models are not declared?
- Finding 6: drop `ss.freq` from the public set (keep it internal for `Dist` count scaling) and delete `ss.rate`/`ss.time_prob`/`ss.rate_prob`? The 16-constructor grid is the single largest piece of vocabulary in 02.
- Finding 7: should a compartmental sim have `sim.people` at all? If the answer is "yes, for v3 code that reads `sim.people.age`", the `n=1` repr and `n_agents == n_groups` need hiding anyway.
- Finding 8: give `pars=` its spec meaning only, breaking `ss.Sim(pars=sim_pars)`?
- Finding 5(a): which is right for `per × dur`, the spec's count or the code's probability? The code's is what Starsim 3 users have; the spec's is what `freq` does today.
- `ss.erlang`: keep as a documented name people search for, or cut in favour of `stages=`?
