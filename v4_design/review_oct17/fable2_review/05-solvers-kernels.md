# Solvers and kernels: review

I read `starsim/solvers.py` (4,136 lines), `starsim/kernels.py` (1,372), `starsim/gradients.py` (1,121), the solver-choice and run sections of `sim.py`, the `ss.Disease` → engine hand-off in `diseases.py`, `ss.Delivery.shifts()`, the spec files 10, 11, 12 and 18, and the "10 to 12" section, departures, known issues and deferred list. I ran small checks under all six solvers with the v4 Python (scripts in `/tmp/claude-1000/-home-cliffk-idm-ssv4/ca97d20f-10b5-44a7-9912-4c092dbb024e/scratchpad/check1.py` to `check6.py`). Verdict: the core design is right and verified (one flat `Program` shared by Numba and JAX; whole runs at 2 µs/step; the timing convention, conservation, integrality and joint competing hazards all hold under every solver), but the same semantics are executed by five RK4s, three outcome evaluators, two op-stack interpreters, and a Python copy of every stochastic solver, and the stepped stochastic path has a real reproducibility bug. About a third of `solvers.py` is paths and special cases that one or two general mechanisms would subsume.

## Top findings

1. **Bug: in the stepped path, adding an unrelated disease changes another disease's stochastic draws.** `ss.kernels.seed()` sets Numba's single global RNG state; `Compartmental.init_program()` calls it per engine (`solvers.py:2277`, and lazily from `step()` at `solvers.py:2860`, so the last engine to build its program reseeds after earlier engines have drawn), and `one_step()` (`kernels.py:1284`) then draws from that shared state as the engines interleave. Repro: an SIR plus a second declared disease, `solver='binomial'` or `'gillespie'`, seed 3, forced onto the stepped path (any intervention, analyzer, or `verbose=1`): `n_I` of the SIR differs by up to 236 (binomial) and 248 (gillespie) from the SIR alone; the whole-run path (`kernels.run()` seeds per call, `kernels.py:1136`) gives 0. This breaks 11-random §Streams ("Adding a module does not change any other module's draws") and conformance suite 10, and it also means that in a sim with two or more stochastic declared modules, `verbose=1` (which forces the stepped path) changes the numbers. Fix: give each engine its own stream in the kernels (derive the seed per engine and per step, `H(engine_seed, ti)`, inside `run()` and before each `one_step()`; then stepped and whole runs agree bit for bit for any number of modules, which they already do for one). Note the same run also uses a second generator, the engine's NumPy `rng`, for outcomes, `take()`, `land()` and movers (`solvers.py:1368`, `1926`, `2077`, `2906`), so a stochastic run is already two streams.

2. **The Python copies of the five solvers buy nothing measurable and could be dropped.** Measured (SIR, 10,000 people, 3,650 daily steps): whole-run kernels 2 µs/step; stepped kernels ~200 µs/step; Python solvers ~280 µs/step (binomial 196 vs 201; gillespie 206 vs 332). The stepped cost is the Python bookkeeping around a step (`start_step`, `update_targets`, `step_tables`, `one_step()` allocating a fresh workspace at `kernels.py:1288`, `record_stocks`, `update_results`), not the arithmetic, so the kernel-vs-Python divide is not where the speed is; the whole-run-vs-stepped divide is. The Python solvers (`step_ode`'s RK4 branch and Python `derivs` at `solvers.py:2365-2399` and `2920-2938`, `step_binomial_once` 2985, `step_tau` 3037, `step_gillespie` 3064, `step_sde_once` 3116, `draw_targets` 2954, `piece` 3097: about 330 lines) are reached only when `init_program()` refuses (`solvers.py:2138-2144`, `2176`: a rate that is a plain Python function of the sim, a `dict` beta per network, or a `where=` on a network's `n_contacts`) or when a test sets `engine.use_kernels = False`. Proposal: always step with the kernels; evaluate a function-of-the-sim rate in Python once per step into `consts`/`fixed` (or at the start, middle and end as `step_tables()` already does for smooth time-varying values, `solvers.py:2342`), fold a `dict` beta into the mixing term's `contacts` at `Mixing.init()`, and treat the `where=` network modifier as per-group `contacts` (the program already has `contacts` per term). What is lost: a function of the sim that reads compartments would see them at the stage times rather than at every RK4 stage (the same approximation `tables()` already makes for time-varying modifiers at `solvers.py:2549`), the six oracle tests in `tests/test_kernels.py`, and the ability to debug a solver in pure Python. What is gained: one definition of each solver, the end of the known issue "kernels draw from Numba's generator, so `use_kernels=False` gives different numbers", and the end of a worse version of it that is not listed: turning `beta=0.3` into `beta=lambda sim: 0.3` moves the model to the Python path and changes its draws (verified: max diff 224 in `n_I` with the same seed), which is the same model written two ways giving different random numbers.

3. **One representation, five executions.** The `Program` (`kernels.py:25-83`) is the right idea and it is genuinely shared, but it is consumed by: RK4 in Python `derivs()` (`solvers.py:2365`), RK4 in `kernels.step()` (`kernels.py:705`), RK4 in `kernels.settle()` for count states under stochastic solvers (`kernels.py:507`), RK4 in `Agents.step_counts()` for count states as agents (`solvers.py:3745`, written over `sc.objdict`s), and RK4 in `gradients.Run.stepper()` (`gradients.py:261`); the op-stack interpreter appears in `kernels.step()` (`kernels.py:798-849`), again in `kernels.place_rates()` (`kernels.py:375-422`, a per-place copy with a different stack layout), and in `gradients.Run.rates()` (`gradients.py:189-222`); and outcomes are computed per step in `Engine.step_outcomes()` (`solvers.py:1341`), for a whole run in `Compartmental.derived_outcomes()` (`solvers.py:2785`), and in JAX in `Density.outcomes()` (`gradients.py:994`). Concrete merges that lose nothing: (i) `Agents.step_counts()` should build a `Program` for the count states and call `kernels.settle()`, which has the same semantics (RK4 over the step with the people as at its start); (ii) `place_rates()` should be the general rate loop called on a slice of groups (`a, b`), not a second interpreter; (iii) `step_outcomes()` should be `derived_outcomes()` applied to one step (it already handles arrays with a trailing step axis); (iv) the result bookkeeping that appears four times (`update_results` 1417, `run_all` 2613, `collect` 2713, `derived` 2759, plus `store()` closures in two of them) should be one "results from stocks and flows arrays" function that the stepped path calls with one row. Together these are about 300 lines of `solvers.py` and 70 of `kernels.py`, and each is a place where the semantics can drift (the departure "counts are advanced by RK4 as agents" was a bug of exactly this kind: implementation.md §03 says it "was biased by 5% and a step early").

4. **JAX: keep it, but as the ODE run only, and stop differentiating "the steps either side" numerically.** Could Numba be the only compiled path? It would drop 1,121 lines; what is lost is exact gradients for L-BFGS-B (the 8-parameter fit converges in 110 evaluations where Nelder-Mead stops at 1,600, implementation.md §12), NUTS for ODE models, and `run_sets` (1,000 runs in 0.5 s vs 1.2 s). Finite differences through `restart()` plus the whole-run kernel cost about 2 runs per parameter at 2 µs/step, which is competitive with JAX for a fit (JAX's gradient "costs about 8 runs" per implementation.md) but not for NUTS, which needs thousands of gradients and the fused log-density. Could JAX be the only compiled path? No: compile is per model shape and per `n_max` change (about 1 s each, `gradients.py:530`), import is 1.7 s, the exact solver's event loop is hostile to XLA, and the fork deadlock (known issues) would then affect every `ss.parallel()`. So both stay, and the Numba-by-default departure from 12-backends (which says SciPy for small and JAX for large/fitted) is the right call. The duplication to cut is inside `gradients.py`: `gradient()` differentiates the run in JAX and then the Python tail (parameters to program numbers, run to results and likelihood) by central differences with `capture()`, `tangent()`, `give()` and `shift=` (`gradients.py:641-699`), so a gradient is 1e-10 rather than exact and costs two restarts per parameter; but `Density` already evaluates the rates, outcomes, results and likelihood from the parameters in JAX (`gradients.py:935-1047`). `sim.gradient()` should be `jax.jacfwd` of a `Density`-style results function, which removes the central-difference machinery (about 80 lines) and the `given`/`store_replayed` hooks in `Compartmental` (`solvers.py:2619`, `2672`). `JointRun` (`gradients.py:385-461`) goes with finding 10.

5. **Spec vs code: `ss.MFNet` has no compartmental approximation; the spec uses it as the example.** `Mixing.init()` accepts only `RandomExactNet`, `StaticNet` and `PartnerNet` with an `n_contacts` (`solvers.py:152`); `ss.Sim(sir, networks=ss.MFNet(), solver='ode')` raises `E804: MFNet has no compartmental approximation yet` (verified). 12-backends §Approximations shows exactly this call printing "MFNet approximated by partner-change rates between sex/risk groups", corpus model 10 in 18-conformance asserts it runs, and implementation.md §06 ticks "Networks, as agents and (approximated, with a note) as compartments". `MFNet` now inherits `DegreeTargets` (`networks.py:1456`) so the `PartnerNet` branch nearly applies; either finish it or list it as a departure. `RandomNet` and `RandomExactNet` do work and print the note.

6. **`integrator=` does not accept the spec's spelling, and rewrites the user's word.** 12-backends says `integrator='scipy'` or `'jax'`; the code accepts `'rk4'`, `'euler'`, `'jax'`, or any `solve_ivp` method name (`parameters.py:325`, `solvers.py:2940-2948`), and `integrator='scipy'` dies inside SciPy with a raw `ValueError: method must be one of {...}` (verified). `integrator='jax'` is silently rewritten to `'rk4'` with `sim.jax = True` (`sim.py:372-374`), so `sim.integrator` reports `'rk4'` for a user who asked for `'jax'`. Proposal: validate the name at `init_solver()` with a coded error listing the choices, accept `'scipy'` as an alias of `'LSODA'` (or `'RK45'`), and keep the user's word in `sim.integrator`. Also, under a SciPy integrator the run is stepped from Python and prints the per-step progress bar at `verbose=0.5`, which the whole-run path never prints (verified), so the output differs with the path taken.

7. **The solver vocabulary: cut `sde`, fix `substeps=`, and say what `binomial` costs.** Six names plus `auto` and `stochastic` is fine (and `sim.solvers()` collapsing the stochastic ones into one column is good), but: (a) `substeps=` means three things: integrator substeps for `rk4`/`euler` (default automatic), whole step versus stage-exact chain for `binomial` (default 1, whole steps), Euler-Maruyama substeps for `sde`, and nothing for `tau`/`gillespie`; its docstring at `parameters.py:326` is stale ("one for each stage of the dwell time with the most stages", superseded by `draw_chain()` per implementation.md). (b) The `binomial` whole-step default is a large bias at ordinary steps: a seasonal SIRS (dur 8 and 60 days) at `dt=1` gives `n_I` 17% above the daily ODE on average (max 38%) where `tau` gives +0.5% and `gillespie` −0.8% (`check6.py`); the Erlang-stage test gave +2.5% at `dt=1` and +6.9% at `dt=4`, reduced to +0.6% and +1.8% by `substeps=5`. `W102` fires (dt/mean = 0.125 > 0.1) but says "0.12 of people leave in a step", which does not sound like 17%. The agent-based run has the same bias (+15%), which is the known O(dt) issue. Keep `binomial` (the interop importers need whole-step semantics: `epydemix.py:250`, `atomica.py:283`, odin, camdl), but either default `substeps` to the ODE's rule or make `W102` name the solvers that do not have the problem (the spec asks for exactly that: "naming ... a solver that would not have the problem"). (c) `sde` is used by one test and `pmcmc`'s solver list (`calibration.py:1530`) and by nothing else; its stated niche (large populations with noise) is covered by `tau`, whose cost is bounded by the rates (leaps of `0.03/maxrate`, `kernels.py:880`) and not by the population. Cutting it removes `kernels.diffuse()` (40 lines), `step_sde`/`step_sde_once` (31), the `solver == 5` branches, and one row of the user's table; what is lost is real-valued Gaussian-noise trajectories, which nobody in the corpus or vignettes asked for. (d) `stochastic` picks by `total_pop × n_transitions ≤ 1e6` (`sim.py:347-352`), which is not a count of events (that depends on run length and rates) but is a serviceable rule. (e) `use_kernels` is an engine attribute used only by tests; it needs no user vocabulary and disappears with finding 2.

8. **Movers, deliveries and the movement register are one operation implemented three times.** `kernels.move()` (`kernels.py:562`: a set of compartments, group to group, at a rate), `kernels.apply_shifts()` (`kernels.py:1063`: a share at a time point, from `Shifts`), and `kernels.apply_events()` (`kernels.py:985`: a count at a time point, from `Register`) each move people in some compartments from group g to group h; they differ only in whether the amount is a rate, a share, or a count, and when. Each has its own namedtuple (`Program.mov_*`, `Register`, `Shifts`), its own builder (`init_movers` 57 lines at `solvers.py:1609`, `init_register` 51 plus `register_sets` 31 at `1670`/`1453`, `init_shifts` 16 plus `store_replayed` at `2596`/`2672`), its own agent-side version (`step_transfers` 41 at `3704`, `step_register` 66 plus `add_people` 49 plus `shift_states` at `3828`/`3894`/`3814`), its own JAX version for one of the three (`Run.deliver`, `gradients.py:336`), and its own slot in `run()`, `run_many()` and `advance()`. One `Move` record (compartments, from-group, to-group, amount, kind in {rate, share, count}, schedule) and one kernel would replace all of it, and it is also the natural home for the deferred cascade ("treatments that cure" are a move along a transition to a destination's entry compartments, which `force()` at `solvers.py:1959` already does by hand). What is lost: nothing in function; the hypergeometric "choose whole people at random from a place" in `apply_events()` is the `count` kind's draw.

9. **`I.n` means "in my place" in a rate and "everyone" in a result.** With a space dimension, a `Count` leaf in a rate evaluates through `ctx.local_count()` (`transitions.py:417`), which for compartments is the number in the same place (`Compartmental.local_count`, `solvers.py:1900`) and for agents the number in each agent's place (`Agents.local_count`, `3411`); in a result expression `StockCtx.local_count = count`, the total (`solvers.py:1558`); and an inflow whose rate uses a count arrives per place (`inflow_split`, `solvers.py:731`). 12-backends says `.n` is "used exactly as written under every solver". So `beta * W.n / (W.n + K)` is per place in the rate while `ss.result(W.n)` is the total, with nothing in the spelling to say so, and the behaviour switches on when the user adds `stratify(place=...)`. Give the local count its own spelling (`W.here`, say) and keep `.n` the total everywhere, or state the rule in `describe()` next to the dimensions.

10. **`Crossing` is a shared-memory protocol between engines; one joint program would replace it and unlock the kernels for it.** `Crossing` (`solvers.py:351-534`, 186 lines) plus 28 `self.cross` hooks in `count`, `set_count`, `shift`, `force`, `step`, `update_results` and `kernel_only`, plus `sim.init_crossings()` (57 lines at `sim.py:733`) and `JointRun` (`gradients.py:385`) implement "each engine holds everyone over the product of the diseases' compartments; the owner changes them; the others `refresh()` before reading and `claim()` before writing", stepped one disease at a time. The general mechanism already in the code is "a state of another disease is a dimension" (`strat.kind == 'disease'`, `solvers.py:618`). If a crossing were one `Compartmental` engine over the joint compartment grid, with each disease's flows acting along its own axis, then whole runs, `run_many()`, `advance()` (the particle filter), JAX and the deliveries would all take crossings with no new code, which implementation.md lists as "not yet" in three places (§06, §13 pmcmc, and the Python loop at `Crossing.run()` with one kernel call per disease per step). What changes: the diseases' flows are evaluated together from the same state rather than in turn, an O(dt) change that is the ODE's own rule for flows within a disease (10-execution §Order under each solver).

## Other findings

- **`Engine.make_rng()` seeds from `sum(ord(c))` of the module name** (`solvers.py:586`): modules whose names are anagrams (`'ab'`, `'ba'`) share a stream for outcomes, movers and `take()`. Use a real hash.
- **A plain function module is refused under a compartmental solver.** `analyzers=[lambda sim: None]` with `solver='binomial'` raises `E804: the module "<lambda>" (Analyzer) only works on agents` (`sim.py:368-370`), and under `'auto'` makes the model agent-based with the reason "Analyzer only works on agents" printed (`sim.py:979`), while 12-backends §Functions says functions are tried. `try_functions()` (`sim.py:996`) tries rate functions and modules with `try_groups()` but not function modules. Try them on the probe like the rest, and let `compartmental = True` (departures) be the escape hatch for class modules only.
- **The whole-run condition includes `verbose >= 1`** (`sim.py:1888`), so asking for progress output changes the execution path, the printed output, and (with finding 1) the random numbers. Progress for a whole run can be printed around the call; it should not be a reason to step.
- **The known issue "kernels vs `use_kernels=False` give different numbers" is not acceptable as stated**, because the Python path is a production path (any function-of-the-sim rate) and not only a debug switch; see finding 2 for the fix.
- **`one_step()` allocates a workspace every call** (`kernels.py:1288`) and `step_tables()` copies four tables per step (`solvers.py:2352`); keep the workspace on the engine. Small next to the 200 µs of Python per stepped step, but free.
- **Outcomes are drawn from a different generator and, in `run_many()`, for all runs at once** (known issue). With finding 8's `Move` and the outcome kernels being linear convolutions plus binomial thinning, outcomes can be drawn inside `kernels.run()` per step, which removes the second generator and the known issue together.
- **`Mixing.age_matrix()` stratifies the sim as a side effect** (`solvers.py:195-199`: it appends to `sim.pars.stratify` and calls `sim.init_strats()` from inside the mixing builder, with a note). The spec says a matrix with other age groups is aggregated to the model's (`W404`); adding a dimension to the model from a network is a surprise, even with the note, and it is why `Mixing.init()` has to re-run `init_space()` afterwards (`solvers.py:161-165`).
- **The `id()`-keyed value cache** (`Engine.value()`, `solvers.py:836-859`) pins expression parts in `cache['held']` so that "no new object can take their id" (comment at `845`); a cache keyed on the parameter object itself (`p` is hashable) would not need the pin.
- **Two spellings of an exponential dwell behave differently as agents.** `rate=` is a per-step hazard draw and `dur=8` is a sampled exponential dwell rounded to a step (`schedule()`, `solvers.py:3571`); only the second needs `rescale_exits()` and the `mult_<state>` arrays (`solvers.py:3583-3606`, `3171`) when a modifier changes after the draw. If exponential `dur=` were drawn as a hazard like `rate=`, the rescaling machinery would apply only to non-exponential dwells, and the two spellings of one model would give the same draws (18-conformance suite 1 asks for that for the three spellings; a `rate` and its reciprocal `dur` are a fourth).
- **The `W102` threshold is right but its wording underplays the effect** (see finding 7b); and the spec's promise that each note names "a solver that would not have the problem" is not kept by `W102` (`solvers.py:1100`).
- **`eps=0.03` for tau leaps is hard-coded twice** (`kernels.py:880`, `solvers.py:3037`); the `stochastic` note promises "leap condition 0.03". One constant.
- **`interval()` shifts `sim.t.ti` by −1 while a declared step runs** (`solvers.py:536-553`, applied by the loop at `loop.py:359-370`), so a function of the sim sees `ti = 0` during step 1 (verified: `[0, 0, 0, 0, 0, 1, ...]`, five calls per RK4 step). This is in departures and is consistent, but a Starsim-3-style module's `step()` in the same sim sees `ti = 1` at the same moment; worth one line in the user docs.

Modifiers are already general (one `combine()` for set/multiply/add) and the cost there is only that time-varying ones force `tables()` to re-evaluate everything per step rather than only the flows they touch.

## Correctness of the hard parts

- **Timing convention**: under all six solvers, `n_R[0] = recovery[0] = 0`, `diff(n_R) == recovery[1:]` exactly, and the total is conserved to the last bit (`check1.py`); `gillespie`, `tau`, `binomial` and `abm` stay integer; `sde` stays non-negative and conserved. The departure in implementation.md ("results follow the convention of other frameworks") is implemented consistently across the stepped and whole-run paths (0 difference for one module).
- **Competing hazards**: reversing the declaration order of two `rate=` exits at `rate × dt = 0.5` changes the mean final size by 0.4% (binomial) and 1.5% (abm) over 20 runs, which is noise; the joint draw holds in both (`solvers.py:3025-3033`, `3652-3660`, `kernels.py:309-330`).
- **O(dt) across solvers**: the same model gives final sizes 900 (ode), 980/917/896 (binomial at dt 5/1/0.25), 588/872/882 (abm); both discrete-time solvers converge, but see finding 7b for how large the daily-step bias is on a seasonal model.
- **Chain-binomial through stages**: `draw_chain()` (`kernels.py:228`) is exact for the dwell (the Erlang cohort matches the ODE); the residual +2.5% at `dt=1` is the whole-step holding of infection and is removed by `substeps=`.
- **Time-varying rates**: at a 30-day step on a seasonal SIRS, the ODE with three-point quadratic tables matches the daily ODE to 0.0% at the shared time points (`check6.py`); `tau` holds values per quarter step and lands within 1.4% on average, `gillespie` within 4.4% (one run, stochastic). The quarter-step holding (departure) is sound; thinning would buy little here.
- **Kernels vs Python**: the ODE agrees to the last bit; the stochastic solvers do not (finding 2), and the stepped path is not independent across modules (finding 1).
- **Interpretation vs generated code**: the op-stack interpreter costs a branch per op per group per flow per stage, and the deferred note says a model-specialized kernel would close the remaining 25% to Ghana measles. For JAX the interpretation happens at trace time and costs nothing at run time. For Numba, the interpreter compiles once (12 s, cached) for every model, where generated code would compile per model (1–3 s each, cacheable only by hash); for a framework where people build many small models interactively, the interpreter is the right trade, and a generated kernel could be an opt-in for a long run. I agree with the deferral.

## Decisions I would revisit

- **Known issue "kernels vs `use_kernels=False` give different numbers"**: not acceptable while the Python path is reachable from a model change (finding 2).
- **Known issue "with `sim.run(n_runs=)` ... reported outcomes are drawn for all the runs at once, so differ from a single run with the same seed"**: a run should not depend on how many of them were asked for; draw outcomes inside `run()` per step (see the outcomes bullet above).
- **Departure "under `gillespie` and `tau`, a value that varies smoothly in time is held for a quarter of a step"**: agree, and the measurements above support it.
- **Departure "the default ODE integrator is fixed-step RK4 ... in the Numba kernels; JAX only on request"**: agree; the spec's SciPy/JAX split should be rewritten to match, and `integrator='scipy'` should at least be accepted (finding 6).
- **"Not planned: a whole agent-based run in one kernel"**: agree with the reasoning given.
- **`binomial` taking whole steps by default** (implementation.md §10–12): defensible as the field's convention, but the bias at a daily step is larger than the notes suggest (finding 7b); if it stays, `W102` should say which solver would not have the problem, as the spec asks.

## Things that are good

- The `Program` as one flat representation that Numba and JAX both consume, and the whole-run kernels (`run`, `run_many`, `advance`, `step_at`) sharing one `step()`: 2 µs per step for a small ODE, 3 µs for chain-binomial, 11 µs for exact Gillespie in 10,000 people. Do not cut this; cut around it.
- `draw_chain()`/`chain_probs()` (exact passage through Erlang stages in a whole step), `gillespie_places()` (per-place events), and `settle()` (counts as expected values under the stochastic solvers) are each the right algorithm, compact, and verified.
- The joint competing-hazard draw in both engines, verified order-independent.
- The timing convention and conservation, verified identical across all six solvers and both the stepped and whole-run paths.
- `tables()` evaluating time-varying values once and keeping them across `restart()`; `restart()` itself; `run_many()` with the memory cap for by-group results.
- `Agents.infect_groups()` (`solvers.py:4067`) and `kernels.infection_probs()`: one compiled pass that reproduces the general path's draws exactly, so the fast path does not change results.
