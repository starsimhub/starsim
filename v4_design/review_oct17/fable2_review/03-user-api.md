# User-facing API as implemented: review

I read `00-overview`, `01-objects`, `03-states-and-transitions`, `04-parameters`, `08-interventions`, `09-results`, `17-vocabulary`, `examples/README.md` and the corpus table in `18-conformance`, `starsim/__init__.py`, and the three v4 test files, then wrote and ran (with the v4 python, scripts in `/tmp/claude-1000/-home-cliffk-idm-ssv4/ca97d20f-10b5-44a7-9912-4c092dbb024e/scratchpad/s01_overview.py` through `s09.py`) the overview's one-page example verbatim, the two-line SIR, the three spellings and the class form, the nine build-set models, a stratified model, deliveries, `ss.modify`, and Starsim-3-style models mixed with v4 ones. Verdict: the core language is in good shape and fast (the two-line SIR runs in 50 ms, a calibration of one parameter in 0.7 s, all four spellings hash identically), and `describe()` is genuinely useful. But the overview's own one-page example does not run through (`ss.parallel(baseline=fit.sim)` raises `AlreadyRunError`), the two-line SIR as printed in the spec silently simulates nothing (no seed, and R0 = 0.5), several spec snippets fail or silently do nothing when run as written, and the v3 surface is still fully exported (258 names against the spec's 94), which doubles the vocabulary a new user meets without buying v3 users much, because v4 interventions and modifiers do not reach v3 modules anyway.

## Top findings

1. **The two-line SIR, as written in the spec, runs an empty epidemic and says nothing.** `00-overview.md` and `03 §Three spellings` print `ss.Disease(infection=ss.transmission('S -> I', beta=0.05), recovery=ss.progression('I -> R', dur=10))` followed by `ss.Sim(sir, stop=100).run().plot()`. Real output: `n_I max = 0.0, cum_infection[-1] = 0.0`; `describe()` says `init: S = 1.0 [guessed: nothing given]`. Nobody is infected because there is no `init_prev`, and even seeded, beta × dur = 0.5 so R0 = 0.5 and nothing grows. Every test in `tests/test_transitions.py` adds `init_prev=0.01` and uses `beta=0.3`, which is the tell. A disease with a contact-mediated transition and no seed is never what the user meant; the default should be Starsim 3's `init_prev=0.01` (marked `[guessed]` in `describe()`), or at the least a `W` note at run time ("nobody is infected at the start, so 'infection' can never happen"). Separately, change the spec's canonical numbers to something supercritical (`beta=0.3`), since the example is the first thing every user types.

2. **The overview example fails at the scenarios line: `ss.parallel(baseline=fit.sim, ...)` raises `AlreadyRunError`.** `00-overview.md` says `baseline = fit.sim  # the calibrated sim`. Running it (`s01_overview.py`) gives `starsim.sim.AlreadyRunError: Simulation is already complete. Did you mean to copy the sim before running it?` (printed twice, once from the worker and once from the pool), from `starsim/run.py:836` via `sim.py:1833`. The same happens for `sim.run(n_runs=2)` on a run sim. Either `ss.parallel` and `run(n_runs=)` should take a finished sim as a template (call `sim.new()`, which exists at `sim.py:420`, and re-run), or the spec should write `fit.sim.new()`. The first is right: a sim is "one run", and the user is asking for more runs of it; the fact that one has already happened is an implementation detail.

3. **A misspelled keyword to `ss.Disease` silently becomes a parameter, so a typo silently changes the model.** `01 §The constructor form` says a bare number keyword becomes "a parameter in `sir.pars`". So `ss.Disease(infection=..., recovery=..., init_prv=0.01)` constructs fine with `pars = ['init_prv', 'beta', 'dur']` and runs an empty epidemic (real output from `s02b.py`). This is exactly the "parameters that spring into existence on first use" that `04 §Not included` rejects, one level up. The shorthand constructors do better (`ss.transmission('S -> I', bta=0.3)` gives `TypeError: ... Did you mean 'beta'?`), and `ss.Sim(sir, n_agent=100)` gives a key-not-found error with the list of keys. Proposal: a bare-number keyword that no transition, outcome, or result refers to is an error (`E6xx UnusedParameter: 'init_prv' is not used by any transition; did you mean 'init_prev'?`). A deliberately free parameter (for `pars=` or a subclass's `step()`) is written `ss.par(0.01)`, which is the spec's own rule for "name a parameter when it is reused". Cost: nothing in the tests needs a bare unused number.

4. **`pars=` matches the sim's own parameters before the model's, so `pars=dict(dur=5)` silently sets the run duration.** On an SEIR whose parameters are `beta, dur_latency, dur_recovery`, `ss.Sim(b, stop=100, pars=dict(dur=5))` is accepted and leaves `sim.pars.dur = 5` (real output, `s05_verify.py §D`); `E602` at `starsim/sim.py:415` never fires because `dur` is a key of `SimPars`. Two namespaces (sim settings and model parameters) share one keyword. The collision is made likely by finding 5: a user who learned `sir.pars.dur` from the two-transition SIR will write `pars=dict(dur=...)` on the three-transition one. Proposal: `pars=` on a sim with declared modules should only ever mean model parameters (raise `E602` for `dur`), and the sim's own `dur` (a v3 alias for `stop - start`) should go, since `stop=` covers it.

5. **Parameter names are unstable: `sir.pars.dur` becomes `sir.pars.dur_recovery` when a second dwell time is added.** `test_names` asserts this (`['beta', 'dur_I_to_S', 'dur_recovery']`), and it is what I got: `a pars: ['beta', 'dur'] | b pars: ['beta', 'dur_latency', 'dur_recovery']`. Any `pars=`, `ss.modify`, or calibration bound written against `dur` breaks when the model grows by one transition, which is the normal way a model grows. Meanwhile `04 §The default` promises the stable spelling, `sir.recovery.dur`, and that works, but `sir.infection.beta` returns `None` (real output, `s02b.py`), so the stable spelling is only half there. Proposal: always qualify slot-named parameters by their transition (`dur_recovery` even when there is one), keep `beta` unqualified only because `04` makes it the name of the transmission slot, and make `sir.infection.beta` work. Or drop slot-named parameters from `sir.pars` altogether and make `sir.<transition>.<slot>` the one way to address an inline value; `sir.pars` then holds only what the user named with `ss.par`.

6. **The spec's own snippets silently do nothing, or die with an uncoded error, under the try-it rule.** Three cases run as written: (a) `03 §Custom per-step behavior`'s `seed_cluster` (`if sim.ti == 30: uids = sir.S.uids[:5] ...`): `solver='auto'` chose `ode` because the trial at build time never reaches the branch, then the run died at step 31 with `AttributeError: 'CountState' object has no attribute 'uids'`, not `E804`. (b) `08 §Simple cases`' `ss.transfer(vaccinated=True, coverage=0.7, years=[2021, 2022], eligible=ppl.age > 65)` ran as agents (correctly chosen) and delivered `[0. 0. 0. 0. 0. 0.]` with `eligible [0. 0. ...]`, because an unstratified population's ages are uniform on 0–60 (`people.age.max() = 59.98`), so nobody is over 65; no note says the eligible set was empty on every step. (c) `03 §Source inference`'s SEIR without `source=` is "guessed" at build time, printed only by `describe()`, and the run is silent: peak 180 instead of 3061. Proposals: for (a), run the try-it trial again on the first real call of a per-step function and convert any `AttributeError` on a group-only object into `E804` with the function's name; for (b), a `W` note when a delivery finds nobody eligible on every step it ran, and one default age distribution (the departures list says stratified populations get 0–100; unstratified get 0–60); for (c), print the source guess as a run-time note whenever the guessed source state has a spontaneous outflow to another state that is not the first state, since that is the SEIR shape.

7. **Three spellings of "who is infected at the start" give three different model hashes.** `03 §Initial conditions` says `I = ss.State(init=0.01)`, `init_prev=0.01`, and `init=dict(I=0.01)` are "the same thing". They give identical results but `model` hashes `de3702 / 53ef34 / 7beaa3` and three different `pars` hashes (`s05_verify.py §B`). The equivalence rule in `01` is stated for the three transition spellings and holds for them (all four forms hash `31531b`); it should hold here too, and the initial condition arguably belongs in `pars`, not `model`, since it is a value and not structure. Proposal: resolve all three to one spec field (`init` by state) before hashing, and put it in the `pars` hash.

8. **A modifier is accepted under `interventions=`, `connectors=`, `analyzers=`, and `demographics=`, with identical results; the spec's `modifiers:` slot does not exist.** `00 §The object model` lists `modifiers: ss.modify` as a sim slot; `ss.Sim(sir, modifiers=...)` is a key-not-found error, while all four other slots take it (`s08_last.py`, peak 2399 in each). Tests themselves pass the same modifier as `connectors=` in one place and `interventions=` in another (`test_deliveries.py:82`). Since every module has the same lifecycle, the typed slots carry no meaning for v4 objects; they are a v3 habit. Proposal: document `modules=` (it already exists in `SimPars`) as the one list, keep `interventions=` etc. as sugar for v3 code, and remove `modifiers:` from the spec's object model.

9. **The exported surface is 258 names (plus 32 submodules); the spec's vocabulary is 94.** I classified every name in `starsim/__init__.py` by where it is used (`s07_exports.py`). 68 are used in the v4 tests; 113 appear in the design; 74 appear in no test, doc, design page, or library module at all; 55 more appear only in v3 tests or docs. The 74 are mostly internals promoted to `ss.`: `Agents, Compartmental, Engine, Mixing, CountState, Graph, Transfer, Delivery, RoutineDelivery, CampaignDelivery, BaseTest, BaseScreening, BaseTriage, BaseTreatment, BaseVaccination, campaign_vx, campaign_triage, routine_triage, Pars, Person, IndexArr, IntArr, ModifiableArr, Fit, fit, mismatch, compare, CalibComponent, linear_interp, linear_accum, step_containing, Binomial, ModelComparison, MultiResult, MultiResults, multi_run, make_engine, solver_names, link_dists, make_dist, scale_types, rand_raw, histogram, beta_dist, beta_mean, time_prob, rate_prob, error, note, warn, shrink, metadata, Profile, Debugger, Diagnostics, mock_*, module_map, module_types, find_modules, required, load_fonts, standardize_*, validate_sim_data, apply_age_range, seasonality, PregnancyPars, PostnatalNet`. Proposal: export only the spec's 94 names plus what v3 docs still use (`ss.SIR/SIS/SEIR`, `ss.RandomNet`, `ss.Births/Deaths/Pregnancy`, `ss.uids`, `ss.FloatArr/BoolState`, `ss.MultiSim`, `ss.Samples`, `ss.options`), and leave the rest reachable as `ss.solvers.Engine`, `ss.calibration.Fit`, and so on. The deprecated time classes `ss.rate`, `ss.time_prob`, `ss.rate_prob` warn on use and should go. `ss.day`, `ss.week`, `ss.month`, `ss.year` are exported as *instances* (`ss.day(1)` raises `'days' object is not callable`), one letter from `ss.days`; drop them.

10. **v4 interventions, modifiers, and calibration do not reach v3 modules, so "coexistence" is two disjoint languages, not one.** Real output (`s04_v3.py`): `ss.vaccinate(ss.Vaccine(...))` on `ss.SIR` gives `E506 UnknownDisease: ... the sim has no declared diseases. Use disease=`; `ss.modify(sir.pars.beta, ...)` with `sir = ss.SIR()` gives `E504 ... not 0.1 (peryear). A plain number has no name to refer to`, and the path form `'sir.pars.beta'` gives `E504 ... Quantities that can be modified: randomnet.pars.n_contacts`; `ss.change` the same. The other direction works: `ss.routine_vx(product=ss.simple_vx(...))`, `ss.Births`, and `ss.RandomNet` all run alongside an `ss.Disease` (as agents). See the compatibility section below for the recommendation.

## Other findings

- **Positional values after an arrow are accepted, against `01 §Not included`.** `ss.transmission('S -> I', 0.3)` sets `beta=0.3` and `ss.progression('I -> R', 10)` sets `dur=10` (both ran, `s05_verify.py §C`, `s09.py`). The second is the "guess from the size of a bare number" the spec refused for `@`. Pick one: either reject (spec), or state the rule (the positional is the constructor's main keyword: `beta` for transmission, `dur` for progression) and accept it in the spec. Rejecting is safer, given `03 §A bare number after @ is a rate`.
- **`I >> R @ 10` is a rate of 10 per step and `describe()` prints `rate = 10` with no mark.** This is per spec, but a user coming from the keyword form (`dur=10`) will write it, and 10 per step is never a hazard anyone means. A `W` note for a bare rate above 1 per step on a spontaneous transition would catch nearly every case (the ODE auto-substeps so `W102` does not fire; as agents the note fires but the run continues: `recovery has rate × dt = 36 ... so 1 of people leave in a step`, and note "1 of people" reads as a typo for "all").
- **The default `dt` is one unit, so a model in days run over years silently dies as agents.** `ss.Sim(sir, networks=ss.RandomNet(), n_agents=2000, start=2000, stop=2005)` with `dur=ss.days(10)` gives `unit year, dt year, cum_infection = 0` (`s05_verify.py §H`); the same with `start='2000-01-01', stop='2000-12-31'` gives `unit day` and 1562 infections. The unit is inferred from the start and stop years and overrides the typed `ss.days(10)` in the model. Proposal: when the model has typed durations, the smallest of them should set the default `dt` (or the unit), not the format of `start`; dates and years should set the calendar only. Same root as the known issue "`stop=ss.weeks(12)` runs in weeks even if every rate is per day".
- **`infection_log` records nothing for a declared disease.** `ss.Sim(sir, networks='random', analyzers='infection_log', n_agents=1000, ...)` gives `cum_infection 990, log rows 0` (`s05_verify.py §I`). `09 §The transmission log` says this works. `diseases.py:264` creates the log for any `Disease`, but the agents engine in `solvers.py` never calls `add_entries` (grep finds none). Bug.
- **`sir.solvers()` does not exist on a module; `sir.to_json()` is v3's, not the spec.** `03 §Looking at the model` lists `sir.solvers()` and `sir.to_json()` (the model spec). `hasattr(sir, 'solvers')` is `False`; `sim.solvers()` works and prints a clear table. `to_spec` exists only on the sim (a listed departure). Add `solvers()` to the module or drop it from the spec; the spec table is the better place for it since the solver depends on the sim's networks.
- **`solver='ode'` on `ss.MFNet` raises `E804` rather than printing the partner-change approximation note the corpus promises.** `18 §The corpus #10`: "`solver='ode'` prints the partner-change approximation note and runs". Real: `E804 CapabilityError: cannot run with solver="ode": MFNet has no compartmental approximation yet`. `ss.RandomNet` and `ss.MixingPool` do get the approximation. Not in the departures list.
- **Results have two names for the same series.** `sim.results.sir` holds `infection, cum_infection, new_infections, cum_infections` and they are `allclose` (`s08_last.py`). The spec lists this as open (`09 §Automatic results`, `19`). Decide: `infection` matches the model text and `.select(to=...)`; `new_infections` is v3's. I would keep the transition's name and add `new_infections` only for `ss.Infection` subclasses, where it is the state-named result.
- **A state object belongs to one module, so the spec's "three spellings" block fails if run top to bottom.** `03 §Three spellings` reuses `S, I, R` across three `ss.Disease(...)` calls; the third raises `E206 DuplicateDeclaration: state "S" is used by transitions in two modules, "sir2" and "disease"` (real, `s02_sir_lengths.py`). A user sweeping `beta` in a loop with one `S, I, R = ss.states(3)` outside the loop hits the same. `E206` is right for two diseases in one sim; for two diseases that are never in the same sim it is a surprise. Proposal: `ss.Disease` copies the states it is given (the class form already copies class members, `diseases.py:87`), so a state is a declaration and can be reused; `E206` is then raised by the sim, where it belongs.
- **`ss.contacts('Kenya')` with `stratify=dict(age=[0, 15, 65])` prints its aggregation note twice.** `describe()` shows the note once at the top and once under `note` at the bottom, and `run()` prints it a third time; with `verbose` default the ODE run prints one line and the ABM prints a progress bar. Pick one place for notes.
- **`ss.transmission` has `source=` but `ss.State` has `infectious=True`, and the operator form has neither** (the source is in the rate). Three ways to say which state infects; `describe()` shows the resolved answer, which helps, but the string form's guess is the risky one (finding 6c).
- **`years=` on a sim with no dates means steps** (a listed departure), so `ss.vaccinate(..., years=[5])` in `test_deliveries.py` reads "year 5" and means "step 5". The keyword name misleads in exactly the sims the tests use. `at=` (as `ss.change` has) or `times=` would not.
- **Error quality is good where it is coded, and raw where it is not.** Coded ones I hit: `E602 ... Parameters are sir.beta, sir.dur; did you mean sir.beta, sir.dur?` (the "did you mean" lists everything when the list is short, which reads oddly), `E204`, `E209` (`Give it one, e.g. I >> R @ 0.1`), `E210` (with the fix), `E705` (with both fixes), `TypeError: A set of sources needs parentheses: write (S | I | R) >> D @ rate`. Uncoded ones: `S >> 0.5 * A + 0.5 * B @ 0.3 * I` gives `TypeError: A transition (Transition(-> <unnamed state> @ 0.3 * None)) cannot be used inside a rate; did you mean one of its states?`, which does not say to add parentheses as `03 §Python precedence` promises; `ss.modify(sir.pars.bta, ...)` is a bare `AttributeError: 'Pars' object has no attribute 'bta'`; `res.n_I.select(sex='female')` says `not stratified` rather than listing dimensions (the spec says "lists the dimensions it does have"; here there are none, so the message is fine, but a stratified one should list them).
- **`ss.dur(10)` defaults to years with a warning; `ss.dur(10, 'day')` is an error.** The time module has two generations of API side by side (`ss.dur`, `ss.datedur`, `ss.rate`, `ss.time_prob` next to `ss.days`, `ss.perday`). The spec uses only the lowercase unit forms; the base classes should not be in the first-tier vocabulary.
- **`ss.Sim(sir, solver='ode', n_agents=1000)` runs as an ODE with no note that `n_agents` was ignored.**
- **`msim.plot()` failed once with `ValueError: No legend handles found`** on the overview's stochastic sim (age-stratified, `ss.contacts('Kenya')`, `data=`, `solver='stochastic'` → `tau`, `n_runs=4`; `s01_overview.py`, last stage). I could not isolate it: the same with `binomial` or `tau` on an unstratified sim, with or without data, plots fine. Noting as a repro, not a diagnosis.

## What `describe()`, `run()`, and errors look like in practice

`describe()` is the best thing in the user's chair. The two-line SIR gives 18 lines, every guess marked, and a stratified national model with a vaccine, a screen with follow-up, a modifier, and an outcome gives 26 lines (`s06_errors.py`), which is the right length. Real excerpt from the latter:

```text
dimension    age (age): 0-14, 15-64, 65+; people age between the groups [guessed: ages uniform from 0 to 100]
dimension    risk (plain): low, high
dimension    has_vaccine (plain): False, True
...
delivery     kids: vaccine: vaccine with efficacy against acquisition 0.8; protection lost after a mean of years(2); delivery in rounds; adds has_vaccine as a property of people
delivery     screening: test: test for infection (sensitivity 0.9, specificity 0.98); delivery in rounds
delivery     screening_positive: treatment: treatment that cures with probability 0.9; delivery follow-up
modifier     flu.pars.beta: masks multiply=0.6 start=2020-03-15 stop=2020-06-01
schedule     every day: kids, screening, screening_positive, masks, vaccine, test, treatment, flu
```

Two things are missing from it that the user needs most: the rows that show the delivery `years=[2021]` and `coverage=0.6` (the one line says only "delivery in rounds"), and the age split `[guessed: equal across levels]` for `risk` is printed but the `split=[0.8, 0.2]` I gave is not. `what_modifies()` is clear.

`run()` at default verbosity prints one line for an ODE (`solver: ode (every part of the model has a compartmental form)`) plus notes, but a progress bar with escape codes for agents (`Initializing sim with 500 agents / Running days(0) ( 0/21) ...`). The notes are accurate and short when they appear; the problem is what does not appear (findings 1, 6).

The transition table and equations are exactly what the spec shows, and `sim.solvers()` prints a readable table. `sir.R0()` is a nice surprise that the spec does not advertise.

## Keywords and objects a user needs

For the two-line SIR to produce an epidemic: `ss.Disease`, `ss.transmission`, `'S -> I'`, `beta=`, `ss.progression`, `dur=`, `init_prev=`, `ss.Sim`, `stop=`, `run`, `plot`: 11 names, 2 of them (`init_prev`, a sensible `beta`) not in the spec's line. The concepts: a disease is transitions; a transition is an arrow plus one number; the sim needs a stop; nothing else. That is good.

For the overview example: `ss.par(bounds=)`, `ss.days`, `ss.states`, `>>`, `@`, bare state in a rate, `ss.outcome(delay=, every=)`, `ss.weeks`, `ss.Disease(init_prev=)`, `stratify=`, `ss.contacts`, `total_pop`, `start/stop` as dates, `data=` by column name, `describe`, `run`, `plot`, `calibrate`, `fit.sim`, `fit.pars`, `pars=`, `ss.modify(multiply=, start=)`, `interventions=`, `ss.parallel(name=sim)`, `solver='stochastic'`, `n_runs=`, `msim.plot`: about 28 names and perhaps 12 concepts (parameter with bounds, state, transition, exposure, outcome, stratification, mixing, data matched by name, fit, modifier, scenario, run). Reasonable for what it does; the cost is that two of the 28 do not run (finding 2) and one plots nothing without a seed.

## Starsim 3 compatibility

What it costs the v4 user: 164 extra `ss.` names to scan in tab completion and the docs, of which a v4 user needs none; two product vocabularies (`simple_vx/routine_vx/campaign_vx/routine_screening/campaign_screening/treat_num` alongside `Vaccine/vaccinate/screen/treat`); two disease vocabularies (`ss.SIR(beta=, dur_inf=, init_prev=)` with results `n_infected, n_susceptible` alongside the declared `ss.Disease` with `n_S, n_I`); two time APIs; `describe()` that says nothing about a v3 module (`Sim: 2 modules ... schedule every step: randomnet, sir` is the whole of it); and the sim's own `dur`, `birth_rate`, `death_rate`, `pop_scale`, `rescale*`, `people_results` parameters, which a v4 user will meet in every key-not-found message.

What dropping it would cost: the library (`starsim/library`: HIV, cholera, Ebola, measles, MNCH) and every tutorial and downstream model (STIsim, tbsim) are written as `ss.Infection` subclasses with `step()`, `FloatArr`, `BoolState`, and `uids`; `test_*.py` other than the three v4 files is all v3. That is a real migration, and `implementation.md` says tbsim's TB has already been redeclared, which shows it can be done.

Opinion: keep the v3 *module model* (subclass `ss.Module`, `step()`, arrays, `uids`), because the spec itself says "subclassing adds behavior" and the agents engine needs it; but stop exporting the v3 *vocabulary* at the top level and stop documenting it. Concretely: `ss.SIR/SIS/SEIR` become library models written in the declared form (then `describe()`, `equations()`, `ss.modify`, `ss.vaccinate`, and `calibrate()` work on them, which they do not today, finding 10); `simple_vx`, `routine_vx`, `campaign_vx`, `routine_screening`, `campaign_screening`, `routine_triage`, `campaign_triage`, `treat_num`, `BaseVaccination`, `BaseTest`, `BaseScreening`, `BaseTriage`, `BaseTreatment`, `RoutineDelivery`, `CampaignDelivery`, `Product`, `Dx/Tx/Vx` move to `ss.interventions.*` and the v3 docs; `ss.Connector` and `ss.Analyzer` stay (they are the class form for `ss.modify` and for results the declared form cannot express, and `infection_log` and `dynamics_by_age` are built on them). The intermediate step that costs nothing is a `starsim.v3` namespace that re-exports today's `ss.*` so v3 scripts change one import line, and a top-level `ss` that is the spec's 94 names plus `Module`, `Intervention`, `Connector`, `Analyzer`, `uids`, `FloatArr`, `BoolState`, `options`.

## Things that are good

- `describe()`: every guess marked, the resolved rate shown with its denominator, the schedule at the end. Do not cut it, and do not shorten it; it is the safety net that makes guessing defaults acceptable.
- The four spellings really do hash the same (`31531b` four times), and the class form with `ss.states(3)` in the class body just works, including two instances of one class in one sim.
- The build-set models run as the spec writes them, with the exceptions above: cholera (counts, `ss.null`), Erlang in three spellings with no notes, branching with a competing hazard, age stratification with a matrix or with `ss.contacts('Kenya')` (and the aggregation note), outcomes with `delay=`, `every=`, `duration=`, chained; `calibrate()` in 0.7 s recovering `beta` to 1e-13; the Kenya example as an ODE at 50 million people.
- Error codes with the fix in the message (`E210`, `E209`, `E705`, `E602`), and the parentheses `TypeError` for sources.
- `sim.solvers()`, `sir.equations()`, `sir.transitions`, `sir.R0()`, `sim.what_modifies()`: cheap, correct, and they make the model inspectable without running it.
- `ss.contacts(matrix)` without `age=` fails with the exact line to write; `ss.contacts(matrix, age=...)` with no `stratify=` creates the age dimension for you.
- `ss.change` and `ss.modify(start=)` agree to the bit; ODE and agents agree within the tolerances the tests state.

## Questions for Cliff

1. Should a disease with a contact-mediated transition and no seed default to `init_prev=0.01` (Starsim 3's default), or error? Either is better than running nothing silently.
2. Is `sir.pars` meant to hold inline slot values (`beta`, `dur_recovery`) at all, or only `ss.par`-named ones, with `sir.recovery.dur` as the address for inline values? The spec says both; the implementation does the first and half of the second.
3. `years=` as the campaign keyword: keep it (and have it mean steps in a sim without dates), or rename to `at=` to match `ss.change`?
4. Is the v3 vocabulary meant to be first-tier in v4's docs and tab completion, or only importable? If the latter, is a `starsim.v3` namespace acceptable, or should v3 names simply remain where they are under `ss.` and be undocumented?
5. Should `ss.transmission('S -> I', 0.3)` and `ss.progression('I -> R', 10)` be accepted (and the spec changed), or rejected (and the code changed)?
6. Should the initial condition be in the `pars` hash rather than the `model` hash?
