# Open questions

What this revision settled, what is still open, what is left out of v1, and what could go wrong with the design as a whole.

Sources: the open-questions sections of the documents in [best-practices](../best-practices) (which now live here), choices that had to be made while writing this specification, and choices the implementation made. Section A includes the questions that the implementation and the vignettes have answered since this list was first written; each says what the code does. Many of the "open" items in section B are places where the code makes a guess; the guess is stated, as the code makes it, so that it can be confirmed or changed.

The reasons are one record, read by `sim.solvers()`, `describe()`, and the `CapabilityError` | [12](12-backends.md#functions-try-it) |

## B. Open

### B1. Defaults that are guesses

Each of these is what the code does, and could reasonably go the other way. The rows that the implementation settled are in section A.

| Question | Current guess (what the code does) | Alternative |
|---|---|---|
| **Where `init_prev` puts people** | Through the infection transition, so into `E` in an SEIR | Directly into the infectious state |
| **A transition whose rate uses only counts** (`beta * W.n`) | Classed as spontaneous | A third kind, or counted as an infection when it mentions a state |
| **The denominator** | Written by the user (`N = S + I + R`), or the share in a state, `I.frac` | A built-in total population |
| **Counts across stratifications** | A count used in a rate is matched on the dimensions the two sides share and summed over the rest; people dimensions skip states that are not people | Explicit `.sum()` and `.select()` always. Needs confirming on a real cholera or malaria model |
| **Two `set=` modifiers on the same people** | The later in the loop wins, with a note | An error |
| **Routine delivery** | Each person is offered it once, at first eligibility (recorded as `offered_<delivery>`), or as they reach an age (`at_age=`) | A rate |
| **When capacity runs out** | Recipients chosen at random | A `priority=` function or attribute (oldest first, highest risk first) |
| **A state that is not people** | Its count is advanced deterministically, under every solver and inside an agent-based sim | Drawn (chain-binomial) under the stochastic solvers |
| **Reproducibility across machines** | Identical on the same machine and versions is required; bit-identical across machines is a goal | Required |

### B2. States that are not people

A reservoir or a vector population is an ordinary state that holds a count, in the same disease as the people it infects. That is enough for a water reservoir and a Ross-Macdonald mosquito population. Not settled:

- **Complex vector models.** Mosquito species and larval stages by habitat are stratifications of the vector states (`states=[Sv, Ev, Iv]`), which are regular states, so nothing new should be needed. This needs confirming on a real malaria model with several species.
- **How a reservoir stratifies alongside the people.** The rule is that people dimensions (age, sex, risk) skip states that are not people, `patch` applies to them, and a count used in a rate is matched on shared dimensions and summed over the rest. SimInf's SISe3 vignette (an environmental pressure per herd) is the worked example as compartments; a reservoir per patch alongside agents still needs one.
- **The inference can be wrong.** A state is taken to be a count because no transition connects it to the disease's first state. That is right for every example so far. A disease that deliberately keeps two unconnected sets of people states would be misread and has to say `ss.State(people=True)`. Whether the printed guess is enough is to be seen.
- **Interventions on a vector population** (bed nets, larviciding). They should be `ss.modify` on the vector states' transitions; whether a vector population with its own age structure and interventions is still comfortable as states of the human disease, or wants to be a module of its own, is not known.
- **Small counts under a stochastic solver.** Every state that is not people is deterministic under every solver, as SimInf does (B1). A vector population small enough for its own randomness to matter would want its counts drawn; if one turns up, that is an option on the state.

The way to find out how much this has to grow is to build a real dengue or malaria model with it.

### B3. `solver='auto'` and near-compartmental models

- `'auto'` keeps a model with a non-exponential dwell time an ODE by fitting Erlang stages, and says so; with `approx=False` it runs such a model as agents instead. A dwell time that stages fit badly (a very heavy tail) is still fitted. Whether `'auto'` should prefer agents past some mismatch, and what the threshold would be, is open; the printed line gives the mean and standard deviation kept.
- **A budget for approximations** ([principle 8](../best-practices/principles.md#recommendation)). A stratification runs however many groups it makes; results by group are kept at a coarser interval past about 100 MB a module, but nothing limits the state space itself. Whether, past some number of groups, `'auto'` should pick agents and `approx=False` refuse, and what the number would be, is open.

### B4. Heterogeneity between people in a compartmental run

A dwell-time distribution becomes stages. A distribution on `beta` or `rel_sus` (`ss.lognorm_ex(mean=1, std=0.3)`) runs as agents under `'auto'`; under an explicit `solver='ode'` the mean is used, with a note, and binning it into a dimension (`sir.stratify(rel_sus=[...])`) is the way to keep the heterogeneity. Still open: whether the library should ever offer the binning itself, and with how many groups.

### B5. Which approximation is standard for each network?

- Partner-change rates between sex and risk groups is the standard approximation for a simple sexual network, and is built as the partner-change model for `ss.SexualNet` and `ss.DegreeNet` (see [06](06-routes.md)). For one with age mixing, concurrency, and several partnership types, the grouping and the rates have to be chosen, and the choice printed.
- For a static network where some people have far more contacts than others, the mean contact rate is a poor summary. Grouping by number of contacts is the usual improvement. Whether to build it is open; the note should at least say when the mean is likely to be poor. An agent-based run is always available.

### B6. Stratification details

- **Cross-immunity** is one mechanism, `ss.immunity(due_to=...)`, for strains in shared states and with courses of their own (`ss.Strains(immunity=)`). Between two unrelated diseases it is an `ss.modify`. (Resolved; S7.4, 2026-10-22.)
- **Strains with courses of their own under the compartmental solvers.** As agents they are exact. Under the compartmental solvers, strains that do not affect each other run side by side; strains that affect each other (`immunity=`, a shared state) need agents (decided 2026-10-20: the coupling from the members' shares, marked `approx`, was built and removed), and the crossing is the exact form for explicit `ss.modify(..., where=)` between members. Products over a family (`disease=` a family, `ss.by(<family>=...)` in `efficacy=`) come with it.
- **The exact compartmental form of a strain dimension with partial immunity**: a history of the strains had (`2^k` levels). Until it is built, a compartmental solver raises for it.
- **Stratifying only some transitions**, not just some states. It may be a sign the model wanted two transitions.

### B7. Conditions and custom code

- **Is `who=` with an event enough for event-triggered logic in custom modules?** Deliveries can be triggered by another module's events (a transition, or a delivery or its outcome), and every event is remembered per person (`.ever`, `.count`, `.since`). Whether custom `step()` code needs a helper for "at this person's next visit", or a boolean flag is enough, should be decided against a few real models.
- **Stock that carries over.** `capacity=` per round or per unit time does not express a stock that arrives in batches and is drawn down. A time series covers simple cases; otherwise `deliver=fn`.
- **Within-host state** (viral load, CD4 count, waning immunity). Today a float agent property updated in `step()`, which can be a stratification once binned. More native support, such as declaring a trajectory as a function of time since infection, is worth pursuing and its shape is not settled.
- **Dose response.** A rate can be a function, which covers it in principle. A worked example with viral load is needed to confirm.

### B8. Results and fitting

- **Outcomes that act on individuals.** An outcome is a result, so anything can read it (a trigger on hospital occupancy, a rate), but it marks no individuals; if being hospitalized changes what happens to a person, hospitalization is a state. An outcome with a `duration=` is close to a state with a delay. If real models keep wanting outcomes to act on individuals, a state that takes no part in transmission may serve better.
- **Where do results that combine modules go?** `cases = symptomatic_testing.positive + screening.positive` belongs to neither intervention. It could be declared on the sim, or on the disease that both test for.
- **Results so far.** A trigger that reads a result during a run wants the values up to now (`new[-7:]` as the last seven steps). A `result.so_far` view or a slicing helper is a small thing worth having; it is not specified.
- **Overdispersion.** Superspreading is a property of transmission; noisy reporting is a property of the data. They are different things and need different spellings; only the second has one (the likelihood).
- **Agent-level outputs** (line lists, age at infection, partnership histories) are not time series. `ss.Analyzer` with custom code handles them, which may be the right answer.
- **Should `bounds=` and `prior=` be one argument?** Bounds say what values are valid and where to search; a prior says what is believed. They overlap. Both are kept: the prior defaults to uniform over the bounds, and optimizers use the priors when every series has a likelihood. The question is revisited once calibration has been used in earnest.

### B9. Space

- **Does space need conveniences other dimensions do not have?** Maps as a default plot and per-patch data loading are the likely ones. A subnational planning audience asks spatial questions constantly.
- **Adaptive mobility** (people travel less during an epidemic). The mobility is not a target of `ss.modify` (the targets are parameters, transitions, `rel_sus`, `rel_trans`, and a network's `n_contacts`), and the mixing between places is worked out once at `sim.init()`, so it cannot be written yet; a fittable `away=` needs the same change ([deferred](../admin/deferred.md)). No reviewed framework does it declaratively, so there is nothing to compare against.

### B10. Reproducibility

- **What does common random numbers mean across solvers?** As agents, the pairing is per agent, by slot; under the stochastic compartmental solvers, it is per run, by seed (each module draws from its own generator, seeded from the sim's seed and its name), so it holds only while trajectories stay close; under the ODE there is nothing to pair. An ODE baseline against an agent-based intervention run is not a paired comparison, and nothing says so yet.
- **What is the CRN guarantee when the population differs between scenarios?** Births, deaths, and migration make the agent sets diverge. There is probably a statable guarantee ("agents alive at the divergence point keep their draws") worth writing down.
- **How much contact history should a network keep by default** for contact tracing? (`trace=` on a delivery uses the network's current contacts.)

### B11. The model as code

- Should a people property stratified on the only disease in a sim and the same stratification on the sim be one model? They give the same results, written in two places.

### B12. Names and spellings that may change

- **`ss.null`.** It is a source for births and a sink for deaths, so neither `ss.source` nor `ss.sink` fits both. `ss.null` is short and reads acceptably in both positions; a better word would be welcome.
- **How robust is picking up names from variables?** `S, I, R = ss.states(3)` and `ss.Disease(infection, recovery)` find names by looking at the caller's variables, once, where `ss.Disease(...)` or `ss.Sim(...)` is called. That is convenient and slightly magical. A transition has a fallback (`S_to_I`), and a module one from its states (`sir`); a state does not, and raises a `ValueError`. With no frame at all (from R), the arrow strings and `name=` work. Whether to drop `ss.states(3)` for `ss.states('S I R')`, and to name modules only from their structure, is for Cliff ([deferred](../admin/deferred.md)).
- **Inline parameter names.** An inline value is named after its slot (`beta`, `dur`), and qualified only on a clash (`dur_recovery`). Naming every one `<transition>.<slot>` would be more predictable and would rename the parameters of most models ([deferred](../admin/deferred.md)).
- **The many-run views.** `msim.plot(lines=True)` draws every run, and `.values` is the full runs-by-time array; the names are placeholders for "every run" and "the full array".
- **Which distributions, under which names?** Starsim's list and names are the starting point and can be revisited. `ss.lognorm_ex` and `ss.lognorm_im` are precise and not what anyone would guess. `ss.erlang(k=, mean=)` has been added as a friendlier spelling of `ss.gamma` with an integer shape, and `ss.truncnorm` for a bounded normal.
- **`I` and `I.n`.** A longer spelling for the bare state (`I.contact`, say) would be clearer, and would stop `S >> I @ beta * I` reading like the textbook equation.

### B13. Time

- **Can the Timeline be simpler?** Three views seem irreducible: the step index, time in the sim's own unit, and the calendar date. The proposal is to keep those three and make the rest (`yearvec`, `relvec`, `tvec`) conversions on request, `sim.t.to('year')`. Whether that is a real simplification or only moves the names needs trying in Starsim.
- **A unitless model that later gets a unit.** Giving the sim dates gives it a unit, and the bare numbers that were per step become per day. The note says so; whether a note is enough is open.

### Open questions from best-practices

The open questions of the [best-practices](../best-practices) documents that are still open and not already above, collected here so that there is one list. Each names the document it came from.

- **Deterministic flows inside a stochastic model** (camdl's `deterministic()` and `overdispersed()`, Catalyst.jl's per-reaction scale): per-transition methods are deferred (section C), and their random-number implications (which streams exist, what common random numbers mean) need settling with them. ([stochasticity-and-reproducibility.md](../best-practices/stochasticity-and-reproducibility.md))
- **Ragged stratifications in results and export.** `where=` on `stratify()` is built (people outside have no level, so selecting a level leaves them out), but how such results plot and export (is a man's age missing, or "all ages"?) is untried on a real model. ([stratification.md](../best-practices/stratification.md))

## C. Deferred: not in v1

| Item | Note |
|---|---|
| **Different solvers for different transitions in one run** | Sometimes most of a model is well described by smooth average flows, but one part is a rare chance event. A country that has nearly eliminated polio is the standard example: transmission in a large population can be an ODE, but whether an imported case arrives this month is a matter of chance, and an ODE would instead add a steady trickle of a fraction of a case per day. A mixed run would treat that one transition as whole, random events and everything else as an ODE. If added, it would be a `solver=` keyword on the transition (`ss.transmission('S -> I', beta=1e-6, solver='gillespie')`). Until then, run the whole model with a stochastic solver or as agents |
| **Different solvers at different levels** | Individual animals inside herds that are tracked only as counts, or the reverse. The existing way to combine the two is a state that is not people, which stays a count inside an agent-based sim |
| **Finer network-to-ODE approximations** (pair approximations and the like) | One standard approximation per kind of network. Someone who needs the network's exact behavior runs agents |
| **An `'ide'` solver** | Arbitrary dwell times without stages, by integro-differential equations |
| **Symbolic analysis** beyond `equations()` | Symbolic Jacobians, fixed points, eigenvalues. Gradients for fitting are a different thing and are in (automatic differentiation of the ODE run, in JAX). `R0()` stays as an optional numeric helper for simple models |
| **Travelers in transit** | People in neither their home patch nor their destination. A transit patch can be added by hand |
| **Optimal control** | Interventions that vary in time to optimize an outcome. `cost=` on products gives total cost as a result, which is what cost-effectiveness needs, and `ss.fit.optimize()` reallocates a fixed budget between programs (Atomica's program books), which is the budget optimization that was asked for |
| **Joint likelihoods with correlation between data series** | Series are treated as independent |
| **Edge-level eligibility** | Networks already say who is in contact with whom, and `trace=` on a delivery reaches the contacts of the people it selects (agents only) |
| **Preallocated agent arrays** | An optimization to benchmark before building; it would not change what the user writes |
| **Result caching** | An identical re-run could be a cache hit. It surprises people who expect a re-run to run, and nobody has asked for it |
| **`msim.check_runs()`** | Estimating how many runs a comparison needs. `check_dt()` stays |
| **Movement models beyond gravity and radiation** (`ss.stouffer`, `ss.competing_destinations`) | A matrix or a movement register covers them until a vignette needs one by name. Radiation (`ss.geo.radiation`) is built, since it has no parameters to fit: it gives movement between places with no data to calibrate it to |

## D. Risks

1. **The north star is not met for some frameworks.** "No more lines than the original, and about the same time" is a hard test against a compiled C++ ODE solver or a framework built for one kind of model. The per-vignette table (`tests/north_star.py`, [18](18-conformance.md#13-north-star)) is how this is known: on its first run, 20 of 23 vignettes met the lines target and 16 of 23 the time on repeated runs. The failing rows are published on the "Coming from" pages, and say where the design or implementation needs work.
2. **Guessed defaults are only safe if people read `describe()`.** It is short and marks only what was guessed, and the most consequential guesses (unit, solver, approximations) are printed at run time without being asked. If testing with users shows the output is not read, the answer is to make it harder to miss, not to turn guesses into errors.
3. **The bare-state rule carries a lot.** `beta * I` meaning "exposure through the routes" is what lets one disease run on homogeneous mixing, a contact matrix, or a network without change. It is also a rule a newcomer has to be told once, and the difference between `I` and `I.n` in a rate will be a common question. `describe()` and `equations()` showing the result are the mitigation.
4. **Operator spellings may be too clever.** `S >> I @ beta * I` depends on Python's precedence working out, and has edges (parentheses around a set of sources). The explicit form always works, and error messages for the edges need to be good.
5. **`ss.modify` does a lot of work.** Interventions, co-infection, product efficacy, waning, seasonality, and parameter changes all go through it. If the base and effective value mechanism is slow or surprising, much is affected. It should stay small: a target, an operation, a condition.
6. **Try-it-and-report finds problems late.** A function that cannot run on groups is discovered when it is first called, not when the model is written. `'auto'` tries functions at `sim.init()`, which catches most cases before any time is spent running.
7. **Approximating instead of refusing can mislead.** A user who types `solver='ode'` on a network model gets a result. The one-line note, `solvers()`, and `approx=False` are the safeguards; the recorded differences in [18](18-conformance.md) say how large the effect typically is.
8. **The ordered loop makes module order part of the model.** That is how Starsim works and it allows within-step chains, but two people can build "the same" model with different orders and get slightly different results. `sim.loop` and `sim.check_dt()` make this visible. It matters less than it did: a declared disease takes all of its transitions after the interventions under every solver, and a compartmental run that the kernels take whole (with the deliveries they tabulate) has no module order at run time.
9. **Two languages in one library.** Modules written with `step()` (coded subclasses of `ss.Disease` or `ss.Infection`, and Starsim 3's SIR, SIS, and SEIR in the library, `ssl.AgentSIR` and the others) stay valid next to declared diseases; `ss.SIR`, `ss.SIS`, and `ss.SEIR` are now declared, and the v4 verbs (`ss.modify`, conditions, `sim.fit()`) work on modules written as code too. If the declared form does not cover enough real models, most models will be mostly custom code and the benefits (equations, a choice of solver, stratification) will apply to little of them. The share of each vignette that needs custom code is the thing to watch.
10. **More is inferred than before.** Which states are people, the sim's unit, and the names of states all come from what was written and not from a declaration. Each is printed, and each has an explicit spelling (`ss.State(people=False)`, `unit=`, `ss.states('S I R')`). They are safe to the extent that the printed line is read, which is risk 2 again.
11. **Stratifying in place loses the unstratified model** unless a copy was asked for. In place is the default because it is the usual case, and a line that silently did nothing to `sir` would be the more common mistake; the error on stratifying twice is what a re-run notebook cell hits.
