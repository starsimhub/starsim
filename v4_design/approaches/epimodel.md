## What it's for

EpiModel simulates infectious disease dynamics over *statistically estimated* contact networks. Its distinguishing claim is not the epidemic model — the built-in disease types are SI, SIR, and SIS — but the network model: partnerships are generated by an exponential-family random graph model (ERGM) fitted to target statistics such as mean degree, concurrency, partnership duration, and assortative mixing. This puts it in a category of one within the landscape: everywhere else, contact structure is either assumed (random mixing, contact matrices) or read in from data; in EpiModel it is a fitted statistical object with its own diagnostics.

The deterministic and random-mixing model classes exist mainly as a teaching and comparison ladder alongside the network class, and the package is explicitly built around that ladder — the same conceptual model can be run as an ODE, as a stochastic random-mixing model, and as a network model, so that the contribution of each assumption is visible.

## How a model is specified

Three inputs, always, for all three model classes:

- `param.dcm()` / `param.icm()` / `param.net()` — epidemic parameters
- `init.dcm()` / `init.icm()` / `init.net()` — initial conditions
- `control.dcm()` / `control.icm()` / `control.net()` — everything else: model type, number of steps, number of simulations, and *which modules to run*

and then `dcm(param, init, control)`, `icm(...)`, or `netsim(est, param, init, control)`.

Each of these three constructors collects its named arguments *and arbitrary `...` arguments* into a classed list. So the parameter vocabulary is open: `param.net(inf.prob = 0.4, act.rate = 2, my.new.param = 0.7)` is legal, and `my.new.param` is retrievable inside any module via `get_param(dat, "my.new.param")`. There is no parameter schema and no declaration step; a misspelled parameter name is not an error until something looks for it.

Network models add two steps in front of the epidemic model:

1. `netest(nw, formation, target.stats, coef.diss)` — fit the (T)ERGM. `formation` is a one-sided R formula of ERGM terms (`~edges + concurrent + degrange(from = 4)`), `target.stats` are the values those terms should take, and `coef.diss` encodes partnership dissolution, usually as a mean duration.
2. `netdx(est, nsims, nsteps)` — simulate from the fitted model and check that formation statistics and durations recover their targets. This diagnostic step is treated as mandatory in the documentation, and is a genuinely distinctive piece of practice: the contact structure is validated *before* any disease runs on it.

### Extension: modules

Beyond the built-in types, a model is extended by writing module functions and passing them into `control.net()`. The contract is minimal:

```r
progress_module <- function(dat, at) {
  status <- get_attr(dat, "status")
  ids.EtoI <- which(status == "e" & runif(length(status)) < 0.1)
  status[ids.EtoI] <- "i"
  dat <- set_attr(dat, "status", status)
  dat <- set_epi(dat, "ei.flow", at, length(ids.EtoI))
  return(dat)
}
```

A module is `function(dat, at) -> dat`: it takes the whole simulation state and the current time step, mutates state through accessors, and returns the state. `control.net()` exposes named slots — `infection.FUN`, `recovery.FUN`, `departures.FUN`, `arrivals.FUN`, `nwupdate.FUN`, `prevalence.FUN`, and so on — and any additional `.FUN` argument becomes a new module. Execution order is the order of those slots, overridable wholesale with `module.order`.

The state object `dat` is accessed through a small accessor API rather than directly: `get_attr`/`set_attr` (per-agent attributes), `get_param`/`set_param`, `get_epi`/`set_epi` (time series of outputs), `get_control`, `get_current_timestep`, plus `add_attr` and `get_posit_ids`. The accessors are a relatively recent formalization of what used to be direct list manipulation, and they are the closest thing EpiModel has to a declared interface.

## Core abstractions

| Concept | EpiModel name | Notes |
|---|---|---|
| Population | `network` object of size `n`, or `s.num`/`i.num` counts | Agents are network vertices; there is no separate person object |
| State | `status` nodal attribute, values `"s"`, `"i"`, `"r"`, `"e"`, … | A single string attribute, not a set of typed flags. Custom states are just new string values |
| Other agent state | arbitrary nodal attributes | Untyped R vectors; `get_attr`/`set_attr` |
| Transition | a line of R inside a module | There is no transition object. Transitions are procedural code, not data |
| Contact structure | fitted `netest` object → `networkDynamic` / edgelist | The distinguishing abstraction |
| Contact "act" | `act.rate` parameter | Acts per partnership per time step, distinct from the partnership itself — an unusually explicit separation of *relationship* from *exposure* |
| Time | integer step `at`, starting at 1 | No units, no dates, no per-module time step |
| Parameter | element of the `param.*` list | Untyped; may be a scalar, or a vector interpreted as a time series or as a sensitivity sweep depending on context |
| Intervention | `inter.eff` / `inter.start` built in; otherwise a module, or a scenario updater | Two mechanisms, see below |
| Output | `dat$epi`, a named list of per-step vectors | Written by modules with `set_epi(dat, name, at, value)` |
| Stochastic replicate | `nsims` | Replicates are the unit of parallelism; `future`/`future.apply` backend |

## Time

Time is an integer counter `at`, incremented once per pass through the module list, and everything is expressed per time step. There are no units and no calendar: `rec.rate = 0.05` means "per step", and the modeler holds the interpretation in their head. Rates and probabilities are not distinguished at the type level either — `inf.prob` is a per-act probability, `act.rate` a count per step, `rec.rate` a per-step hazard, all plain numerics, and the per-step transmission probability is assembled by hand in the infection module as `1 - (1 - transProb)^actRate`.

Two consequences worth carrying into the design. First, changing `dt` in an EpiModel model means rescaling every parameter manually, and nothing in the framework can check that it was done consistently — this is precisely the class of error camdl's dimensional types are built to catch. Second, the network model's dissolution coefficients are calibrated to a duration *in time steps*, so the network and the epidemic are locked to a common step by construction; per-module time steps of the kind Starsim supports are not expressible.

Vector-valued parameters are overloaded onto time in one specific place: `inf.prob` and `act.rate` may be vectors indexed by *time since infection*, giving stage-dependent infectivity, with the last element carried forward. That is an elegant trick and a good example of implicit semantics — the same vector passed to `param.dcm()` instead means a sensitivity sweep.

## Stochasticity and reproducibility

Base R RNG, seeded by `set.seed()` at the top of the script. Replicates within a run share the seed stream when run serially, and use `future.seed = TRUE` (L'Ecuyer-CMRG streams) when parallelized, so parallel runs are reproducible but *not* identical to serial ones. There is no notion of a per-module or per-agent random stream, and therefore no common random numbers across scenarios: comparing two interventions requires averaging over replicates rather than differencing paired trajectories.

## Populations and mixing

Three levels, and the differences between them are the pedagogical core of the package:

- **DCM**: no population, just compartment sizes; optionally two groups with a `balance` argument that reconciles mismatched act rates between groups.
- **ICM**: individuals, random mixing, binomial draws.
- **Network**: individuals with attributes, partnerships from a fitted TERGM. Supports multiple network layers (`num.nw`), attribute-dependent formation (`nodematch`, `nodefactor`, `absdiff` and the rest of the ERGM term vocabulary), vital dynamics with arrivals and departures, and `tergmLite` for speed on large populations.

Transmission on the network works from the **discordant edgelist**: at each step, `discord_edgelist()` enumerates every serodiscordant active partnership, a per-edge probability is computed, and `rbinom` decides. This is a clean and inspectable formulation — the unit of transmission is an edge, and the edgelist is available to the modeler — and it is the same formulation Starsim uses.

## Interventions

Three mechanisms, layered historically rather than designed together:

1. **Built-in**: `inter.eff` and `inter.start` parameters, applied as a multiplicative reduction on transmission probability from a given step. Convenient; only one intervention, only on transmission.
2. **Modules**: an arbitrary `function(dat, at)` inserted into the control list. Fully general, entirely procedural.
3. **Scenarios and updaters**: `param.net()` accepts a list of `.param.updater.list` entries — `{at, param = list(...)}` — that overwrite named parameters at a given step. `create_scenario_list()` turns a long-format data frame of `scenario.id / param / at / value` into a list of scenarios, and `use_scenario(param, scenario)` applies one. Combined with `param.net_from_table()`/`param.net_to_table()`, this gives a data-driven, non-programmatic path for both scenario definition and time-varying parameters.

Mechanism 3 is the interesting one for this project: it is a small, declarative, tabular grammar for "change parameter *p* to value *v* at time *t*", which covers a surprising fraction of real intervention specifications without any code. Its limits are equally instructive — it can only set parameter values, so anything that targets a *subset of agents* (screen 40% of over-50s annually) has to fall back to mechanism 2.

## Results

`dat$epi` is a named list of numeric vectors, one per output, one entry per time step, written by whichever module produced it. Built-in models populate compartment counts (`s.num`, `i.num`, …) and flows (`si.flow`, `ir.flow`, …). Custom outputs are created simply by calling `set_epi()` with a new name — again, no declaration.

Two additions are worth noting. **Trackers** (`epi.trackers` in `param`) let a summary statistic be declared as a function of `dat` and computed automatically each step, which is the one place EpiModel supports declarative rather than imperative output. And the **transmission matrix** (`get_transmat()`) records every infection event with infector, infectee, time, and probability, convertible to a phylogeny via `as.phylo.transmat()` — a first-class, per-event provenance record that most frameworks in the landscape lack.

Extraction is `as.data.frame(sim)`, with `out = "mean"`/`"sd"`/`"vals"`; `summary(sim, at = t)` gives cross-simulation summaries.

## Minimal model

Deterministic SIR:

```r
library(EpiModel)

param   <- param.dcm(inf.prob = 0.2, act.rate = 5, rec.rate = 1/3)
init    <- init.dcm(s.num = 999, i.num = 1, r.num = 0)
control <- control.dcm(type = "SIR", nsteps = 200)

mod <- dcm(param, init, control)
plot(mod)
```

The corresponding stochastic random-mixing model is the same three lines with `icm`/`.icm` and `nsims = 10`, which is the point of the parallel API.

Under the hood the built-in SIR is an ordinary `deSolve` derivative function, and a custom model is written the same way and passed as `control.dcm(new.mod = my_model)`:

```r
mod_SI_1g_cl <- function(t, t0, parms) {
  with(as.list(c(t0, parms)), {
    num     <- s.num + i.num
    lambda  <- inf.prob * act.rate * i.num / num
    si.flow <- lambda * s.num
    list(c(-si.flow, si.flow, si.flow), num = num)
  })
}
```

Note that the returned derivative vector is positional and must match the order of `init.dcm()` — an unchecked coupling between two separate function calls, and a good argument for named transitions.

## Worked example

The canonical worked example is the SIS-on-a-dynamic-network pipeline from the package introduction, which exercises the parts no other framework has:

```r
library(EpiModel)
set.seed(12345)

# 1. Specify and fit the contact network
nw           <- network_initialize(n = 500)
formation    <- ~edges + concurrent + degrange(from = 4)
target.stats <- c(175, 110, 0)            # mean degree 0.7; limited concurrency; no degree 4+
coef.diss    <- dissolution_coefs(dissolution = ~offset(edges), duration = 50)
est          <- netest(nw, formation, target.stats, coef.diss)

# 2. Diagnose the network before any disease runs on it
dx <- netdx(est, nsims = 5, nsteps = 500)
plot(dx)
plot(dx, type = "duration")

# 3. Layer the epidemic on top
param   <- param.net(inf.prob = 0.4, act.rate = 2, rec.rate = 0.05)
init    <- init.net(i.num = 10)
control <- control.net(type = "SIS", nsims = 5, nsteps = 500)
sim     <- netsim(est, param, init, control)

# 4. Analyze
plot(sim, sim.lines = TRUE, qnts = 0.5)
d  <- as.data.frame(sim)
tm <- get_transmat(sim)
```

For a full research-scale model, `EpiModelHIV` is the reference implementation: multiple network layers (main / casual / one-off), age and race attributes driving both formation and progression, a full HIV natural history with viral load, and PrEP and ART as modules. It is also the honest illustration of the framework's ceiling — at that scale, essentially every module is user-written and EpiModel is providing the network engine, the loop, and the accessors rather than any disease vocabulary.

## Strengths

- **Contact structure as a fitted, diagnosable object.** Nothing else in the landscape offers `netest` → `netdx` → `netsim`, where the network is estimated from target statistics and validated on its own terms before the epidemic is attached.
- **The parallel API across paradigms.** `param`/`init`/`control` plus a class-specific runner is the same shape for ODE, stochastic random mixing, and networks. It is not automatic interconversion — the modeler rewrites the model — but it makes the comparison cheap, and it establishes that a single input vocabulary can serve three execution modes.
- **A genuinely minimal extension contract.** `function(dat, at) -> dat` is about as small as a module interface can be, and it is learnable in one sitting.
- **Explicit separation of partnership from act.** `act.rate` within a persisting partnership is a distinction most frameworks collapse, and it matters for STIs.
- **Per-event transmission provenance** via the transmission matrix, including the route to a phylogeny.
- **A tabular scenario grammar** (`scenarios.df`, `param.net_from_table`) that lets time-varying parameters and scenario sets be specified as data.
- **Exceptional teaching infrastructure** — the JSS paper, the SISMID/NME course, and the Gallery of worked extensions. Much of EpiModel's influence is pedagogical, and the design pays for that with explicitness.

## Limitations

- **No typed time.** Everything is per-step, unitless, and unchecked; rates, probabilities, and counts are all `numeric`. Changing the step size is a manual rescaling exercise.
- **State is a string.** `status == "i"` is the whole disease-state mechanism. Multi-disease models, co-infection, and orthogonal state dimensions (infected × vaccinated × pregnant) have to be encoded by hand into extra attributes, and nothing coordinates them.
- **Transitions are code, not data.** There is no object representing "S → I at rate λ". A model cannot be introspected, diagrammed, dimension-checked, or converted to another paradigm without parsing R.
- **No declaration step of any kind** — parameters, attributes, and outputs all spring into existence on first use. Typos become silent behavioral differences.
- **Positional coupling** between `init.dcm()` ordering and the derivative vector returned by a custom DCM.
- **One time step for the whole simulation**, shared between the network process and every disease process.
- **No common random numbers**, so paired scenario comparison is unavailable and small intervention effects need many replicates.
- **Single-disease by default.** There is one `status` attribute; co-circulating pathogens are a modeling exercise, not a framework feature.
- **R-and-statnet-bound.** The ERGM machinery is the reason to use EpiModel and also the reason its models cannot straightforwardly leave R.

## Implications for the lingua franca

1. **Adopt the three-part input split.** `param` / `init` / `control` — model parameters, initial conditions, execution settings — is a clean and well-tested separation, and the fact that the same split serves ODE, ICM, and network models is direct evidence that it is paradigm-independent. It maps onto camdl's `parameters` / `init` / `simulate` blocks almost exactly, which is a useful convergence to note.
2. **Take the network as a first-class, *specifiable* object, not just an input.** EpiModel's strongest idea is that a contact structure can be described by target statistics (mean degree, concurrency, duration, mixing) and then generated. A lingua franca that only accepts an edgelist cannot express "a network where mean degree is 0.7 and partnerships last 50 days" — and that description, not the edgelist, is what modelers actually have. Whether the language should include a network-specification vocabulary of this kind is a real design question raised by this framework.
3. **Keep partnership and act distinct.** Duration-of-relationship and acts-per-unit-time are different quantities with different data sources. Collapsing them into a single "contact rate" is lossy for anything sexually transmitted.
4. **Do not repeat untyped time.** EpiModel is the clearest case in the review for why the language needs dimensional types on rates, probabilities, durations, and counts: the framework is otherwise well designed, and every one of its time-related sharp edges follows from `numeric` being the only type.
5. **Make transitions data.** The single largest gap between EpiModel and this project's goals is that an EpiModel model is a set of R closures. Everything the design wants to do downstream — diagram it, convert it to ODEs, check it, generate it from prose — requires the transition to be an inspectable object.
6. **Steal the tabular scenario grammar, then extend it.** `{scenario, param, at, value}` is a good minimal declarative form for time-varying parameters and scenario sets. Its failure mode — anything targeting a subset of agents drops back to procedural code — tells us where the intervention vocabulary needs to be richer: interventions need an *eligibility* expression, not just a parameter and a time.
7. **Record transmission events.** The transmission matrix is cheap, generally useful, and enables phylodynamic comparison. It should be part of the standard result set rather than an opt-in.
8. **Note what the parallel API does *not* do.** EpiModel gets you three paradigms with one input vocabulary but three separately written models. That is the honest baseline this project is trying to beat: same vocabulary *and* same model text.
