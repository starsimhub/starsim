# Starsim v4: the working plan

Written 2026-10-21 on `v4-simplify`, merging [oct20/simplify_plan.md](../oct20/simplify_plan.md) (the simplification plan, which governs) and [oct20/implementation.md](../oct20/implementation.md) (the remaining work after the `v4-rs` merge). This replaces both as the working plan; they keep the full history of what was done and why, including each item's original brief and its done notes. Here, done items are one line each, keeping only what later work needs (what changed in behavior, what was left, and questions for Cliff); open items keep their full brief. References in brackets point back to the surveys, as in the simplification plan: [Cx §2.5] is section 2.5 of [simplify_codex.md](../oct20/simplify_codex.md), [Cl 13] item 13 of [simplify_claude.md](../oct20/simplify_claude.md).

The [constitution](../constitution.md) governs this plan: where they differ, the constitution wins, and the plan should be changed to match.

Sizes: S is under a day of agent work, M a few days, L more. **SWA** marks a silent wrong answer.

## In one page

- **The direction** [Cx Recommendation, §6]: ordinary Python components are the foundation, and the declarative language is an optional way of building them. A modeler should be able to say "I can use this loop with my arrays, then add only the services I need", and an engineer should be able to write an ordinary component without touching solver choice, graph expansion, JAX, source generation and the namespace together.
- **The compartmental boundary is firmer** [Cx §2, Cl "The core language"]: a small declared subset has explicitly supported compartmental forms ([oct20/simplify/support_matrix.md](../oct20/simplify/support_matrix.md)). Individual histories, parent–child links, queues and remembered selection run as agents (`auto` picks agents; an explicit compartmental solver raises one clear `CapabilityError`). User-owned NumPy components keep their own algorithms. Crossing stays, simplified and bounded; pregnancy has a small, explicitly described ODE approximation.
- **No baggage** (constitution, development principle 4). v4 is unreleased: no deprecation shims, no moved-name hints, no migration examples. But avoid needless incompatibilities, such as renaming a class whose meaning is unchanged. Migration is by AI-assisted scripts (`python -m starsim.interop.migrate`) and the migration skill. What v3 users relied on must still be possible with the new classes, though not every bell and whistle.
- **What stays in the package but leaves the root**: `ss.interop` and `ss.library` stay (and the library should grow), but are not imported by `import starsim`; inference is the submodule `ss.fit`; errors, debugging and spatial tools get submodules (S6.7). Plotting stays first-class and at the top level.
- **JAX and BlackJAX are dependencies**, imported when first used; the kernels' ODE and the JAX run stay two implementations of the same steps, kept in agreement by a test (S1.6).
- **Robyn's Phase B is closed.** What was built of B2, B4, B5 and B9 stays; B1, B6 and B7 were paused by S0.2 and their compartmental forms removed by S3. No strict xfail is left for Phase B.
- **Startup time is now a requirement** (constitution, secondary principle 4): a simple model must run without a long compile, and compilation is opt-in. The compartmental kernels now run uncompiled by default, with the same results (S5.11); agents compile about 5 s once per install, which is accepted.
- **Docs still wait** for the final implementation; what goes stale meanwhile is listed under [Stale](#stale), not fixed on every change (constitution, development principle 1).

## Rules for implementing this plan

The Codex architecture is the governing direction; the Claude inventory supplies concrete cuts, not a requirement to complete every refactor. Cliff's explicit decisions take precedence over either survey. Keeping interop, the library, inference, pregnancy, strains, plotting and the existing import style is compatible with modularity: what matters is that the scheduler and numerical components do not depend on their internals.

- **Do not replace deleted features with a new framework.** No universal capability lattice, generated multi-backend compiler, generalized hybrid population engine, or mandatory policy-builder vocabulary. If a cut needs a large replacement, stop and reassess that item rather than force it through for a line target.
- **Separate the kinds of support.** A component can run in the Python schedule without population data, graph lowering, whole-run compilation, gradients, serialization, or snapshots. Those are separate optional capabilities; absence of one must not block an ordinary run. The global declared solver governs declared population models, not the internal algorithm of an opaque NumPy component.
- **Preserve scientific meaning, without over-correctness** (constitution, primary principle 4, which ranks below simplicity, performance and flexibility). Conservation, competing risks, event timing, shared-person correlations, CRN and observation alignment remain requirements, and a silent wrong answer is still a bug. But stated approximations (Euler steps, float32, a coarse step) are usually fine; don't add machinery to remove an error the user would accept. A fallback/refusal must occur before unsupported declarations start running. Do not retry a partially executed arbitrary callback under another solver.
- **Use concrete replacements, not test counts, to justify cuts.** One test is not evidence of low usage; zero downstream callers is a search result, not a permanent fact. For each removed convenience, demonstrate its supported replacement or record that the capability is deliberately being dropped. Keep small helpers when replacing them introduces more rules.
- **One ownership contract and one schedule.** Ordinary arrays/callbacks must remain usable outside Starsim. Category keywords and the agent phase preset stay; neither should impose people or disease initialization on independent components. A schedule must say when a callback observes state and when mutations become visible.
- **Spec first.** A change to behavior or API starts in the spec (`v4_design/design/`); the code is then changed to match it, and the changed spec files are copied unchanged to LFD's `design/` (a straight copy, no separate edit).
- **Work nimbly** (constitution, development principle 1): beyond the spec, a change updates the code and the tests it affects. It does not update every doc page, LFD vignette, importer, migration row or downstream repo for each rename: add what is now out of date to [Stale](#stale), and work the list off at S8.2–S8.3. Add a test for a real gap, not for each change.
- **The constitution's examples illustrate; they don't specify.** Read each principle as a goal for the whole system (e.g. composability: fewer hidden dependencies, so that many kinds of mix-and-match become easy), not as a list of named cases to support. A plan item should improve the system; one example turning out infeasible is fine if the system is better.
- **Fix the cause where it lives** (constitution, development principle 3): if the clean fix is in Numba, Sciris or a downstream model, write up the proposed fix there rather than build a workaround in Starsim; don't make it in the other repo unasked.
- **Distinguish moves from deletions.** Namespace changes and moves into the in-package library save no package lines. Benchmark-dependent savings and new adapter code must be counted separately. Useful documentation and scientific validation are not a line budget.
- **Checks**: focused checks per change, the full suite (`cd tests && ./run_tests`) at coherent stage boundaries, and the perf guard for execution changes. Reuse the recorded baseline (S0.3) rather than rerunning everything before every edit.

These rules are acceptance criteria for the stages, not extra infrastructure to implement.
